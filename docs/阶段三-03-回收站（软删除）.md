## 一、设计思路

### 1.1 为什么现在做这个

这不是一个"锦上添花"的功能，而是**当前项目里风险最高的一处缺口**。

项目开发过程中真实发生过一次数据丢失事故（BUG-011）：一个临时脚本误删了真实数据库里的全部待办，
**一条都找不回来**。那次事故之后我们做了三件事来防止"脚本误删"：

| 措施 | 防止什么 |
| --- | --- |
| 测试隔离（`_isolation.py`） | 防止 **脚本** 误删数据 |
| 危险函数要 `confirm=True` | 防止 **代码** 误删数据 |
| 启动自动备份 | 提供**事后**补救 |

但还有一个口子没堵：**你自己手滑删错一条待办**。

这三道防线一个都拦不住 —— 因为那是正常操作，不是 bug。
所以需要的是另一种机制：**让"删除"本身变得可以撤销。**

### 1.2 核心思路：把"删除"拆成两步

| | 以前 | 现在 |
| --- | --- | --- |
| 点「删除」 | 执行 `DELETE FROM tasks`，数据**当场消失** | 只写一个 `deleted_at` 时间戳，**数据还在** |
| 能不能救回来 | ❌ 不能 | ✅ 能，去回收站点「还原」 |
| 什么时候真消失 | —— | 你在回收站点「彻底删除」时 |

**这就是"软删除"（soft delete）**：删除不再是"抹掉数据"，而是"给数据打个标记，并让所有查询都跳过它"。

对使用者来说，两版的体验几乎一样 —— 点完删除，列表里立刻就没有了。
区别只在于：**一个是终结，一个是暂停。**

### 1.3 三个关键设计决定

#### 决定一：用什么字段表示"已删除"

| 候选方案 | 优点 | 缺点 |
| --- | --- | --- |
| A. `is_deleted` 布尔值 | 最简单直观 | 只能回答"删没删" |
| B. `deleted_at` 时间戳 | 还能回答"什么时候删的" | 稍微不直观 |
| C. 布尔值 + 时间戳两列 | 信息最全 | **两个字段可能互相矛盾** |

**选 B。**

理由：

1. 回收站要按"删除时间倒序"排列（最近删的排最前），B 天然满足，A 还得再加一列；
2. C 会出现 `is_deleted=1 但 deleted_at 为空`这种自相矛盾的状态 ——
   **一列能表达清楚的事，不要用两列**，少一个不一致的可能；
3. 时间字段在本项目里是现成的套路（`created_at` / `completed_at` / `reminded_at` 都是），
   格式统一是 `YYYY-MM-DD HH:MM`，不引入新概念。

> **判断标准**：`NULL` 表示正常，有值表示已删除。
> 和 `completed_at` 完全同构 —— 学过一个，另一个自然就懂。

#### 决定二：`purge` 只能删"已进回收站"的任务

这是**最重要的一条安全规则**。

假如 `purge()`（彻底删除）能直接删正常任务，那么某天有人手滑写错一行：

    task_repo.purge(task_id)      # 本想写 delete，写成了 purge

就会**直接永久删掉用户的数据，连回收站都没有**。

所以加了一道闸门：

    if task.deleted_at is None:      # 还没进回收站
        return False                 # 拒绝执行

这意味着"彻底删除"必须**先删除、再彻底删除**，走两步。
多一步，就堵死了误操作的路 —— 这和 `confirm=True` 是同一个思路：
**危险操作要让人"多做一个动作"，而不是一键直达。**

#### 决定三：迁移必须"只加列、不动数据"

老用户的数据库里没有 `deleted_at` 这一列。而

    Base.metadata.create_all()

**只会建"不存在的表"，不会给"已存在的表"加新列**。

如果不处理，老用户一升级就会看到：

    sqlite3.OperationalError: no such column: tasks.deleted_at

程序直接打不开 —— 而且是在**他们已经在用、里面有真实数据**的时候。

所以加了一个轻量迁移：用 `ALTER TABLE ... ADD COLUMN` 补上缺的列。
它安全的原因是：**加列不会碰任何已有数据**，只是往表结构里多塞一个字段。

> **没有引入 Alembic。** 专业迁移工具能处理"改类型""删列""拆表"这类复杂变更，
> 但也会带来一个新依赖和一堆配置文件。
> 本项目只需要"加一列"，20 行代码就能安全搞定 ——
> **工具要匹配问题的复杂度。**

### 2.2 数据库迁移

`app/database.py`

    MIGRATIONS = [
        ("deleted_at", "ALTER TABLE tasks ADD COLUMN deleted_at VARCHAR(16)"),
    ]

    def migrate_schema() -> list:
        """给【已经存在】的数据库补上后加的列。"""
        from sqlalchemy import inspect, text

        added = []
        try:
            inspector = inspect(engine)
            if "tasks" not in inspector.get_table_names():
                return added
            existing = {col["name"] for col in inspector.get_columns("tasks")}
            for column, ddl in MIGRATIONS:
                if column in existing:
                    continue
                with engine.begin() as conn:
                    conn.execute(text(ddl))
                added.append(column)
        except Exception as exc:
            raise RuntimeError("数据库升级失败，程序无法继续：%s" % exc) from exc
        return added

### 2.3 仓库层：软删除 + 三个新动作

`app/repositories/task_repo.py`

    def delete(task_id, user_id=1) -> bool:
        """软删除：只打标记，数据还在。"""
        with get_session() as session:
            task = session.get(Task, task_id)
            if task is None or task.deleted_at is not None:
                return False
            now = timeutil.now_str()
            task.deleted_at = now
            task.updated_at = now
            return True

    def restore(task_id, user_id=1) -> bool:
        """从回收站还原。"""
        with get_session() as session:
            task = session.get(Task, task_id)
            if task is None or task.deleted_at is None:
                return False
            task.deleted_at = None
            task.updated_at = timeutil.now_str()
            return True

    def purge(task_id, user_id=1) -> bool:
        """彻底删除 —— 只有回收站里的才能删。"""
        with get_session() as session:
            task = session.get(Task, task_id)
            if task is None or task.deleted_at is None:
                return False
            session.delete(task)
            return True

    def list_deleted(user_id=1):
        """回收站列表，按删除时间倒序。"""
        with get_session() as session:
            stmt = (
                select(Task)
                .where(Task.user_id == user_id, Task.deleted_at.is_not(None))
                .order_by(Task.deleted_at.desc(), Task.id.desc())
            )
            return list(session.execute(stmt).scalars().all())

    def purge_all(user_id=1, confirm=False) -> int:
        """清空回收站。必须显式确认。"""
        if not confirm:
            raise ValueError("purge_all() 会永久删除回收站里的全部任务且无法恢复，"
                             "必须显式调用 purge_all(confirm=True)。")
        with get_session() as session:
            stmt = select(Task).where(Task.user_id == user_id, Task.deleted_at.is_not(None))
            tasks = session.execute(stmt).scalars().all()
            n = len(tasks)
            for task in tasks:
                session.delete(task)
            return n

### 2.4 所有查询都要"跳过回收站"

这是软删除**最容易漏**的一步。漏掉任何一个查询，回收站里的任务就会从那个地方"漏"出来。

本项目中一共 7 处需要加 `Task.deleted_at.is_(None)`：

| 函数 | 漏掉会怎样 |
| --- | --- |
| `get()` | 删掉的任务还能按 id 查到、还能被改 |
| `list_tasks()` | 删掉的任务还在列表里显示 |
| `list_between()` | 删掉的任务还占着日历格子 |
| `list_undated()` | 删掉的任务还出现在"未安排日期"面板 |
| `count_by_status()` | 统计数字对不上 |
| `due_for_reminder()` | **删掉的任务到点还会弹提醒**（最让人困惑的一种） |
| `count_deleted()` | （反向）回收站计数错误 |

### 2.5 接口层

`app/routers/tasks.py`

    GET    /api/tasks/trash              回收站列表
    POST   /api/tasks/{id}/restore       还原
    DELETE /api/tasks/{id}/purge         彻底删除（不可恢复）
    DELETE /api/tasks/trash?confirm=true 清空回收站

> **⚠️ 路由顺序**：`/trash` 是固定字符串，**必须定义在 `/{task_id}` 之前**。
> 否则 `/api/tasks/trash` 会被当成 `task_id="trash"`，转整数失败直接返回 422。
> 这个坑本项目真的踩过（BUG-006），所以专门写了一条回归测试盯着它。

### 2.6 前端

- 四个页面的导航都加上「回收站」入口

## 三、关键代码逐行解释

### 3.1 `deleted_at is not None` 为什么能当"已删除"用

    if task.deleted_at is not None:      # 进过回收站了

`deleted_at` 的类型是"字符串或 NULL"。本项目里它只有两种取值：

- `NULL` —— 没删过
- `"2026-09-13 14:20"` —— 在那个时刻被删了

所以"是不是 NULL"就等价于"删没删"，
而具体的时间字符串又顺便记录了删除时刻。**一个字段干两件事，且不会自相矛盾。**

### 3.2 为什么查询条件要写成 `Task.deleted_at.is_(None)` 而不是 `== None`

    Task.deleted_at.is_(None)        # ✅ 正确
    Task.deleted_at == None          # ⚠️ 能跑，但不是推荐写法

因为 SQL 里判断 NULL 不能用 `=`（`NULL = NULL` 的结果不是真也不是假，而是"未知"），
必须用专门的 `IS NULL`。SQLAlchemy 的 `.is_()` 就是生成 `IS` 的，
而 `== None` 恰好被 SQLAlchemy 特殊照顾、也能生成 `IS NULL`。

**推荐 `.is_()`**：意图明确，而且在"不是单纯比较"的场合（比如 `.is_not(None)`）更可靠。

### 3.3 迁移函数为什么必须"幂等"

    if column in existing:
        continue          # 已经有了，跳过

**幂等** = 同一个操作执行一次和执行一百次，结果一样。

为什么必须幂等？因为 `init_db()` 每次程序启动都会调用它。
如果第二次执行就报 `duplicate column name: deleted_at`，
那么**用户第二次打开程序就会崩** —— 这是个致命 bug。

有了这行判断，重复调用就是安全的。

### 3.4 迁移失败为什么要"响亮地报出来"

    except Exception as exc:
        raise RuntimeError("数据库升级失败，程序无法继续：%s" % exc) from exc

这里的 `except` 看起来像是"捕获了又原样抛出"，多此一举。其实有两个作用：

1. **换一句人话**。原始的 `sqlite3.OperationalError: duplicate column name` 对用户毫无意义，
   `"数据库升级失败，程序无法继续"` 才说得清楚发生了什么。
2. **【绝不】静默跳过**。如果这里写的是 `pass`，程序会带着一个"缺列"的数据库继续跑，
   然后在几十个不同的地方报出各种奇怪的错误 —— 排查难度会大十倍。

   **失败的时候，要让它失败得清清楚楚。**

### 3.5 为什么要给 `deleted_at` 建索引

    Index("idx_tasks_deleted", "user_id", "deleted_at")

因为**几乎每一条查询都带 `deleted_at IS NULL` 这个条件**。

没有索引时，SQLite 要把整张表从头翻到尾才能找出"没被删的"，数据一多就明显卡顿。
建了索引，数据库能直接跳到符合条件的记录。

> **索引的取舍**：它让"查"变快，代价是"写"稍微变慢（每次插入都要更新索引）
> 和多占一点磁盘。对一个"读远多于写"的待办清单来说，非常划算。

### 3.6 前端为什么换成 DOM API 而不是 `innerHTML`

    // 以前（列表页的写法）
    el.innerHTML = '<div class="task-title">' + escapeHtml(task.title) + '</div>';

    // 现在（回收站页的写法）
    var node = document.createElement('div');
    node.className = 'task-title';
    node.textContent = task.title;          // ← 永远只当纯文本

待办标题是**用户自己输入的**。如果标题里写了 `<script>alert(1)</script>`：

- `innerHTML` 会把它**当成标签解析**，脚本真的会跑（这就是 XSS 攻击）；
- `textContent` **永远只当文字**，浏览器不可能把它解释成标签。

`innerHTML` 版本靠 `escapeHtml()` 转义来保证安全 —— 能work，但属于"**记得转义就安全**"。
`textContent` 属于"**想不安全都做不到**"。

**安全设计的高下之分，就在于你是靠"记得小心"，还是靠"结构上不可能出错"。**

## 四、如何运行

> **⚠️ 所有命令都要在 `to_do_list` 这个文件夹里执行**（见 BUG-004 的教训）。

### 4.1 直接运行

1. 双击 **`start.bat`**
2. 浏览器打开 `http://127.0.0.1:8000`
3. 顶部导航多了一项 **「回收站」**，点进去即可

### 4.2 老数据库会自动升级

**你不需要做任何事。** 程序启动时会自动：

1. 建好缺失的表（`create_all`）
2. 给已有的表补上缺失的列（`migrate_schema`）
3. **先备份**，再动数据

**这次升级会不会丢数据？**
不会。它只做一件事：给 `tasks` 表**加一列**。
已有的每一行、每一个字段都原封不动，新列在老数据上填 `NULL`（= 未删除）。

> **已经做过演练验证**：在真实数据库的**副本**上跑了一遍升级，
> 结果是 14 列 → 15 列，待办条数不变，每条内容完全一致，全部标记为"未删除"。

### 4.3 怎么用

| 我想…… | 怎么做 |
| --- | --- |
| 删除一条待办 | 在待办列表点「删除」→ 它进入回收站 |
| 找回误删的 | 进「回收站」→ 找到它 → 点「还原」 |
| 永久删掉某条 | 「回收站」→ 点「彻底删除」→ 确认 |
| 一次性清空 | 「回收站」→ 点「清空回收站」→ 确认 |

**注意**：只有「彻底删除」和「清空回收站」是**不可恢复**的，两处都有二次确认弹窗。

## 六、Bug 排查

### 6.1 症状：升级后程序打不开，报 `no such column: tasks.deleted_at`

**原因**：迁移没有执行，或者执行失败被静默吞掉了。

**排查步骤**：

1. 看日志 `data/logs/app.log`，搜 `数据库升级失败`；
2. 用命令行直接查数据库有没有那一列：

       python -c "import sqlite3; c=sqlite3.connect('data/todo.db'); print([r[1] for r in c.execute('PRAGMA table_info(tasks)')])"

   数一下有没有 `deleted_at`。

3. **如果真没有，先别慌 —— 数据不会丢。** 手动补一列即可：

       python -c "import sqlite3; c=sqlite3.connect('data/todo.db'); c.execute('ALTER TABLE tasks ADD COLUMN deleted_at VARCHAR(16)'); c.commit()"

   然后再启动程序。

> **为什么数据不会丢？** 因为升级只做"加列"，从头到尾没有 `DELETE` 或 `UPDATE`。
> 这也是当初选择"只加列、不动数据"的原因 —— **把风险限制在最小范围。**

### 6.2 症状：删掉的任务还在列表里显示

**原因**：某个查询函数漏了 `Task.deleted_at.is_(None)`。

**排查**：对照本文 2.4 节的表格，逐个检查那 7 个函数。
最稳妥的办法是**为每个函数写一条测试**（本项目的 `tests/test_trash.py` 已经这么做了）。

**经验**：软删除的"漏"，永远不会报错，只会表现为"删了还在"。
所以它必须靠**测试**兜底，不能靠肉眼检查。

### 6.3 症状：删掉的任务到点还是弹提醒

**原因**：`due_for_reminder()` 忘了加过滤条件。

**这是一个特别值得警惕的 bug** —— 用户会觉得"这软件有鬼"：
明明删掉的任务，到点还是弹出来了。

对应测试：`test_deleted_task_never_reminds`。

### 6.4 症状：访问 `/api/tasks/trash` 返回 422

**原因**：路由顺序错了 —— `/trash` 被定义在 `/{task_id}` 后面。

**报错长这样**：

    {"detail":[{"loc":["path","task_id"],
                "msg":"unable to parse string as an integer",
                "input":"trash"}]}

**修复**：把 `/trash` 的路由**挪到** `/{task_id}` 之前。

**这是 BUG-006 的复发。** 因为路由顺序在代码里是"看不见"的，
所以 `tests/test_trash.py::test_trash_route_not_shadowed_by_task_id` 专门盯着它 ——
以后谁挪错了位置，测试立刻会红。

### 6.5 症状：还原报 404，但回收站里明明有它

**可能原因**：你调的是 `/api/tasks/{id}`（普通查询），而不是 `/{id}/restore`。

普通查询接口**看不见回收站里的任务**（这是故意的），
所以它返回 404 是**正确行为**，不是 bug。

**记住这条分界线**：

| 场景 | 用哪个 | 看得见回收站吗 |
| --- | --- | --- |
| 日常查询 / 修改 / 完成 | `get()` | ❌ 看不见（故意的） |
| 还原 / 彻底删除 | `get_including_deleted()` | ✅ 看得见 |

### 6.6 症状：直接彻底删除一条正常任务，返回 404

**这不是 bug，是设计。** 见 1.3 的决定二：
彻底删除**只能**作用在回收站里的任务。

如果你确实想永久删除一条正常任务，正确流程是：

    先点「删除」→ 再去回收站点「彻底删除」

**多这一步是有意为之** —— 让"不可恢复"的操作无法一键直达。
