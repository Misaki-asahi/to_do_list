## 一、设计思路

### 1.1 为什么四个功能一起做？

因为它们本质是**同一件事的四个面**——都围绕"操作一条已存在的待办"。
拆开做的话，前端的列表渲染、事件绑定要反复改四次，每次都要重新测一遍。
**合起来做，接口一次定型，前端只写一遍。**

| 功能 | 接口 | 状态码 |
| --- | --- | --- |
| 查看单条 | `GET /api/tasks/{id}` | 200 / 404 |
| 筛选 + 搜索 | `GET /api/tasks?status=&keyword=` | 200 |
| 修改 | `PATCH /api/tasks/{id}` | 200 / 400 / 404 / 422 |
| 标记完成 | `POST /api/tasks/{id}/toggle` | 200 / 404 |
| 删除 | `DELETE /api/tasks/{id}` | 200 / 404 |

### 1.2 用 PATCH 而不是 PUT（重要）

这两个词经常被混用，但语义差别很大：

| 方法 | 含义 | 危险之处 |
| --- | --- | --- |
| `PUT` | "用我给你的这份**完整数据替换**掉原来那条" | **没传的字段会被清空！** 只想改标题，结果提醒时间、分类全没了 |
| `PATCH` | "**只改我提到的**这几个字段" | 没传的字段保持原样 —— 这才是"改标题"该有的行为 |

对"编辑待办"这种场景，`PATCH` 才是正确的选择。

### 1.3 ★ `PATCH` 的经典难题：怎么区分"没传"和"传了 null"？

假设用户想**清空提醒时间**。前端发送：

    PATCH /api/tasks/5
    {"remind_at": null}

而用户只想**改标题**时：

    PATCH /api/tasks/5
    {"title": "新标题"}

问题来了：这两种请求里，`remind_at` 都"没有值"。后端怎么知道该不该清空它？

**Pydantic 的标准答案是 `model_dump(exclude_unset=True)`：**

    changes = payload.model_dump(exclude_unset=True)

| 情况 | 结果字典 | 后端行为 |
| --- | --- | --- |
| 字段**从没出现过** | 不含该键 | **不改** |
| 字段**出现且为 null** | `{'remind_at': None}` | **清空** |

`exclude_unset` 的字面意思是"排除掉**没有被显式设置过**的字段"。
这是 PATCH 语义在 Python 里的标准实现方式，务必记住。

### 1.4 为什么用 toggle（切换）而不是"设为完成"

如果提供两个接口 `/complete` 和 `/uncomplete`，前端每次点击都要：

    if (task.status === 'done') { await api.uncomplete(id); }
    else { await api.complete(id); }

这段判断写在**前端**，就有两个风险：

1. 前端拿到的 `status` 可能是**过期的**（别人在另一台设备改过了）；
2. 以后还有别的地方要切换状态，这段判断要**再写一遍**，容易写漏。

**改成 `/toggle` 之后，前端只需要说"切换一下"，具体翻成什么由后端决定。**
这种"把判断集中在数据源"的思路，是避免前后端不一致的通用手法。

### 1.5 前端的两个关键技术

**① 事件委托（Event Delegation）**

列表是动态渲染的，如果给每个"编辑""删除"按钮各绑一个监听器：

- 每次重新渲染列表，**所有监听器都要重新绑定**（很容易漏）；
- 100 条待办 × 3 个按钮 = **300 个监听器**。

事件委托的做法：**只在父容器上绑一个监听器**，通过 `event.target` 判断点的是谁：

    listBox.addEventListener('click', onListClick);

    function onListClick(event) {
      const action = event.target.getAttribute('data-action');   // 'edit' / 'delete' / 'toggle'
      const id = parseInt(event.target.getAttribute('data-id'), 10);
      ...
    }

好处：**新渲染出来的元素自动生效，不用重新绑定**。

**② 防抖（Debounce）**

搜索框每敲一个字都会触发 `input` 事件。输入"写周报"三个字 = **3 次请求**。
防抖让它"停下来 300 毫秒后才发一次"：

    function debounce(fn, delay) {
      let timer = null;
      return function () {
        clearTimeout(timer);        // 取消上一次还没执行的
        timer = setTimeout(fn, delay);
      };
    }

> **注意区分防抖和节流**：
> **防抖** = 停下来之后执行一次（适合搜索框、窗口 resize）
> **节流** = 每隔一段时间执行一次（适合滚动加载、鼠标移动）

### 1.5.1 ⚠️ 修订：编辑改为弹窗（用户反馈）

本文档最初记录的是"**就地编辑**"：点"编辑"后，数据填回**顶部那张表单卡片**。

**用户实测后提出**：

> "编辑待办弹出一个新的窗口，在原部分修改不够突出，让别人不好看清"

**问题分析**：用户点的是**列表中部的某一条**，但内容填到了**页面顶部**，
视线要往上跳一大段；而且顶部表单一秒前还是"添加待办"的样子，
**形态变化不明显**，容易让人以为点了没反应。

**修订方案**：

| 操作 | 形态 | 理由 |
| --- | --- | --- |
| **添加** | 保持**内嵌**表单 | 高频操作，始终可见最顺手（可能一口气录入五条） |
| **编辑** | 改为**居中弹窗** | 低频、需要专注；弹窗把它从周围信息里"拎出来"，不易看错 |

配套改进：
- 弹窗标题明确写"**编辑待办 #N**"，一眼知道在改哪一条
- 打开时**全选标题**，方便直接改写
- 增加**未保存修改保护**：有改动时关闭会先确认，避免手滑丢掉编辑内容
- 编辑逻辑独立成 `app/static/js/edit.js`，与列表逻辑（list.js）通过事件解耦

> **通用经验：操作形态要匹配使用频率。**
> 高频操作用"就地/内嵌"减少点击；低频操作用"弹窗/独立页面"保证专注。
> **不要为了代码复用而强迫两种场景共用一套界面** —— 这正是最初犯错的地方。

### 1.6 空状态要说人话

列表为空时显示"暂无数据"是最差的做法——用户不知道是**真的没有**，还是**加载失败**，还是**筛选条件没匹配上**。

本项目根据当前情况给出不同的提示：

| 情况 | 提示 |
| --- | --- |
| 一条都没有 | 还没有任何待办 —— 在上面填写标题，点"添加" |
| 搜索没匹配上 | 没有找到匹配「xxx」的待办 —— 换个关键字试试 |
| 已完成标签下为空 | 还没有已完成的待办 —— 完成一条后会出现在这里 |
| 未完成标签下为空 | **所有待办都完成啦 🎉** —— 休息一下吧 |

**最后一条尤其重要**：用户把事全做完时，应该得到一句鼓励，而不是一片空白。

### 2.2 服务层的六条修改规则（`update_task`）

    # 规则 1：改了标题就再去一次空格
    # 规则 2：时间字段不能改成过去
    # 规则 3：开启提醒就必须有提醒时间（要合并计算，不能只看本次改动）
    # 规则 4：提醒时间变了，就重置"已提醒"标记   <- 最容易被忽略的一条
    # 规则 5：优先级合法性
    # 规则 6：分类去空格，空的变 None

**规则 4 为什么要单独说？** 举例：

1. 提醒设在 8:00，**已经弹过了**（`reminded_at` 被写入）；
2. 用户把提醒改成 9:00；
3. 如果不重置 `reminded_at`，扫描条件是"reminded_at 为空"——
   **它永远不为空，所以 9:00 永远不会弹！**

这类"改了一个字段，却影响了另一个字段的逻辑"的情况，
**必须在服务层统一处理**，绝不能指望前端记得。

## 三、关键代码逐行解释

### 3.1 路由顺序（本步真的踩坑了，见 BUG-006）

    # ✅ 正确顺序
    @router.get("/stats")        <- 固定字符串，必须在前
    @router.get("/{task_id}")    <- 动态路径，必须在后

    # ❌ 错误顺序：/api/tasks/stats 会返回 422
    #    {"loc":["path","task_id"],"msg":"unable to parse string as an integer",
    #     "input":"stats"}

**FastAPI 按定义顺序自上而下匹配，先匹配上的先用**，不是"最精确优先"。
这条和很多人的直觉相反。

> ⚠️ 我在自己的文档里专门警告过这个坑，实现时还是踩了。
> 说明**"知道"和"做到"之间有距离**——所以要有防呆机制（把动态路由集中放到文件末尾），
> 而不能只靠记性。

### 3.2 `if not changes: raise HTTPException(400)`

    changes = payload.model_dump(exclude_unset=True)
    if not changes:
        raise HTTPException(status_code=400, detail="没有提供任何要修改的字段")

如果不加这个判断，用户发一个空的 `{}`，代码会一路跑到数据库执行一次**什么都不改的 UPDATE**——
白白浪费一次写操作，还会刷新 `updated_at`，让"最后修改时间"变得毫无意义。

**早失败（fail fast）**是接口设计的通用原则：明显无意义的请求，在入口就拒掉。

### 3.3 `if value is None: return None` —— 校验器里的"放行"

    @field_validator("title")
    @classmethod
    def _title_not_blank(cls, value):
        if value is None:
            return None          # ★ 关键：None 要放行
        value = value.strip()
        if not value:
            raise ValueError("标题不能为空，也不能只有空格")
        return value

**为什么 `None` 要放行？**
因为 `TaskUpdate` 里"没传 title"就是 `None`，而"没传"意思是**不改标题**，不是"把标题设成空"。
如果这里对 `None` 报错，用户就没法只改描述而不动标题了。

**同一个校验逻辑，在 `TaskCreate`（必填）和 `TaskUpdate`（可选）里的行为必须不同。**
这就是为什么两个类要分开写，而不是继承复用。

### 3.4 `Promise.all` 并行请求

    const results = await Promise.all([api.listTasks(filters), api.taskStats()]);
    renderList(results[0]);
    renderStats(results[1]);

列表和统计是两个**互不依赖**的请求。串行等待要花两倍时间：

    串行：发出请求1 → 等回来 → 发出请求2 → 等回来    总耗时 = t1 + t2
    并行：同时发出请求1和请求2 → 都回来             总耗时 = max(t1, t2)

`Promise.all` 接收一个 Promise 数组，全部成功时返回结果数组（**顺序和传入顺序一致**）。
只要有一个失败，整个 `Promise.all` 就 reject —— 所以外面要包 `try/catch`。

### 3.5 `finally` 保证按钮恢复（第二次强调）

    btnSubmit.disabled = true;
    try {
      ...
    } catch (err) {
      showMessage(err.message, true);
    } finally {
      btnSubmit.disabled = false;   // 无论成功失败都会执行
    }

不写 `finally` 的后果：**一次提交失败后，按钮永远卡在禁用状态**，
用户改完再点也没反应，只能刷新页面。这个 Bug 太常见了，务必形成条件反射。

### 3.6 `closest()` 找到所属的列表项

    const row = target.closest('.task-item');
    const titleEl = row ? row.querySelector('.task-title') : null;
    const name = titleEl ? titleEl.textContent : ('#' + id);

`closest(选择器)` 从当前元素开始**向上**找最近的匹配祖先。
用在事件委托里非常方便：无论用户点的是按钮还是按钮里的文字，都能找到所属的那一行。

后面两个 `? :` 是**防御性写法**：万一元素不存在（页面结构被改动过），
也不会因为"读取 null 的属性"而抛出异常。删除确认框宁可少显示一个名字，也不能整个功能崩掉。
