# 第二阶段 · 功能 12：系统级提醒重构

> 日期：2026-09-12　|　触发原因：**用户反馈**
> 目标：提醒出现在**屏幕右下角**、**系统级**、**不点掉就不消失**

---

## 一、为什么重构

### 1.1 用户原话

> "提示的优先级不高，能不能做成系统级的，不点取消就一直挂在右下角"

### 1.2 原实现的三个硬伤

| # | 问题 | 后果 |
| --- | --- | --- |
| 1 | 只在浏览器里可见 | 切到 VS Code / 微信就完全看不到提醒 |
| 2 | 居中弹窗挡住内容 | 打断感太强，像"报错"而不像"提醒" |
| 3 | 浏览器关掉就完全没有提醒 | 这是原设计文档自己承认的限制 |

> **这三个问题不是"调调样式"能解决的，是架构问题。**

### 1.3 技术方案对比

| 方案 | 系统级 | 位置 | 不点不走 | 浏览器关着也能弹 | 结论 |
| --- | --- | --- | --- | --- | --- |
| 页面内居中弹窗 | ❌ | 屏幕中央 | ✅ | ❌ | 现状，要改 |
| 浏览器 Notification API | ✅ | 右下 | ⚠️ 多数浏览器会自动消失 | ❌ | 不够 |
| **Windows 原生通知** | ✅ | **右下角** | ✅ | ✅ | ✅ **采用** |

### 1.4 关键技术点：scenario="reminder"

Windows 通知 XML 里的这个属性表示"**这是一条提醒**"，
效果是**通知会一直停留在屏幕上，直到用户点掉它**。
不加的话几秒后自动消失 —— 那正是我们不要的。

    <toast scenario="reminder" duration="long">
      <visual>
        <binding template="ToastGeneric">
          <text>待办提醒</text>
          <text>买牛奶</text>
        </binding>
      </visual>
      <audio src="ms-winsoundevent:Notification.Reminder" />
    </toast>

## 二、架构变化（最重要的一节）

### 2.1 主控权从"前端"移交给"后端"

    【重构前】
      前端每 20 秒轮询 /api/reminders/due
      -> 接口内扫描 + 标记 + 返回 -> 前端弹居中模态框
      浏览器关掉 = 没有任何提醒

    【重构后】
      后端线程每 20 秒扫描
      -> 发 Windows 系统通知（右下角，不点不走）
      -> 标记已提醒 + 放进 UI 收件箱
      -> 前端轮询 /api/reminders/inbox（只读快照）
      -> 右下角常驻卡片（带操作按钮）-> 用户处理后调 /ack 确认

### 2.2 ⚠️ 这次改动推翻了我之前的一个设计决定

最初实现提醒时，我**特意砍掉了后台线程**，并在文档里写下推理：

> "reminded_at 应该在用户真的看到时才写入。否则浏览器没开时，
>  提醒会被标记掉却没人看见 —— 等于永久丢失。"

**这个推理当时完全正确。** 但它的前提是：**提醒只能由前端显示**。

现在前提变了 —— 后端自己就能显示提醒（系统通知），
所以"后端标记"不再等于"没人看见"。

> **★ 通用经验：结论要连着它的前提一起记。**
> 只记结论、忘了前提，就会在前提变化时继续执行一个已经过时的决定。
> **写文档时把"为什么"写清楚，价值就在这里。**

### 2.3 双通道通知，各司其职

| 通道 | 谁发 | 作用 | 浏览器关闭时 |
| --- | --- | --- | --- |
| **Windows 系统通知** | 后端线程 | **保证你一定看得到** | ✅ 仍然有效 |
| **页面右下角卡片** | 前端轮询 | **提供操作按钮** | — |

两条通道同时出现是**故意的**：一个负责"送达"，一个负责"能处理"。

### 2.4 提示音只在必要时响

系统通知自带音效。页面再响一次就会听到两声。
所以接口返回 `native_supported`，页面据此决定要不要自己播：

- 系统通知可用 → 页面**不响**（避免双响）
- 系统通知不可用 → 页面**自己响**（兜底）

### 3.2 发通知（`app/core/notifier.py` 核心）

    def show(title, body, lines=None, timeout=20) -> dict:
        """发送一条 Windows 原生通知。返回 {ok, message}，不抛异常。"""
        if not is_supported():
            return {"ok": False, "message": "当前系统不支持 Windows 通知"}
        _ensure_script()
        XML_FILE.write_text(build_xml(title, body, lines), encoding="utf-8")
        result = subprocess.run(
            ["powershell", "-NoProfile", "-NonInteractive",
             "-ExecutionPolicy", "Bypass", "-File", str(PS_SCRIPT)],
            capture_output=True, text=True, timeout=timeout,
            creationflags=getattr(subprocess, "CREATE_NO_WINDOW", 0),
        )
        return {"ok": "TOAST_OK" in (result.stdout or ""), ...}

### 3.3 扫描并发送（`reminder_service.scan_and_fire`）

    for task in batch:
        result = notifier.show(title="待办提醒", body=task.title, lines=[...])

        # ★ 只有通知真的发出去了，才标记"已提醒"
        #   如果通知失败却标记掉，这条提醒就【永远消失】了
        if result.get("ok"):
            task_repo.mark_reminded(task.id, timeutil.now_str())

        # 无论系统通知成没成功，都放进 UI 收件箱
        payload = task.to_dict()
        payload["_native_ok"] = bool(result.get("ok"))
        with _inbox_lock:
            _inbox[task.id] = payload

## 四、关键代码逐行解释

### 4.1 为什么必须用 powershell.exe（5.1），不能用 pwsh（7）

Windows 通知 API 是 **WinRT 组件**：

| 版本 | 能否直接调用 WinRT | 结果 |
| --- | --- | --- |
| **Windows PowerShell 5.1**（系统自带 `powershell.exe`） | ✅ 有类型投影 | 正常工作 |
| PowerShell 7（`pwsh`） | ❌ 没有类型投影 | 直接报错 |

所以代码里固定写 `"powershell"`。这点很容易踩坑 ——
因为现代教程都在推荐 pwsh，但**在这里它偏偏不行**。

### 4.2 脚本存成 utf-8-sig：那个 BOM 不是多余的

    PS_SCRIPT.write_text(script, encoding="utf-8-sig")

**Windows PowerShell 5.1 判断文件编码靠"有没有 BOM"**：

| 文件 | 5.1 怎么读 | 中文结果 |
| --- | --- | --- |
| UTF-8 **无** BOM | 按本地代码页（中文系统是 GBK）读 | **乱码** |
| UTF-8 **有** BOM | 正确识别为 UTF-8 | 正常 |

`utf-8-sig` 就是"带 BOM 的 UTF-8"。那两三个字节决定了中文会不会乱码。

> 对比：Python 自己的脚本反而**不该**加 BOM —— 同一个编码问题，两种语言要相反的处理。

### 4.3 CREATE_NO_WINDOW：不让黑窗口闪一下

    creationflags=getattr(subprocess, "CREATE_NO_WINDOW", 0)

不加这个标志，每发一条通知都会**闪一下黑色命令行窗口**。
一条还不明显，一天几十条就是灾难。

用 `getattr(..., 0)` 是跨平台兼容写法：非 Windows 上这个常量不存在，取默认值 0。

### 4.4 ★ 只有通知成功才标记"已提醒"

    if result.get("ok"):
        task_repo.mark_reminded(task.id, timeutil.now_str())

这是整个提醒系统里**最重要的一行判断**。

考虑这个场景：用户没开通知权限，或者被系统策略拦掉了。
如果不管三七二十一就标记 `reminded_at`，这条提醒**永远不会再出现** ——
而用户从头到尾什么都没看到。

> **宁可下次再试一遍，也不能把没送达的提醒吃掉。**
> 这和"取快递必须先签收"是一个道理：**没签收的，就不算送达。**

### 4.5 收件箱为什么放内存而不是数据库

    _inbox = {}
    _inbox_lock = threading.Lock()

收件箱存的是"**已经弹过系统通知、但页面还没显示过**"的临时状态，
生命周期只有几秒到几分钟。

放进数据库要加字段、写迁移、清理过期数据，**收益却几乎为零**。

**缺点**：程序重启后收件箱清空。但这时系统通知早就发过了，
用户不会因此漏掉提醒，所以可以接受。

> 判断标准：**数据的生命周期和它的存储位置应该匹配。**
> 秒级/分钟级的临时状态放内存，长期数据放数据库。

### 4.6 _stop_event.wait(秒数) 为什么比 time.sleep() 好

| 写法 | 关闭服务时的表现 |
| --- | --- |
| `time.sleep(20)` | 要**干等最多 20 秒**线程才退出 |
| `_stop_event.wait(20)` | 收到停止信号**立刻返回**，马上退出 |

`Event.wait(timeout)` 的语义是："等这个事件被设置，最多等 timeout 秒"。
有人 `set()` 就立刻醒，没人 set 就睡满超时。

### 4.7 ★ 后台线程的"静默死亡"（BUG-012）

改造时我把 `config.REMINDER_POLL_SECONDS` 改名成 `REMINDER_SCAN_SECONDS`，
有一处使用方没改到。如果那一行还在 try 外面，会这样：

    ① 线程执行到这一行
    ② 抛 AttributeError
    ③ 【不在 try 里】-> 异常冒出 _loop() -> 线程函数返回
    ④ 线程直接结束
    ⑤ 页面正常、接口正常，只是【再也不提醒了】

**后台线程死了不会有人告诉你。**
所以现在的规矩是：**循环体里不允许有任何一行裸露在 try 之外**，
并且加了带默认值的 `_interval()` 兜底。完整分析见 **BUG-012**。

## 五、如何运行

### 5.1 先测试通知能不能响

打开 `http://127.0.0.1:8000/settings` → "**系统通知**"卡片 → 点"**发一条测试通知**"。

**预期**：屏幕**右下角**出现通知，**不点掉它就不会消失**。

### 5.2 如果没看到

| 检查项 | 怎么做 |
| --- | --- |
| 专注助手 / 勿扰模式 | 点任务栏右下角的通知中心图标看一眼 |
| 系统通知被关 | 设置 → 系统 → 通知 |
| 通知一闪而过 | 被系统策略降级了，可以在通知中心里找到 |
| 设置页圆点是红的 | 当前系统不支持（非 Windows） |

### 5.3 完整体验

    python scripts/test_reminder.py

**然后什么都不用做**，等最多 20 秒：

1. 屏幕**右下角**弹出系统通知
2. 浏览器开着待办页面时，页面**右下角**也出现一张卡片
3. 卡片上有"标记完成 / 稍后提醒"两个按钮

## 六、测试方法

### 测试 1：系统通知能响吗

设置页 → "发一条测试通知"。**右下角应出现通知，且不自动消失。**

### 测试 2：🎯 浏览器关掉也能提醒（本次重构的核心价值）

1. **完全关闭浏览器**
2. 运行 `python scripts/test_reminder.py` 造一条到点提醒
3. 等最多 20 秒
4. **预期：屏幕右下角照样弹出系统通知** ✅

> 这是重构前**做不到**的事。

### 测试 3：防重复

通知弹出后**不要点它**，再等 30 秒。**预期：不会再弹第二条。**

### 测试 4：页面卡片不自动消失

卡片出现后**不要点任何按钮**，等 1 分钟。
**预期**：卡片一直挂着；**刷新页面后它还在**（收件箱没被清空）。

### 测试 5：三个操作按钮

| 按钮 | 预期 |
| --- | --- |
| **标记完成** | 卡片消失；列表里该条变灰划线 |
| **稍后提醒** | 卡片消失；提醒时间变成"当前 + 10 分钟" |
| **×**（关闭） | 卡片消失；任务内容不变 |

### 测试 6：后台线程状态

访问 `http://127.0.0.1:8000/api/reminders/scheduler`：

    { "running": true, "poll_seconds": 20,
      "last_run": { "at": "2026-09-12 23:55", "fired": 0, "native_ok": 0, "error": null } }

**排查"为什么不提醒"时先看这里**：

| 现象 | 含义 |
| --- | --- |
| `running: false` | 后台线程没起来 |
| `last_run.error` 非空 | 线程里出异常了 |
| `last_run.at` 一直不变 | 线程卡住了 |
| `fired` 一直是 0 | 可能真的没有到点的提醒 |

## 七、常见问题排查

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 测试通知返回 ok=true 但没看到 | 被专注助手/勿扰模式拦了 | 见 5.2 |
| 通知一闪就没了 | `scenario="reminder"` 没生效 | 检查 `notifier.build_xml()` 生成的 XML |
| 每条通知都闪一下黑窗口 | 少了 `CREATE_NO_WINDOW` | 见 4.3 |
| 通知里中文乱码 | PowerShell 脚本没存成 `utf-8-sig` | 见 4.2 |
| 提醒完全不响 | 后台线程没起来或已死 | 看 `/api/reminders/scheduler`，见测试 6 |
| 同一条提醒反复弹 | 标记失败或 ack 没调用 | 检查 `mark_reminded`；看收件箱是否堆积 |
| 页面卡片和系统通知同时出现 | **设计如此** | 见 2.3 |
