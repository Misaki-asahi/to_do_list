## 三、✅ 上传前的必备件（均已完成）

### 3.1 `README.md` —— ✅ 已完成

**这是别人打开你仓库看到的第一样东西。** 已写好。

> **注意分工**：README 只面向**使用者**。所有开发内部信息（进度、待办、已知问题、
> Bug 记录）都放在 `PROJECT.md` 和 `docs/` 里，**不要塞进 README** ——
> 那会让第一次来的人看到一堆"还没做完"的痕迹。

一个好的 README 应该包含：

| 段落 | 内容 |
| --- | --- |
| 标题 + 一句话介绍 | 这是一个什么项目、解决什么问题 |
| 功能特性 | 用列表列出主要功能（带截图效果最好） |
| 快速开始 | 环境要求（Python 3.10+）、安装依赖、启动命令 —— **三步以内** |
| 使用说明 | 待办 / 日历 / 提醒 / 设置 四个页面各能做什么 |
| 项目结构 | 用树形图说明每个目录干什么 |
| 技术栈 | Python / FastAPI / SQLite / 原生前端 |
| 常见问题 | 把你踩过的坑（端口占用、通知不显示等）放进去 |
| 开发文档 | 指向 `docs/` 目录 |
| 许可协议 | 指向 LICENSE |

### 3.2 `LICENSE` —— ✅ 已完成

**没有 LICENSE 的仓库，默认是"保留所有权利"** —— 别人**在法律上不能使用、修改、分发**你的代码。
这意味着：把它公开到 GitHub，别人也不能合法地用它。

建议用 **MIT 协议**（最宽松、最常用，适合学习项目）：
- 别人可以自由使用、修改、商用
- 但必须保留你的版权声明
- 你自己不承担任何责任

`LICENSE` 第 3 行的版权人已确定为：

    Copyright (c) 2026 Misaki

> **为什么要专门记一笔？**
> 最初这里写的是 `Copyright (c) 2026 <Misaki>` —— **尖括号是占位符标记**。
> MIT 协议要求版权声明指向**一个具体主体**，`<...>` 这种写法在正式项目里
> 看起来像"还没填完的模板"，别人会不确定版权到底归谁。
> **发布前必须去掉尖括号** —— 这类细小但正式的地方，正是开源项目的体面所在。

## 四、📋 建议的上传步骤

```
1. ✅ README.md 和 LICENSE 已就绪（LICENSE 的版权人待填，见 3.2）

2. 在 GitHub 上新建一个空仓库（不要勾选 "Add README"）

3. 本地关联并推送：
     git branch -m main                        # master -> main（跟上 GitHub 的默认分支名）
     git add -A
     git commit -m "初始提交：离线待办清单 v0.2.0"
     git remote add origin https://github.com/你的用户名/to_do_list.git
     git push -u origin main
```

> ⚠️ **推送前再确认一次 `data/` 没有被推上去。**
> 可以执行 `git ls-files data/` 检查，正确的结果应该**只有 `data/.gitkeep` 一行**。
>
> ⚠️ **不要写成 `git ls-files | findstr data`** —— `findstr` 默认是**子串匹配**，
> 它会把 `app/database.py` 也列出来（因为「**data**base」里含有「data」），
> 让人误以为有敏感文件被跟踪，白白紧张一场。
> 要匹配**路径开头**，得用锚定写法：`git ls-files | findstr /R "^data/"`。
