## 一、设计思路

### 1.1 为什么这一步排在重构和测试之前

第三阶段要做的第一件事，本来应该是"代码重构"。但我把它换成了异常处理和日志，理由很直接：

> **程序已经打包成安装包发布出去了。**
> 而安装版**没有黑色命令行窗口** —— 一旦出错：
>
> | | 源码运行 | 安装版 |
> | --- | --- | --- |
> | 报错显示在哪 | 黑窗口里看得见 | **哪儿都看不见** |
> | 用户能做什么 | 把报错复制给你 | 只能说"它坏了" |
> | 你能做什么 | 照着堆栈查 | **完全无从下手** |

**所以对一个要发布给别人用的程序来说，日志不是"锦上添花"，是"基本配置"。**

### 1.2 三个必须堵住的异常入口

异常会从三个地方漏出来，一个都不能少：

| # | 入口 | 漏掉会怎样 | 拦截方式 |
| --- | --- | --- | --- |
| ① | **Web 请求处理中** | 用户看到一句 `Internal Server Error`，日志里什么都没有 | FastAPI 全局异常处理器 |
| ② | **后台线程里** | **线程安静地死掉**，程序表面正常，只是那个功能再也不工作了 | `threading.excepthook` |
| ③ | **主线程里** | 程序崩溃退出，没有任何记录 | `sys.excepthook` |

> ⓘ 第 ② 种我们**已经踩过**了 —— 见 BUG-012（配置常量名写错，后台提醒线程静默死亡）。
> 那次的教训就是"后台线程抛异常不会被任何人看到"。这次从根上堵住。

### 1.3 顺带做一次重构：删掉 15 处重复的 try/except

加了全局异常处理器之后，路由函数里的这种代码就**完全多余**了：

```python
# 以前：每个接口都要抄一遍
try:
    task = task_service.create_task(payload)
except task_service.BusinessError as exc:
    raise HTTPException(status_code=400, detail=str(exc))
return task.to_dict()

# 现在：一行
return task_service.create_task(payload).to_dict()
```

**这不只是少写几行代码的问题。** 更关键的是：

- 每加一个接口就要再抄一遍，**漏写一处，那个异常就会变成 500**；
- 抄的时候状态码容易写错（400 写成 404）；
- 错误响应的格式在十几个地方各自拼装，**前端要处理好几种结构**。

### 1.4 统一的错误响应格式

```json
{ "detail": "提醒时间不能早于当前时间（现在是 2026-09-13 12:52）",
  "type": "business_error" }
```

| 字段 | 作用 |
| --- | --- |
| `detail` | **给人看的**，可以直接显示在界面上 |
| `type` | **给程序看的**，前端可以据此做不同处理（比如 404 时自动刷新列表）|

四种错误，一个格式：

| 状态码 | type | 什么情况 | 例子 |
| --- | --- | --- | --- |
| **400** | `business_error` | 业务规则不通过 | 提醒时间填成了过去 |
| **404** | `not_found` | 要操作的东西不存在 | 修改一条已被删掉的待办 |
| **422** | `validation_error` | 提交的数据格式不对 | 标题为空、优先级越界 |
| **500** | `internal_error` | **程序有 Bug** | 任何没预料到的异常 |

### 2.2 日志系统（`app/core/logging_setup.py`）

```python
def setup(level=None) -> logging.Logger:
    """初始化日志系统（重复调用只会生效一次）。"""
    # 1) 文件处理器：按天滚动，保留 14 天
    file_handler = logging.handlers.TimedRotatingFileHandler(
        str(config.LOG_FILE), when="midnight",
        backupCount=config.LOG_KEEP_DAYS, encoding="utf-8", delay=True)

    # 2) 控制台处理器（打包版 stdout 是 None，要先判断）
    if config.LOG_TO_CONSOLE and sys.stdout is not None:
        root.addHandler(logging.StreamHandler(sys.stdout))

    # 3) 把"话太多"的库调安静
    for name in ("httpx", "httpcore", "urllib3", "asyncio"):
        logging.getLogger(name).setLevel(logging.WARNING)
    logging.getLogger("uvicorn.access").setLevel(logging.WARNING)
```

### 2.3 全局异常处理器（`app/main.py`）

```python
@app.exception_handler(app_errors.AppError)
async def handle_app_error(request: Request, exc: app_errors.AppError):
    """处理所有自定义异常（业务规则 / 找不到 / 取值不合法）。"""
    logging_setup.get_logger("api").warning(
        "%s %s -> %s（%s）", request.method, request.url.path,
        exc.status_code, exc.message)
    return JSONResponse(status_code=exc.status_code,
                        content={"detail": exc.message, "type": exc.error_type})


@app.exception_handler(Exception)
async def handle_unexpected(request: Request, exc: Exception):
    """兜底：任何没被上面接住的异常。"""
    logger.exception("未处理的异常 %s %s", request.method, request.url.path)
    return JSONResponse(status_code=500, content={
        "detail": "服务器内部错误。详细信息已记录到日志文件，可以在设置页点「查看日志」。",
        "type": "internal_error"})
```

## 三、关键代码逐行解释

### 3.1 `TimedRotatingFileHandler` 的 `delay=True` 有什么用

```python
TimedRotatingFileHandler(..., delay=True)
```

默认情况下，创建 handler 的**那一刻**就会把日志文件建出来。
加 `delay=True` 表示"**真的写第一条日志时再创建**"。

好处：只跑一下 `--help` 之类的操作，不会凭空多出一个空日志文件。

### 3.2 为什么打包版要判断 `sys.stdout is not None`

```python
if config.LOG_TO_CONSOLE and sys.stdout is not None:
    root.addHandler(logging.StreamHandler(sys.stdout))
```

打包成 `--noconsole` 之后，`sys.stdout` 是 `None`。
这时候给他加 `StreamHandler`，**第一条日志就会崩** —— 而且是在"记录错误"的时候崩，特别讽刺。

### 3.3 `threading.excepthook`：后台线程的救命绳

```python
def _thread_excepthook(args):
    logger.critical(
        "后台线程 %s 出现未捕获的异常：\n%s",
        args.thread.name if args.thread else "?",
        "".join(traceback.format_exception(
            args.exc_type, args.exc_value, args.exc_traceback)))

threading.excepthook = _thread_excepthook
```

`args` 是 `threading.ExceptHookArgs`，里面有四个东西：

| 属性 | 是什么 |
| --- | --- |
| `exc_type` | 异常类型（如 `RuntimeError`）|
| `exc_value` | 异常对象 |
| `exc_traceback` | 堆栈信息 |
| `thread` | **哪个线程出的事**（排查的关键）|

> **这一段的价值极高。** 在它之前，后台提醒线程如果抛异常，
> 结果就是"提醒莫名其妙不响了"，而且**一点线索都没有**（BUG-012 就是这种情况）。

### 3.4 中间件里为什么【不能】记异常日志

```python
@app.middleware("http")
async def log_requests(request: Request, call_next):
    try:
        response = await call_next(request)
    except Exception:
        # 【注意】这里不要记日志 —— 异常会继续往上冒，
        # 最终由全局异常处理器负责记录。
        raise
```

我第一版在这里写了 `logger.exception(...)`，结果**同一个异常在日志里出现了两遍**，
每一遍还带着完整的堆栈 —— 日志立刻膨胀一倍。

> **原则：一个事件，只在一处记录。**
> 这个原则在这次的改动里用到了三次：中间件、uvicorn 的访问日志、还有后面会讲的备份。

### 3.5 为什么只记 `/api/` 请求和错误响应

```python
if path.startswith("/api/") or response.status_code >= 400:
    ...记录...
```

打开一个页面会带出十几个静态资源请求（CSS、7 个 JS）。
如果全都记下来，**日志一天能涨几万行**，真正的错误反而被淹没在噪音里。

所以策略是：**业务接口全记，静态资源只在出错时记。**

### 3.6 500 错误为什么不能把堆栈给用户看

```python
# 对用户说的：
"服务器内部错误。详细信息已记录到日志文件。"

# 记进日志的：
logger.exception(...)   # 完整堆栈
```

异常堆栈里可能包含：**绝对文件路径、数据库结构、甚至 SQL 语句**。
把这些原样返回给浏览器，等于给攻击者递地图。

**正确做法：对用户说人话 + 日志里存完整现场。** 两边各取所需。

### 3.7 请求日志中间件为什么用 `time.perf_counter()`

```python
start = time.perf_counter()
...
cost = (time.perf_counter() - start) * 1000
```

| 函数 | 用途 |
| --- | --- |
| `time.time()` | 挂钟时间，**可能被系统对时调整**（NTP），算出负数耗时 |
| **`time.perf_counter()`** | 单调递增的高精度计数器，**专门用来测耗时** |

测时间差一律用 `perf_counter()`。这是个小细节，但用错了会在日志里看到 `-3 ms` 这种怪东西。

### 3.8 `TODO_DATA_DIR`：一次到位的测试隔离

```python
DATA_DIR = Path(os.getenv("TODO_DATA_DIR", str(BASE_DIR / "data")))
```

原来只有 `TODO_DB` 一个覆盖点，只隔离了数据库文件。
但测试跑起来还会往 `data/backups/` 写备份、往 `data/logs/` 写日志 —— **这些仍然会污染真实目录**。

加上 `TODO_DATA_DIR`（覆盖整个数据根目录）之后，
`_isolation.use_isolated_db("xxx")` 一行就能把**数据库、备份、日志全部隔离**到临时目录。

## 四、如何运行（怎么查看日志）

### 4.1 在界面上看（推荐给使用者）

打开**设置页** → 找到「**日志**」卡片：

| 按钮 | 作用 |
| --- | --- |
| **查看最近日志** | 在页面下方显示最后 150 行（黑底等宽字体，自动滚到最新）|
| **打开日志目录** | 用资源管理器打开 `data/logs\` |
| **复制日志内容** | 一键复制到剪贴板，直接发给别人看 |

### 4.2 直接看文件（推荐给开发）

```
data/logs/app.log              当前日志
data/logs/app.log.2026-09-12   前一天的历史日志（自动生成）
```

日志格式：

```
2026-09-13 12:52:18 | INFO    | app        | 离线待办清单 v0.1.0 启动
2026-09-13 12:52:18 | INFO    | access     | POST /api/tasks -> 201 （10 ms）
2026-09-13 12:52:18 | WARNING | api        | POST /api/tasks -> 400（提醒时间不能早于当前时间）
2026-09-13 12:52:18 | ERROR   | app        | 未处理的异常 GET /api/tasks
2026-09-13 12:52:18 | CRITICAL| uncaught   | 后台线程 reminder-scheduler 出现未捕获的异常：
```

| 级别 | 什么时候用 |
| --- | --- |
| INFO | 正常的关键事件（启动、请求）|
| WARNING | 用户操作有问题（400 / 404）—— 不是程序的错，不用告警 |
| ERROR | 没预料到的异常（500）|
| **CRITICAL** | **程序层面可能已经出问题了**（线程死了、主线程崩了）|

## 六、常见问题排查

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 设置页的「日志」卡片是空的 | `/api/settings` 没返回 `logs` 字段 | 确认 `setting_service.system_stats()` 里有那一行 |
| 日志文件**没有生成** | 数据目录不可写 | 看程序启动时有没有打印"无法创建日志文件"警告 |
| 日志**涨得太快** | 某个库在刷屏 | 在 `logging_setup.setup()` 里把那个库设成 WARNING |
| 同一条请求在日志里出现两次 | 中间件和 uvicorn 访问日志都在记 | 确认启动时传了 `access_log=False` |
| 500 之后接口**一直 500** | 服务真的坏了（不是异常本身）| 看日志里最后那个堆栈 |
| 想看更详细的日志 | 默认是 INFO 级 | 把 `config.LOG_LEVEL` 改成 `"DEBUG"` |
