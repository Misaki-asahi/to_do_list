## 一、设计思路

### 1.1 为什么现在才写测试

阶段二做功能时，验证手段一直是"手动跑一遍 `check_repo.py`"。
那套东西能用，但有两个问题：

| 问题 | 后果 |
| --- | --- |
| 只能测"正常路径" | 边界情况（空值、非法输入、超长字符串）测不到 |
| 改代码后要靠人记得重跑 | 忘了跑 = 没测 |

而阶段三加进来的东西（回收站、异常处理、安装器）**恰恰全是边界情况密集的地方**。
所以测试不是"工程化流程里该有的一步"，而是**这个阶段最需要的安全网**。

### 1.2 测试怎么分层

测试按"离用户多近"分三层，越靠下的越快、越稳、越多：

```
        ┌─────────────────────────────┐
  少 →  │  接口测试（HTTP 层）         │  34 + 23 + 14 + 10 + 20 = 101 项
        │  真的发请求，检查状态码和 JSON │
        ├─────────────────────────────┤
        │  服务层测试（业务规则）        │  31 项
        │  标题能不能空、时间能不能是过去 │
        ├─────────────────────────────┤
  多 →  │  仓库层 / 纯函数测试          │  43 + 28 + 26 + 30 = 127 项
        │  不进 HTTP，直接调函数，最快    │
        └─────────────────────────────┘
```

**为什么这么分？** 因为越往下的测试**越快、越好定位问题**。
接口测试挂了，可能是路由、服务、数据库任何一层的问题；
而纯函数测试挂了，问题一定在那个函数里。

**但接口测试也不能省** —— 有些问题只有走完整个 HTTP 流程才会暴露
（比如路由顺序、状态码、JSON 字段名）。

### 1.3 测试必须有隔离（这条最要紧）

**这是用一次真实事故换来的**（见 BUG-011：临时脚本误删了用户的全部待办）。

所以测试启动的第一件事，是**在导入 app 之前**把数据目录整个切走：

```python
# tests/conftest.py —— 必须在 import app 之前
TEST_DATA_DIR = PROJECT_ROOT / "data" / "test" / "pytest"
os.environ["TODO_DATA_DIR"] = str(TEST_DATA_DIR)
os.environ["TODO_DB"] = str(TEST_DATA_DIR / "pytest.db")

# 现在才可以安全地导入 app
from app.main import app
```

**为什么顺序不能反？** 因为 `app.config` 在**第一次被导入时**就会读环境变量定下路径，
导入之后再设就来不及了。

## 三、关键代码逐行解释

### 3.1 为什么必须"先设环境变量、再导入 app"

```python
os.environ["TODO_DATA_DIR"] = str(TEST_DATA_DIR)
from app.main import app          # ← 这一行执行时，路径就定死了
```

`app/config.py` 里是这样的：

```python
DATA_DIR = Path(os.getenv("TODO_DATA_DIR", str(BASE_DIR / "data")))
```

**模块级代码只在第一次导入时执行一次。** 所以：

- 导入**之前**设环境变量 → 生效
- 导入**之后**再设 → 那个 `DATA_DIR` 早就是旧值了，改环境变量没用

这个坑本项目真的踩过（BUG-009：容错代码写了但永远不执行），
本质是**"在错误的时间点做正确的事，等于没做"**。

### 3.2 为什么每个测试前后都要清库

```python
@pytest.fixture(autouse=True)
def clean_db(client):
    _reset_database()
    yield
    _reset_database()
```

**测试之间必须互相独立。** 如果上一个测试留下的数据影响下一个测试，
就会出现**"单独跑通过、一起跑失败"**这种最让人头疼的问题。

本项目就真的遇到过：测设置表时前面留下的 `theme` 键，让"全部设置"的断言挂了 ——
**测试自己把测试搞挂了。**

> **`autouse=True` 的含义**：不用在每个测试函数里写参数，自动生效。
> 少写一遍，就少一次"忘了写"的机会。

### 3.3 为什么要把系统通知换掉

```python
notifier.show = lambda *args, **kwargs: {"ok": True, "message": "测试环境：已跳过"}
```

**因为测试真的会弹通知。** 跑一遍测试就弹几十个窗口，而且这些通知
**不点不掉** —— 既不礼貌，也没法自动化。

**注意这不影响测"该不该弹"** —— 我们要验证的是**逻辑**（这条任务到点了吗），
不是**外观**（弹出来长什么样）。把"显示"换成空实现，逻辑照样能测。

### 3.4 重构：为什么把 try/except 从路由里拿掉

**重构前**，每个路由都长这样：

```python
@router.post("")
def create_task(payload: TaskCreate):
    try:
        return task_service.create_task(payload).to_dict()
    except BusinessError as exc:
        raise HTTPException(status_code=400, detail=str(exc))
```

**问题**：同一个 `try/except` 在十几个路由里重复；而且**异常 → HTTP 状态码**这个映射
散落在各处，想改一处得改十几处。

**重构后**，路由只剩一行：

```python
@router.post("")
def create_task(payload: TaskCreate):
    return task_service.create_task(payload).to_dict()
```

异常统一交给 `app/main.py` 的全局处理器翻译：

```python
@app.exception_handler(BusinessError)
async def _business_error(request, exc):
    return JSONResponse(status_code=400, content={...})
```

**收益**：
- 路由函数只剩"调用服务层"这一件事，**一眼看得懂**
- 状态码映射**只有一处**，改一次全生效
- 新增路由时**不可能忘记**包 try/except

### 3.5 重构怎么保证没改坏

**重构最大的风险是"改完之后行为变了，但没人发现"。**

所以做法是固定的三步：

1. **重构前先跑一遍测试**，记下结果（259 通过）
2. **重构代码**
3. **再跑一遍测试**，结果必须一模一样（还是 259 通过）

**测试就是重构的安全网。** 没有它，重构只能靠"我觉得没问题" ——
而"我觉得"从来不靠谱。

> 这也是**为什么先写测试、再做重构**的顺序不能反：
> 先重构的话，就没有东西帮你确认"行为没变"了。

## 四、如何运行

> **⚠️ 所有命令都要在 `win11` 这个文件夹里执行**
> 也就是你放 `to_do_list` 的那个目录下面的 `win11`（例如 `<你的项目目录>\win11`）

### 4.1 跑全部测试（最常用）

```powershell
python -m pytest tests/
```

预期结果：**259 项全部通过**。

### 4.2 看每个测试的名字

```powershell
python -m pytest tests/ -v
```

加了 `-v` 会把每个用例的名字和结果都列出来，出错时一眼看到是哪个。

### 4.3 只跑某个文件

```powershell
python -m pytest tests/test_trash.py -v
```

### 4.4 按关键字筛选

```powershell
python -m pytest tests/ -k "remind"      # 只跑名字里含 remind 的
python -m pytest tests/ -k "migrate"     # 只跑数据库迁移相关的
```

### 4.5 第一次失败就停下来

```powershell
python -m pytest tests/ -x
```

### 4.6 配置在哪

`pytest.ini`：

```ini
[pytest]
testpaths = tests
addopts = -q --tb=short -p no:cacheprovider --strict-markers
```

| 参数 | 作用 |
| --- | --- |
| `testpaths = tests` | 不写路径时默认只找 `tests/` |
| `-q` | 简洁输出（只打点，不逐个列名字） |
| `--tb=short` | 失败时只显示关键堆栈（默认太长） |
| `-p no:cacheprovider` | **不生成 `.pytest_cache` 目录**（符合项目自包含原则） |
| `--strict-markers` | 用错 marker 直接报错，避免打错字静默失效 |

## 六、Bug 排查

### 6.1 `no such table: tasks`

**原因**：某个测试没有依赖 `client` fixture。

表是在**应用启动钩子**（lifespan）里创建的，而 `client` 负责触发它。
纯逻辑测试如果不依赖 `client`，跑起来时表还没建好。

**修法**：给 `clean_db` 加上 `client` 依赖（本项目就是这么修的）。

### 6.2 "单独跑通过，一起跑失败"

**原因**：测试之间**互相污染** —— 上一个测试留下的数据影响了下一个。

**排查**：
```powershell
python -m pytest tests/test_xxx.py -v      # 单独跑，通过
python -m pytest tests/ -v                 # 一起跑，失败 -> 确认是污染
```

**修法**：检查 `clean_db` 有没有覆盖到那张表。

### 6.3 测试真的弹出系统通知了

**原因**：`disable_native_notifications` fixture 没生效。

**检查**：它是不是 `scope="session"` 且 `autouse=True`。
如果不是自动生效的，某个测试自己调了真的 `notifier.show`。

### 6.4 改完代码测试全红

**先别慌，按顺序看：**

1. **是不是所有测试都红了？** → 多半是导入就失败（语法错误、缺少依赖）
2. **红的是同一类测试吗？** → 说明某个公共的东西坏了（比如 config 常量改名）
3. **只有一两个红？** → 大概率是这一处真的改坏了行为

> ⚠️ **一条重要的心态**：测试变红**不代表你写错了** ——
> 它只代表"现在的行为和你之前承诺的不一样了"。
> 有时候是代码错了，**有时候是测试该更新了**（需求变了）。
> 关键是要**想清楚是哪一种**，而不是直接改测试让它变绿。

### 6.5 测试跑得很慢

本项目 259 项大约十几秒。如果明显变慢：

| 原因 | 检查 |
| --- | --- |
| 某个测试在 `time.sleep()` | 搜 `sleep` |
| 每次都在重建整个数据库 | `clean_db` 用的是 `reset_all` 而不是删文件重建 |
| 有测试真的在发网络请求 | 搜 `requests` / `urllib`（本项目测试只用 `TestClient`，不走真实网络） |
