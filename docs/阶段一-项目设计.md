## 1. 项目目标

### 1.1 一句话定位

做一个**本地优先（Local-First）的桌面待办与提醒工具**：断网也能用，数据只存在你自己电脑上，
但架构上预留了"以后发布到 GitHub、部署成公网网址给别人用"的能力。

### 1.2 目标用户与使用场景

- 主要用户：你自己（学生 / 开发学习者）。
- 次要用户：以后从 GitHub 下载你项目的人（陌生人，需要开箱即用）。
- 典型场景：
  1. 早上打开电脑 —— 程序自动启动 —— 看到今天要做的三件事。
  2. 在月历上点"下周三"，直接建一条"交作业"的任务，提醒设为当天 08:30。
  3. 到点了，屏幕上弹出提醒窗口 + 提示音，即使浏览器标签页在后台。
  4. 做完了，勾选完成，切到"已完成"标签回看。
  5. 换台电脑，把导出的 JSON 备份文件导入，数据回来了。

### 1.3 需求 → 技术方案对照表

你提的 9 条要求，逐条落到具体技术上，避免"想做但不知道怎么实现"：

| # | 你的要求 | 落地技术方案 | 属于哪个模块 |
| --- | --- | --- | --- |
| 1 | 离线可修改内容并设提醒 | 后端跑在 `127.0.0.1`，完全不依赖外网；提醒由本地调度器触发 | M5 提醒服务 |

## 2. 技术选型与理由

| 层 | 选型 | 为什么选它（而不是别的） |
| --- | --- | --- |
| 后端框架 | **FastAPI** | 自带交互式接口文档（`/docs`），写起来短，用 Python 类型做校验；以后部署到公网也扛得住。Flask 更老更简单，但需要自己写校验。 |
| 数据校验 | **Pydantic v2** | FastAPI 自带，一个类就完成"字段类型 + 必填 + 长度"校验。 |
| 数据库 | **SQLite** | 单文件、零安装、离线可用；Python 标准库自带驱动。数据量到百万级都够用。 |
| ORM | **SQLAlchemy 2.x** | 让"以后换 Postgres"只需要改一行连接字符串；避免手写 SQL 拼接出错。 |
| 前端 | **原生 HTML + CSS + JavaScript** | 你明确说"要学前端"：不引入 React/Vue，先把 DOM、事件、fetch 这些基本功练扎实。代码零构建，双击即运行。 |
| 提醒调度 | **前端轮询 + 接口内扫描**（不需要后台线程） | 见下方修订说明：后台线程会导致"提醒被消费却没人看见"，反而会丢提醒。 |
| 开机自启 | **Windows 启动文件夹快捷方式** | 不需要管理员权限，用户自己在"启动"文件夹里能看到、能删掉，透明可控。 |
| 打包（后期） | **PyInstaller** 或 **Docker** | 本地发 exe 给别人双击运行；公网部署用 Docker。 |

> 备选方案：如果你更想做成"传统桌面窗口程序"（双击出现一个窗口，而不是浏览器），
> 可以用 **PyWebview**（Python 开一个原生窗口装网页）或 **Tkinter**。
> 这属于第 9 章的确认点之一，我推荐先做浏览器版，因为它天然可以变成"公网网址"。

### 3.2 每个模块的职责

#### M1 配置模块（config.py）
- **负责**：集中管理所有"常量"和"路径"——数据库文件位置、服务端口、默认提醒提前量、日志级别。
- **不负责**：任何业务逻辑。
- **为什么单独拿出来**：以后要发布给别人用，别人电脑上的路径不一样，改一个文件就够。

#### M2 数据模型模块（models.py + schemas.py）
- **models.py**：定义数据库表长什么样（SQLAlchemy 类）。
- **schemas.py**：定义 API 收发的 JSON 长什么样（Pydantic 类）。
- **为什么要分成两个**：数据库字段和接口字段经常不一样。比如数据库有 `id` 和 `created_at`，但"新建任务"时用户不需要填这两个。分开写，接口就不会被内部字段污染。

#### M3 数据访问层（repositories/）
- **负责**：唯一能碰数据库的地方。提供 `create / get / list / update / delete` 等方法。
- **不负责**：判断"这条任务该不该提醒"这类业务规则。
- **好处**：以后想换数据库，只改这一层。

#### M4 任务服务（services/task_service.py）
- **负责**：待办的增删改查业务规则。例如：
  - 标题不能为空；
  - 标记完成时自动记录 `completed_at`；
  - 修改截止时间时，如果提醒时间晚于截止时间，自动修正提醒时间。
- **对应你的需求 4（增查改删 + 状态筛选）**。

#### M5 提醒服务（services/reminder_service.py + routers/reminders.py）
- **负责**：
  1. 前端每 20 秒调用一次接口，接口内扫描："有没有 `remind_at <= 现在` 且还没提醒过的任务？"
  2. 找到就标记 `reminded_at = 现在`（**幂等**，保证只弹一次）。
  3. 前端轮询到"待弹提醒"后，弹出窗口。
- **关键设计**：提醒状态记在**数据库**里而不是内存里 —— 程序重启后不会把旧提醒再弹一遍，也不会漏掉关机期间到点的提醒。

#### M6 日历模块（前端 static/js/calendar.js 为主）
- **负责**：月历视图渲染、点击某天快速建任务。
- **决策变更（2A）**：**不做 `.ics` 导入导出**。因此后端不需要单独的日历服务，
  月历数据直接用已有的「按日期范围查询任务」接口就能拿到，少写一层代码。
- **对应你的需求 8**。

#### M7 系统集成模块（core/autostart.py + routers/settings.py）
- **负责**：查询/开启/关闭开机自启（读写 Windows 启动文件夹），返回当前状态给设置页。
- **对应你的需求 7**。专门界面 = 设置页 `/settings`。

#### M8 部署与发布能力（scripts/ + README.md）
- **负责**：一键启动脚本、依赖清单、Git 忽略规则、给别人看的说明书。
- **对应你的需求 9**。

## 4. 程序整体流程

### 4.1 启动流程

```
双击 start.bat
   │
   ├─ 1. 检查 Python 环境与依赖（少了就提示 pip install -r requirements.txt）
   ├─ 2. 读取 config.py 配置
   ├─ 3. 连接 SQLite；文件不存在则自动建库建表（首次运行自动完成）
   ├─ 4. （提醒不需要后台线程 —— 由前端轮询驱动，见 4.3 节修订说明）
   ├─ 5. 启动 FastAPI 服务，监听 127.0.0.1:8000
   └─ 6. 自动打开浏览器访问 http://127.0.0.1:8000
```

### 4.2 一次"添加待办"的完整数据流（最重要的心智模型）

```
用户在前端填标题/日期/提醒时间
        │  点击"保存"
        ▼
①前端 JS：fetch POST /api/tasks  {title, due_at, remind_at}
        ▼
②路由层 routers/tasks.py：接住请求，交给 Pydantic 校验（字段类型对不对）
        ▼
③服务层 task_service.py：执行业务规则（标题非空、提醒时间不能早于现在等）
        ▼
④数据层 task_repository.py：INSERT 一行，返回带 id 的新任务对象
        ▼
⑤原路返回 JSON 给前端
        ▼
⑥前端 JS：把新任务插入页面列表，弹出"已添加"提示
```

> **记住这条链路**：前端 → 路由 → 服务 → 数据 → 数据库 → 原路返回。
> 你以后写任何功能都是这条路，只是中间的处理不同。这就是"结构清晰"的意义。

### 4.3 提醒触发流程（本项目的核心难点）

```
【前端】每 20 秒调用一次接口：
   GET /api/reminders/due

【接口内部】这一次调用同时完成"扫描 + 消费"：
   ① 查询 remind_at <= 当前时间  AND  reminded_at IS NULL
        AND status = 'todo'  AND  remind_enabled = 1
   ② 若有结果 → 立刻把 reminded_at 写成当前时间（消费掉，防止重复弹）
   ③ 把结果返回给前端

【前端】拿到结果后：
   ├─ 页面内弹出醒目模态框（带"完成 / 稍后提醒 / 知道了"按钮）
   ├─ 调用浏览器 Notification API（系统级通知，切到别的软件也能看到）
   └─ 播放提示音（Web Audio 现场合成，不需要音频文件）
```

#### ⚠️ 修订说明：为什么最终【没有】用后台线程

原设计是"后端起一个线程每 20 秒扫描并标记"。实现时重新推演，发现它会**丢提醒**：

| 方案 | 浏览器没开时会怎样 |
| --- | --- |
| 后端线程扫描并标记 | 时间到了 → 线程把 `reminded_at` 写上 → **但没人看见** → 你打开浏览器时它已经不弹了 → **提醒永久丢失** ❌ |
| **前端轮询，接口内扫描+标记** | 没人轮询 → 提醒**保持未标记状态** → 重新打开时补弹 ✅ |

**核心洞察：`reminded_at` 应该在"用户真的看到"时才写入，而不是"时间到了"就写入。**

这样"不漏提醒"是**自动成立**的——因为没被看到的提醒永远不会被消费掉。
顺带还少了一个线程、少了一类并发 Bug。

- **"扫描"和"消费"必须放在同一个函数里**（原子操作）：如果分成"先查询、前端显示完再回来标记"，
  中间那段时间下一次轮询会查到同样的任务，导致同一条提醒被弹好几次。
- 代价：浏览器标签页切到后台时，定时器会被浏览器降频（约 1 分钟一次）。
  前端额外监听了 `visibilitychange`，**标签页切回来的一瞬间立刻检查一次**，所以实际体验没有等待感。
- 进阶（第三阶段可选）：把轮询升级成 **SSE / WebSocket** 推送，彻底解决后台降频问题。
  已记入 `docs/待优化与已知问题.md`。

### 4.4 开机自启流程

```
用户在设置页打开"开机自启"开关
        ▼
POST /api/settings/autostart {enabled: true}
        ▼
core/autostart.py：
   - 找到 Windows 启动文件夹
     %APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup
   - 在里面创建快捷方式 → 指向 start.bat（静默启动版）
   - 关闭时：删除该快捷方式
        ▼
设置页显示实时状态："已开启 ✅（快捷方式位置：…）"
```

> 下次开机时，Windows 自动执行 start.bat → 服务在后台起来 → 你打开浏览器就是待办列表。
> **注意**：开机自启版本不自动弹浏览器窗口（避免每天开机被浏览器打断），改为常驻托盘/后台，你手动点图标即可。

### 5.1 生成文件地图（哪些是"自动产生"的，能不能删）

**项目自包含原则：所有运行产生的文件，一律放在 `to_do_list` 文件夹内。**

| --- | --- | --- | --- |

| `backups/*.db` | `data/backups/` | 自动备份 | ✅ 可删，但删了就没备份 |

| `exports/*.json` | `data/exports/` | 手动导出 | ✅ 可删（先确认已备份） |
| `__pycache__/` | 各代码目录下 | Python 自动生成 | ✅ 随时可删（用 `clean.bat`） |
| `.pytest_cache/` | 项目根 | 测试框架 | ✅ 随时可删 |

> 💡 一条命令清理全部安全项：**双击 `clean.bat`**，或运行 `python scripts/clean.py`。
> 它会明确告诉你**清理了什么、释放了多少空间**，并且**绝不动你的 `todo.db`**。

**结构设计的三个原则（你可以用来判断自己写的文件该放哪）**
1. **按"角色"分文件夹，不按"页面"分**。所以是 routers / services / repositories，而不是 add_page / list_page。
2. **依赖只能从上往下**。路由可以调服务，服务可以调数据层；**数据层绝不能反过来调服务**。
3. **越靠下的层，越不知道上面发生了什么**。数据库层完全不知道有"网页"这回事。

## 6. 数据该如何保存

### 6.1 为什么用 SQLite 而不是 JSON 文件

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| JSON 文件 | 简单、肉眼可读 | 并发写会损坏、查询要全量读进内存、无事务 | ❌ 不适合 |
| CSV | 能用 Excel 打开 | 结构弱、无法存嵌套、无事务 | ❌ 不适合 |
| **SQLite** | 单文件、有事务、支持复杂查询、Python 自带 | 无（对单人使用来说） | ✅ **选它** |
| MySQL/Postgres | 支持多用户并发 | 要安装服务、要联网配置 | ⏳ 以后部署公网时再换 |

**SQLite 的定位**：一个文件 = 一个数据库。你把它复制走，就是完整备份。你在 Git 里忽略它，就不会把自己的隐私数据传到 GitHub。

### 6.2 核心表结构设计

#### 表 1：`tasks`（待办事项）

| 字段名 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | INTEGER | 主键、自增 | 唯一编号 |
| title | TEXT | 非空、≤200 字 | 待办标题 |
| description | TEXT | 可空 | 详细描述 |
| status | TEXT | 默认 `'todo'` | 取值：`todo`（未完成）/ `done`（已完成） |
| priority | INTEGER | 默认 1 | 0=低、1=中、2=高 |
| due_at | TEXT | 可空 | **截止时间**，精确到分，格式 `YYYY-MM-DD HH:MM` |
| remind_at | TEXT | 可空 | **提醒时间**，精确到分，格式 `YYYY-MM-DD HH:MM` |
| remind_enabled | INTEGER | 默认 0 | 是否开启提醒（0/1） |
| reminded_at | TEXT | 可空 | **已提醒时刻**；非空 = 已弹过窗，用于防重复 |
| category | TEXT | 可空 | 分类标签（如"学习""生活"），为筛选预留 |
| created_at | TEXT | 非空 | 创建时间，自动生成 |
| updated_at | TEXT | 非空 | 最后修改时间，每次更新自动刷新 |
| completed_at | TEXT | 可空 | 完成时刻，用于统计"本周完成了几件事" |
| user_id | INTEGER | 默认 1 | **多用户预留**：现在恒为 1，以后加登录直接启用 |

**索引设计**（让查询变快）：
- `idx_tasks_status`：按完成状态筛选时走索引。
- `idx_tasks_remind`：提醒扫描每 20 秒查一次，必须有索引，否则数据一多就卡。

#### 表 2：`settings`（设置项）

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| key | TEXT | 设置名，如 `autostart_enabled`、`theme`、`remind_sound` |
| value | TEXT | 设置值（统一存字符串，读取时转换） |
| updated_at | TEXT | 最后修改时间 |

> 用"键值对表"而不是给每个设置建一列：以后加新设置**不用改表结构**，扩展性最好。

### 6.3 时间存储规范（最容易出 Bug 的地方，单独讲）

**决策 3B：采用「纯本地时间字符串」方案。**

- **存储格式**：`YYYY-MM-DD HH:MM`，例如 `2026-02-20 08:30`。
- **为什么选它**：肉眼直接可读，导出的 JSON 一眼能看懂，排序规则天然正确
  （因为"年月日时分"从大到小排列，字符串排序 = 时间排序），调试最省心。
- **代价（可接受）**：如果将来真的上线公网、且用户在别的时区，显示时间会按服务器时区走。
  本项目定位是"本机离线使用 + 少数几个人共用"，这个代价可以接受。
- **统一入口**：所有"字符串 ↔ 时间"的转换只写在 `core/timeutil.py` 里，别处一律调用它。
  这是将来要改成时区方案时，唯一需要动的地方。
- **精确度**：界面上只让用户选到"分"（`HH:MM`），秒一律填 `00`。

### 6.4 数据安全与备份

- **自动备份**：程序启动时，若 `data/todo.db` 存在，复制一份到 `data/backups/todo_YYYYMMDD.db`，只保留最近 7 份。
- **手动导出**：设置页提供"导出全部数据为 JSON"，方便迁移。
- **软删除（可选）**：删除的任务先标记 `deleted_at`，可在回收站找回。第一阶段先用硬删除，保持简单。
- **不进 Git**：`.gitignore` 里必须写 `data/`，防止把个人待办推送到 GitHub。

### 6.5 为"发布到公网 / 多人使用"预留的能力

现在**不实现**，但结构上**留好口子**：

1. 每个任务都有 `user_id`，将来加一张 `users` 表即可，不用导数据。
2. 所有配置在 `config.py`，数据库地址、端口、密钥都能用环境变量覆盖。
3. 数据访问层是独立的，把 SQLite 换成 Postgres 只改 `database.py` 一处。
4. 前端调用统一走 `api.js`，将来后端换成别的域名，只改这一个文件里的 `BASE_URL`。
