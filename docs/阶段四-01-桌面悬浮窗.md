# 阶段四-01 · 桌面悬浮窗

> **本文档对应的功能**：v0.3.0 新增、v0.3.1 按用户反馈重做的「桌面悬浮窗」——
> 一个浮在桌面上的小窗口，能自由移动、控制大小、调背景透明度和字号颜色、
> 设置提醒、编辑内容、按日期/优先级/分类分块显示，
> 并且能在设置里开关、开机自启后自动出现。
>
> **内容按项目约定的「六步交付」组织**：
> 设计思路 → 代码 → 逐行解释关键代码 → 如何运行 → 测试方法 → Bug 排查。

## v0.3.1 二次改版记录（用户反馈驱动）

v0.3.0 交付后用户实际用了一会儿，提了一批非常具体的反馈。
下面把这批反馈**原话照录**，并说明各自对应到什么改动 ——
这份对照表本身比结论重要，因为它记录了"用户眼里的问题"和
"代码里的原因"是怎么对应起来的。

### 反馈 ①：窗口层级

> 1.悬浮窗要设于桌面，任何窗口都能覆盖。

**改动**：`FLOATING_ALWAYS_ON_TOP` 默认从 `True` 改成 **`False`**。

这改变了功能的**定位**：从"浮在最上层的工具窗"变成"贴在桌面上的便签"。
你打开浏览器 / 编辑器工作时它会被挡在后面（不打扰你），
按 Win+D 回到桌面时它就在那里。

**连带影响（必须知道）**：窗口被别的程序盖住之后，用户点不到它。
所以"叫它回来"的路子必须有 —— 设置页的「立即显示」按钮、
窗口右键菜单里的「总在最前面」、以及 ⚙ 设置弹窗里的同名开关，三个入口都保留。

> **验证方式**：`GetWindowLongPtr(hwnd, GWL_EXSTYLE)` 检查 `WS_EX_TOPMOST` 位 ——
> 默认应该是 **False**。实测确认。

### 反馈 ②：编辑和分类的位置与丰富度

> 2.最下面部分编辑和分类排版有误且功能过于简单，两功能放于上方，
>   编辑点击后可以弹出一个新窗口（类似于离线待办清单软件中的编辑），

**改动**：

| 原来 | 现在 |
| --- | --- |
| 底部分类下拉框 + 只有点标题文字才能编辑 | **顶部工具栏**：「＋ 新建」「⟳ 刷新」「⚙ 设置」「✕ 关闭」+ 分类按钮 |
| 编辑弹窗只有 标题 / 优先级 / 分类 / 提醒 | **编辑弹窗补齐成和网页版一致**：标题 / 分类（带已有分类快捷按钮）/ 重要度 / 截止时间 / 提醒时间（带快捷项）/ 详细描述 + 「删除」「标记完成」 |
| 底部还有一个"显示范围"下拉框 | 去掉（范围和分块是两个维度，界面上只留更常用的分块切换，范围在设置弹窗里） |

**点一行任意位置都能打开编辑**（原来是只有标题文字可点，
而标题往往很短，右半行是空的 —— 用户点了没反应，会以为坏了）。

### 反馈 ③：分类默认档次和"带上具体日期"

> 分类默认按日期分，今天 明天 七天内 之后（要附带具体日期）。

**改动**：分组标题从「今天」变成「今天 9-14」这种形式，档位也重新划过：

| 档位 | 标题长什么样 | 说明 |
| --- | --- | --- |
| 0 | `已过期 9-11` | 漏掉的，排最前面 |
| 1 | `今天 9-14` | |
| 2 | `明天 9-15` | |
| 3 | `七天内 9-16 ~ 9-21` | **显示的是日期范围**，因为这一档装了好几天 |
| 4 | `之后 10-24` | 超过一周的，显示它自己的日期 |
| 5 | `未安排日期` | 没有截止时间的，永远最后 |

**为什么"七天内"要显示范围而不是单个日期？**
因为这一档里可能有 6 个不同的日子。写成"7 天后"会误导
（那块里不只有 7 天后那一天）；写成 `9-16 ~ 9-21` 才准确。

**为什么标题里不显示年份？**
待办清单的视野通常只有最近几个月。每个分组条都塞上 `2026-`
会让标题变长，而多出来的信息对"我现在该做什么"毫无帮助。

### 反馈 ④：紧凑排列 + 放不下才滚动

> 若一个界面足够则将这几个日期紧密排列，有待办事件后插入相应日期中，
> 直至一个页面放不下，这时可以鼠标滚轮下拉。

**改动**：

- 行高、边距、分组条高度全部收紧（分组条 16 像素，比任务行还矮一点 ——
  它只是分隔符，不该抢任务的注意力）；
- **滚动条改成"需要时才出现"**（`ScrollFrame._update_scrollbar()`）：
  内容放得下的时候不显示滚动条，不占地方；
- 滚轮绑到整个应用（`bind_all`）—— 否则鼠标停在任务文字上时滚不动。

### 反馈 ⑤：分类旁边放个三角，点一下换分类

> 分类也可按照重要度或待办类型分类，在分类旁边设定一个三角点击即可更换分类类别。

**改动**：顶部工具栏有一个 `[日期 ▾]` 按钮，点一下弹出菜单：

- 按日期分块
- 按优先级分块（用户说的"重要度"）
- 按分类分块（用户说的"待办类型"）

**界面上的文字用用户的话（重要度 / 待办类型），代码里仍用
`priority` / `category` 这两个键** —— 界面文字和程序标识分开，
以后想改文案不用动逻辑。

### 反馈 ⑥：排版拥挤、字号小一点

> 3.整个界面排版有点拥挤，字号默认小一点，不要占满。

**改动**：默认字号 10 → **9 磅**；默认不透明度 30% → 50%（后来又按第 5 轮反馈定为 70%）；
行内边距从 3 像素降到 1~2 像素。

### 反馈 ⑦：右上角设置按钮

> 最后右上角要有设置按钮，可以调节字号 背景颜色 透明度 字体和字体颜色
> 是否关闭悬浮窗，

**改动**：右上角 ⚙ 打开**设置弹窗**，里面正好是用户点名的这几项：

| 项 | 控件 |
| --- | --- |
| 字号 | 滑块（6~72 磅），旁边实时显示数值 |
| 背景透明度 | 滑块，**带清晰度提醒** |
| 字体 | 下拉框（宋体/楷体/仿宋/黑体/…）+ 手打输入框 |
| 字体颜色 / 背景颜色 | 色块按钮，点一下弹出预设色 |
| 是否关闭悬浮窗 | 左下角「关闭悬浮窗」按钮 |

**注意 ✕ 和「关闭悬浮窗」的区别**（这一点在界面上要让人分得清）：

| 操作 | 效果 | 下次开机 |
| --- | --- | --- |
| 标题栏的 **✕** | 只是**隐藏**窗口 | 还会出现（功能仍开着） |
| 设置里的「**关闭悬浮窗**」 | **关掉功能** | 不会出现 |

### 反馈 ⑧：鼠标移到边缘即可移动和缩放

> 鼠标位于悬浮窗边缘即可移动与调整悬浮窗大小，
> 调整大小后里面内容排版相应改变。

**改动**：

- 四条边 + 四个角各铺一条"感应区"（`_build_edge_grips()`，6 像素宽，角落 10 像素）；
- 光标进入感应区会变成对应的箭头（↔ / ↕ / ⤡），告诉用户"这里可以拖"；
- 拖边改一个方向，拖角改两个方向，左上角拖动时窗口位置同步跟着走；
- **改完大小内容会重新折行**（`_reflow()`：给每个任务行的 Label 重设 `wraplength`）。

### 反馈 ⑨：字体清晰度是前提（这一条是"最高优先级"）

> 任务加一项：保持字体的高清晰度为排版的最基本前提。

这条一出来，就把前面几条里**互相冲突的地方**定了优先级。
它直接改掉了三件事：

| # | 改动 | 为什么 |
| --- | --- | --- |
| 1 | **声明 DPI 感知**（新增 `enable_dpi_awareness()`） | 不声明的话 Windows 会把整个窗口**拉伸放大**，文字被插值糊掉。**这才是"看不清"的真正原因（和透明度无关）** —— 所以它是"字体清晰"这条前提的**真正落点** |
| 2 | ~~透明度默认 50% → 92%，下限 5% → 80%~~ | ⚠️ **这一条后来被推翻了**（见下面的第 5 轮）。它建立在"透明度低会把字弄糊"这个**错误前提**上。用户澄清"清晰 = 分辨率保持高"之后，透明度就不需要收这么紧了 |
| 3 | 界面和文档里写清"透明会怎样影响可读性" | 这一条保留 —— 只是说法改了：损失的是**对比度**（字被桌面透淡、变难读），不是**锐利度** |

**★ 这一段值得原样留着，因为它是"基于错误前提做取舍"的活教材。**
当时我以为"想要很透"和"想要字清楚"是冲突的，于是让前者让步、把下限一路抬到 80%。
后来用户一句话就把它推翻了 —— **两个要求根本不冲突，是我把两个概念当成一个了。**
教训：**遇到互相冲突的要求，先问清"这两个词各指什么"，再谈取舍。**

**"能调得很透"和"字一直清楚"是此消彼长的 —— 用户说了后者是前提，所以前者让步。**
这就是"定优先级"的实际用法：**把优先级写成默认值和取值范围**，
而不是写在文档里当口号。

## 第 0 步：先弄清楚「要做什么」

用户的原始需求（原话照录）：

> 增加桌面悬浮窗，能自由移动，控制大小，调整背景透明度 字号和颜色，
> 设置提醒，编辑内容，可以设置按日期或优先级或分类 分块显示。
> 可以在设置里选择是否开启，开启后在开机自启动后就能运行和完成编辑与提醒

把它拆成一条条可验收的功能：

| # | 需求 | 验收标准（怎么算做到了） |
| --- | --- | --- |
| 1 | 桌面悬浮窗 | 关掉浏览器它还在桌面上 |
| 2 | 能自由移动 | 按住标题栏能拖到任意位置，位置会被记住 |
| 3 | 控制大小 | 拖右下角能改宽高，大小会被记住 |
| 4 | 调整背景透明度 | 设置页有滑块，拖动后窗口立刻变透/变实 |
| 5 | 调整字号 | 设置页有滑块，7~72 磅可调 |
| 6 | 调整颜色 | 文字色 / 背景色 / 强调色都能选，改完立刻生效 |
| 7 | 设置提醒 | 能新建带提醒的待办，到点会提醒（系统通知 + 窗口内提示） |
| 8 | 编辑内容 | 在窗口里就能改标题、优先级、分类、提醒时间 |
| 9 | 按日期分块显示 | 已过期 / 今天 / 明天 / 本周稍后 / 更远 / 未安排日期 |
| 10 | 按优先级分块显示 | 高 / 中 / 低 三块，高的排最前 |
| 11 | 按分类分块显示 | 每个分类一块，"未分类"永远排最后 |
| 12 | 设置里选择是否开启 | 设置页有总开关，默认关闭 |
| 13 | 开机自启后能运行 | 登录 Windows 后窗口自己出现，不用手动点 |

**第 13 条要特别注意**，它有两个隐含要求：
- 开机自启起的是「服务」，悬浮窗要能跟着服务一起被拉起来；
- 开机时服务还没就绪，窗口不能因为「连不上」就退出（要有等待和重试）。

**关于第 4 条，用户后来明确指定了默认值**（原话照录）：

> 悬浮窗背景透明度可以更改，默认为黑色 30%透明度，字体为宋体

后来进一步确认（原话照录）：

> 改出厂默认值，同时把你现在这台机器的配置也直接改成这套
> 透明度滑块0~100均可设置，字体 字号大小也给用户设置的空间，
> 字体默认包含宋体 楷体 仿宋 黑体

**最终定下的出厂默认外观**（经过三轮用户反馈调整后的结果）：

| 项 | 出厂默认值 | 为什么 |
| --- | --- | --- |
| 背景色 | `#000000`（纯黑） | 用户指定 |
| 文字色 | `#FFFFFF`（白） | 黑底必须配浅色字，否则「黑底黑字」= 看不见 |
| 强调色 | `#FFD166`（暖黄） | 黑底上很跳，用来标高优先级和分块标题 |
| 不透明度 | **70%** | 就是用户说的「透明度 30%」（两个说法方向相反，见下） |
| 不透明度范围 | **30% ~ 100%**（即透明度 70% ~ 0%） | 下限守的是**可读性**（再低只剩一层影子），与锐利度无关 |
| 字体 | 宋体 | 用户指定 |
| 字号 | **9 磅** | 用户要求"字号默认小一点，不要占满" |
| 字号范围 | 6 ~ 72 磅 | 用户要求"给用户设置的空间"；不同显示器合适值差别很大 |
| 位置 / 大小 | (80, 80) / 320×420 | 屏幕左上角附近，不挡中间的内容 |
| 窗口层级 | **不置顶**（任何窗口都能盖住它） | 用户指定：「悬浮窗要设于桌面，任何窗口都能覆盖」 |

**这五轮调整记录在案，因为它演示了"需求是怎么收敛的"**：

```
第 1 轮：用户给了初始值         → 黑底 / 透明度 30% / 宋体 / 10 磅
第 2 轮：实际用了一会儿         → "排版拥挤"、"字号小一点" → 9 磅、不透明度 50%
第 3 轮：提了 8 条界面反馈       → 层级改不置顶、编辑弹窗做全、分组带日期、
                                   边缘缩放、右上角设置按钮 …
第 4 轮：加了一条"前提"         → ★ 字体清晰（锐利）优先 → 声明 DPI 感知
                                   「字体清晰指的是字体分辨率保持高」
第 5 轮：澄清"透明度 30%"的方向  → 不透明度 0.70，下限放开到 0.30
```

**第 5 轮最有价值，因为它同时纠正了我两个理解错误**：

| 我原来以为 | 用户澄清后 |
| --- | --- |
| "透明度 30%" = 不透明度 0.30 | ❌ 是**不透明度 0.70**（允许三成的光透过去）。我一开始真做成了 0.30 —— 那几乎是一层全透的玻璃，窗口等于没用 |
| "字体清晰" = 对比度要高，所以要限制透明度 | ❌ 清晰指的是**分辨率/锐利度**（不能因为像素低而模糊），**和透明度无关**。限制透明度是把两件事混为一谈了 |

**第 5 轮之后，"透明"和"清晰"这两个要求就不再冲突了**：

- 「清晰」这条落在 **DPI 感知** 上（不糊）；
- 「透明度可以调低」这条落在**不透明度范围**上（能透）；
- 两者互不干涉。降低透明度只损失**对比度**（字被桌面透淡），
  不损失**锐利度**（笔画边缘依然清晰）。

这也解释了为什么第 4 轮的取舍（把下限抬到 80%）是**基于一个错误前提**做的 ——
需求理解错了，取舍就白做了。**遇到互相冲突的两个要求，先问清楚"这两个词各指什么"**，
往往比急着做取舍更有用。

## 第 1 步：设计思路

### 1.1 最关键的三个决定

做这个功能要先回答三个问题，它们的答案决定了整个架构。

#### 决定一：用什么画窗口？—— **Python 标准库 tkinter**

候选方案：

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 浏览器无边框窗口（`window.open`） | 复用现成的网页代码 | 关掉浏览器就没了；改不了整窗透明度；会被当成弹窗拦掉 | ❌ |
| Chrome/Edge 的 `--app` 模式 | 界面和网页同源 | 强依赖用户装了某个浏览器；整窗透明度做不到 | ❌ |
| PyQt / PySide | 界面漂亮、功能全 | **要给项目加一个大依赖**（几十 MB），跟「下载即跑」的原则冲突 | ❌ |
| 第三方悬浮窗库 | 现成 | 同样引入依赖，而且这类库大多不维护了 | ❌ |
| **tkinter（标准库）** | **零新依赖**；自带「无边框 + 总在最前 + 整窗透明度」；只在使用时才启动 | 界面风格朴素（想漂亮要自己画） | ✅ |

**为什么"零依赖"这么重要？** 这是本项目立身的第一条原则（见 `PROJECT.md` 决策 6）：
「下载下来就能跑」。为了一个窗口引入几十 MB 的 GUI 框架，
等于提高了所有人的安装门槛，而收益只是「好看一点」。这笔账不划算。

> ⚠️ 一个连带改动：`OfflineTodoList.spec` 里原来有 `excludes=['tkinter']`，
> 是 0.2.0 时代为了省体积加的。现在必须删掉 —— 否则安装版里
> 点「开启悬浮窗」只会得到一个**静默失败**（窗口起不来，没有任何提示）。
> **代价是安装包变大（约 +10 MB），换来的是「安装版也能用悬浮窗」。**
> 这个取舍写在 `.spec` 的注释里，免得以后有人看到体积变大又把它加回去。

#### 决定二：窗口是「服务的一个线程」还是「独立进程」？—— **独立进程**

| 方案 | 问题 |
| --- | --- |
| 在服务进程里开个线程画窗口 | **tkinter 的界面必须在主线程跑 `mainloop()`**，而服务进程的主线程被 uvicorn 占着。硬塞进子线程在 Windows 上会闪退 |
| **独立进程** | ✅ 顺带解决三件事：① 窗口卡住不拖累服务（服务还在发提醒）；② 服务重启时窗口可以不跟着死；③ 界面代码崩了不会让提醒停摆 |

代价是「两个进程要通信」。这就引出决定三。

#### 决定三：窗口怎么拿数据？—— **走本机 HTTP，不直连数据库**

窗口跑在另一个进程里，它要拿待办列表，有两条路：

| 方案 | 问题 |
| --- | --- |
| 直连 SQLite 读库 | ① 两个进程同时写库，可能撞上 `database is locked`；② 窗口就得把 `models` / `repositories` / `services` 整套代码搬过去，以后改一处数据逻辑要保证两个进程都升级 —— 很容易漏 |
| **走 `http://127.0.0.1:8000` 的现成接口** | ✅ 只有一个数据出口；代价是一次本地网络调用（实测 1~3 毫秒） |

选了后者。它带来一条**必须遵守的架构约束**：

> **窗口进程只允许通过 `app/gui/client.py` 访问数据，
> 绝不允许 import `repositories` 或直连数据库。**

这条约束写成了自动化测试（`tests/test_gui_utils.py::TestClientIsTheOnlyExit`，
会去读源码检查有没有出现 `from app.repositories` / `sqlalchemy` 这些字眼）。
**为什么要用测试去检查「代码风格」？** 因为这种约定一旦破了不会报任何错，
只会在「以后要改数据逻辑」的时候才发现有两个地方要改。

### 1.2 数据流全景图

看懂这张图就懂了这个功能：

```
┌───────────────────┐                      ┌─────────────────────────┐
│ 设置页（浏览器）   │  GET  /api/floating   │  FastAPI 服务进程        │
│ · 开关 / 滑块 / 色块│ ───────────────────► │  routers/floating.py    │
│ · 分块方式 / 字号  │  PATCH /api/floating/ │        ↓                │
└───────────────────┘        config        │  services/              │
                                           │   floating_service.py   │
┌───────────────────┐                      │        ↓                │
│ 悬浮窗进程         │                      │  repositories/          │
│ （tkinter，独立）  │ ◄─────────────────── │   floating_repo.py      │
│                   │  GET /api/floating/  │        ↓                │
│ 每 10 秒拉数据     │      data            │   settings 表（键值对）  │
│ 每 3 秒问设置      │  GET /api/floating/  │                         │
│                   │      config          │  ┌───────────────────┐  │
└───────────────────┘                      │  │ 守护线程 supervisor│  │
                                           │  │ 每 3 秒检查一次：   │  │
                                           │  │ 该开就开 / 该关就关 │  │
                                           │  └───────────────────┘  │
                                           └─────────────────────────┘
```

三个要点：

1. **设置存在 `settings` 表里**（键值对结构，复用现成的表，不改表结构）。
   加一项设置只需在 `floating_repo.FIELDS` 里加一行。
2. **守护线程是「设置开关」和「真有一个窗口」之间的桥**。
   没有它，用户点一下开关只能靠「一次性动作」把窗口拉起来；
   而窗口可能因为内存不足、被任务管理器结束等原因意外退出 ——
   有一个东西一直盯着，用户才能放心地把开关开着。
3. **窗口和设置页都是「客户端」**，用的是同一套接口（权限略有不同）。

### 1.3 怎么保证「不会开出两个窗口」？—— 双保险

点两次「开启」就叠出两层窗口，是这类功能最常见的 Bug。本项目用了两道闸门：

| 闸门 | 做法 | 挡住什么 |
| --- | --- | --- |
| 服务端线程锁 `_SPAWN_LOCK` | 「检查有没有窗口」和「启动窗口」放在同一个锁里 | 守护线程和设置页按钮**同时**判断出「没有窗口」然后各拉一个 |
| 窗口进程的文件锁 `floating.lock` | 窗口启动时用 `msvcrt.locking` 抢一个独占锁，抢不到就退出 | 已经有一个窗口在跑时，第二个进程自己退出 |

**为什么"判断有没有窗口"不能靠"试着打开锁文件"？** 这里踩过坑：

> 最初写的是 `open(lock_file, "r+b")`，以为「打不开就是被占用」。
> **这是错的** —— 在 Windows 上，一个文件被别人上了字节锁之后，
> 别的进程依然能正常 `open()` 它，只是读不到被锁的那几个字节。
> 所以「能打开」根本不能说明「没人在用」，结果就是
> 「已经有一个窗口在跑了，服务端却以为没有」→ 又开一个。
>
> **正确做法**：判断「锁有没有被占」唯一可靠的办法是**真的去抢一次**，
> 而且要用和占用方一模一样的方式（同样的粒度、同样的起始位置）。

另外，「谁还活着」靠【文件锁】而不是【pid 文件】：
进程无论是正常退出还是被强杀，**操作系统都会自动释放文件锁**；
而 pid 文件会因为崩溃而残留下来（下次启动就误以为窗口还在跑）。

**pid 文件仍然有用**，它负责两件事：显示「运行中（进程号 xxx）」，以及当
锁被占着、但 pid 文件里的进程已经不在了时，判定为「上一个死掉的窗口留下的残渣」，
清理干净允许重开 —— 否则用户会陷入「再也开不起来」的困境。

### 1.4 「按日期 / 优先级 / 分类分块」怎么实现？

分块的本质是「给每条任务算一个块名，然后按块名聚到一起」。
核心函数就一个：`group_key(task, group_by)`，返回 `(排序号, 块标题, 块内排序号)`。

**为什么第一位是「排序号」而不是块标题？** 因为 Python 排序时先比第一个元素，
把「我希望这块排第几」放第一位，结果就是「块按我指定的顺序排列」，
不用给每种分块方式各写一遍排序代码。

| 分块方式 | 块的划分 | 块顺序 |
| --- | --- | --- |
| `date` | 已过期 / 今天 / 明天 / 本周稍后 / 更远 / 未安排日期 | 按时间紧迫度（过期的排最前，没日期的最后） |
| `priority` | 高优先级 / 中优先级 / 低优先级 | 排序号取**负数**，于是「高」排最前 |
| `category` | 每个分类一块 + 「未分类」 | 按名字排，「未分类」永远最后 |

「未分类永远排最后」是一个刻意的设计：它是兜底分类，不该占据视线的第一屏。

**「显示范围」和「分块方式」是两个独立的维度**，可以自由组合：

| 范围 | 含义 |
| --- | --- |
| `active`（默认） | 未完成的 + 今天完成过的（做了的当天还能看见，有成就感） |
| `today` | 今天到期的 + **已过期还没做的** |
| `week` | 未来七天内的 + 没日期的 |
| `all` | 全部 |

**为什么不把过期的藏起来？** 待办清单的价值恰恰在于「提醒你漏了什么」。
把过期任务藏掉的清单，是一份**会骗人的**清单。

### 1.5 窗口刷新怎么做才不会「一闪一闪」？—— 版本号 + 内容指纹

窗口每 10 秒拉一次数据。如果每次都无脑重画整个列表，会有两个毛病：
① 白白耗 CPU（上百个控件删掉重建）；② 用户正在拖滚动条时列表会「跳」一下。

解决办法是两层判断：

| 层 | 机制 | 作用 |
| --- | --- | --- |
| 服务端 | 数据版本号 `floating_data_version` | 任何写操作（新建/编辑/勾选）都让它 +1 |
| 服务端 | 内容指纹 `signature`（对关键字段算 md5） | 回答「内容到底一不一样」 |
| 客户端 | 指纹没变就 `return`，一个字都不重画 | 彻底避免闪烁和浪费 |

**为什么两层都要？** 版本号是粗粒度信号（「有人动过数据」），
指纹是精确判断（「内容真的一样」）。版本号负责「要不要去问」，指纹负责「问了之后要不要重画」。

### 1.6 设置项怎么存，才能「改一个不影响其它」？

用 `settings` 表的键值对（复用现成的表，不改表结构），
但**读写逻辑由一张「字段表」驱动**：

```python
FIELDS = {
    "opacity":     (PREFIX + "opacity",     "float", config.FLOATING_DEFAULT_OPACITY),
    "font_family": (PREFIX + "font_family", "str",   config.FLOATING_DEFAULT_FONT_FAMILY),
    ...
}
```

**为什么要这张表？** 没有它就得手写十几遍
`_get_int("fw_x", 80)` / `if "x" in changes: set("fw_x", ...)` 这种代码，
加一项设置要改三个地方。有了表，「读全部」「写一批」「取默认值」全变成一次循环。

另一个关键是**接口用 PATCH 语义**：只改用户真正传过来的字段。
如果误用 PUT（整份替换），那么窗口上「拖动一次位置」就会
把用户的字号、颜色、分块方式**全都重置回默认值** —— 这是灾难性的体验。

### 1.7 安全：窗口令牌

`/api/floating/data` 这类「能读写数据」的接口需要带一个随机令牌
（放在 `X-Float-Token` 请求头里）。令牌由服务端生成、存在本机数据库里，
启动窗口进程时用**环境变量**传给子进程。

**这道闸门防的不是「黑客」** —— 服务只监听 `127.0.0.1`，本来就只允许本机访问。
它防的是「意外」：比如另一个网页刚好猜到了接口路径，想通过它把悬浮窗设置改掉
或者把窗口关掉。没有令牌就做不成。

**边界要说清楚**：这不是完整的鉴权机制。真要防黑客得靠「不对外暴露端口」这件事本身。

### 1.8 出厂默认外观的最终定案

| 项 | 值 | 备注 |
| --- | --- | --- |
| 背景色 | `#000000` | 用户指定（纯黑） |
| 文字色 | `#FFFFFF` | 黑底配白字，保证「看得清」；由测试守着 |
| 强调色 | `#FFD166` | 暖黄，黑底上跳得出来 |
| **不透明度** | **70%** | 就是用户说的「**透明度 30%**」—— 两个说法**方向相反**，写反过一次（见下面那段说明） |
| 不透明度范围 | 30% ~ 100% | 即透明度 70% ~ 0%。下限守的是**可读性**（再低只剩一层影子），与锐利度无关 |
| 字号 | 9 磅 | 用户要求"默认小一点，不要占满" |
| 字号范围 | 6 ~ 72 磅 | 用户要求「给用户设置的空间」；不同显示器合适值差别很大 |
| 字体 | 宋体 | 用户指定 |
| 字体预设 | 宋体 / 楷体 / 仿宋 / 黑体 / 微软雅黑 / Microsoft YaHei UI / Consolas / Segoe UI | 用户要求包含前四款中文字体 |

### ★ 「不透明度」和「透明度」方向相反，写反过一次

| 说法 | 含义 | 换算 |
| --- | --- | --- |
| **不透明度**（代码里的 `opacity`） | 数字越大越**不**透明 | 1.0 = 一点也看不透 |
| **透明度**（中文口语） | 数字越大越透 | **透明度 = 100% − 不透明度** |

用户说「透明度 30%」，意思是"允许三成的光透过去"，
所以代码里要写 **`FLOATING_DEFAULT_OPACITY = 0.70`**。

**开发过程中真的写反过一次**：把"透明度 30%"直接填成了 `opacity = 0.30`
（那等于透明度 70% —— 一层几乎全透的玻璃，字都读不出来），
做了半天才发现方向搞反了。

**防复发的措施**：

1. 配置里的注释把三种说法**并排列出来**（0.70 ↔ 30%、1.00 ↔ 0%、0.30 ↔ 70%）；
2. 测试里连**方向**一起断言（`assert cfg["opacity"] == 0.70` 并写上"写成 0.30 就是理解反了"）；
3. 设置页上的滑块标签直接写成「**背景不透明度（透明度 = 100% − 这个数）**」，
   并把换算结果实时显示在旁边（用户调的时候能直接看到"透明度 30%"）。

### 为什么下限是 30%（而不是 0）？

窗口的透明度是**整窗**的：文字和按钮会一起变透明。
如果不透明度低到接近 0，窗口就只剩一层影子了 —— 而且它**没有系统标题栏**，
用户连「用鼠标点一下把它找回来」都做不到，只能去设置页点「立即显示」。
30% 是为了保证「最透明的时候，内容仍然读得出来」。

**注意这个下限守的是「可读性」，不是「清晰度」** —— 这两件事不一样，见下一节。

设置页的文案也据实说明：滑块旁边实时显示「不透明度 70%（= 透明度 30%）」，
并写明"调得越透，桌面透进来越多、字越难读（对比度下降）"——
而不是含糊地说"会变淡"。

### ★★ 「清晰度」和「对比度」是两件事（用户专门澄清过）

用户原话：

> 字体清晰指的是字体分辨率保持高，在任何情况下不能因为模糊像素低而看不清

这句话把两个经常被混为一谈的概念分开了：

| | 是什么 | 由什么决定 | 受透明度影响吗 |
| --- | --- | --- | --- |
| **清晰度**（锐利） | 笔画边缘利不利、有没有糊成一团 | **渲染方式** —— 声明了 DPI 感知，Windows 就不会把窗口位图拉伸放大 | ❌ **不受影响** |
| **对比度**（好不好读） | 字和背景的亮度差有多大 | 半透明混色的比例 | ✅ 会按比例变小 |

**为什么"降低透明度不变糊"？** 因为 tkinter 的 `-alpha` 走的是 Windows 的
**分层窗口（Layered Window）** 机制：整幅位图按同一个系数和桌面混合，
每个像素只和**自己同一位置**的底色混合 —— **不涉及邻域平均**。
而"模糊"的本质恰恰是邻域平均。所以从数学上，它只可能让颜色变淡。

**所以第 4 轮那次"把下限抬到 80%"的取舍是白做的** ——
它建立在"透明度低会糊"这个错误前提上。第 5 轮澄清之后：

- 「字必须清晰」→ 落在 **DPI 感知** 上（`FLOATING_DPI_AWARE = True`）；
- 「透明度可以调低」→ 落在 **不透明度范围** 上（默认 0.70、下限 0.30）。

两条要求**根本不冲突**。这个结论有一条测试专门守着
（`tests/test_floating_service.py::test_clarity_and_transparency_are_different_things`），
里面把这个区分写成了文档。

**旧版本的设置怎么办？—— 迁移。**

开发期间透明度的合法范围曾经是「30~100 的整数」，后来改成「0.05~1.0 的小数」。
用户数据库里已经存着旧格式的值（比如 `92`），直接喂给 tkinter 的 `-alpha`
会抛异常 → **窗口开不出来，而用户完全想不到是透明度的问题**
（他上次动透明度可能是几个月前）。

所以服务启动时跑一次 `migrate_legacy_settings()`：把 30~100 之间的值除以 100。
它必须是**幂等**的（跑两次结果一样），而且要能容忍坏值（设置表可能被手改过）。

## 第 3 步：逐行解释关键代码

### 3.1 表驱动的设置存取：`floating_repo.FIELDS`

```python
FIELDS = {
    "opacity":     (PREFIX + "opacity",     "float", config.FLOATING_DEFAULT_OPACITY),
    "font_family": (PREFIX + "font_family", "str",   config.FLOATING_DEFAULT_FONT_FAMILY),
    # ...
}
```

一个「名字 → (数据库键, 类型, 默认值)」的映射。它换来三件事：

1. `get_config()` 一次循环读完所有字段，并且**按类型转好**（上层拿到的就是
   `float` / `bool` / `int`，不用自己记得"这个字段是 int"）；
2. `set_config(**changes)` 一次循环写完，**自动过滤未知字段**
   （这不是「宽容」，是必要的：防止有人通过接口往设置表里塞任意内容）；
3. `defaults()` 直接从表里取，**默认值和读取逻辑不可能不一致**。

`_cast()` 里那个「转不动就退回默认值」的兜底是刻意的：

```python
except (TypeError, ValueError):
    return default
```

**为什么不抛异常？** 因为这个函数被**守护线程**调用。
后台线程一旦抛异常就会安静地死掉，而程序表面一切正常 ——
用户只会发现「悬浮窗再也开不起来了」。
**一个坏掉的设置值，不值得让整个功能瘫痪。**

### 3.2 分块：`group_key()`

```python
if group_by == "priority":
    priority = task.priority
    # 排序号取负数：这样"高优先级"排在最前面（数字越小越靠前）
    return (-priority, config.PRIORITY_NAMES.get(priority, "中") + "优先级", 0)
```

`-priority` 这个负号是「用一次取负换掉一个自定义比较函数」的典型手法：
默认排序是「小的在前」，而我们希望「优先级高的（数字大的）在前」，
取负之后两者就一致了。

日期分块里判断「明天」用的是：

```python
if timeutil.humanize(due).startswith("明天"):
```

**为什么不自己算「明天是哪一天」？** 因为那涉及跨月、跨年、闰年这些边界。
项目约定「时间换算只允许写在 `timeutil.py` 里」，
这里复用它，就不用在两处各写一遍日期加减法。

「本周稍后」用的是标准库算天数差：

```python
def _days_until(day: str, today: str):
    from datetime import date
    return (date.fromisoformat(day) - date.fromisoformat(today)).days
```

「2 月 28 日到 3 月 1 日差几天」这种问题交给标准库永远比手写可靠。

### 3.3 窗口载荷与缓存：`window_payload()`

```python
now = time.time()
if not force and _data_cache["payload"] is not None and \
        (now - _data_cache["at"]) < _CACHE_TTL_SECONDS:
    return _data_cache["payload"]
```

1 秒的缓存。**为什么需要它？** 设置页的「刷新」和窗口的定时刷新可能同时发生，
而分组、装饰字段（算 `due_label` / `overdue` / `remind_label`）都不便宜。
1 秒足够挡掉这种瞬时重复。

组装时把 ORM 对象**换成普通字典**并加上界面要用的字段：

```python
item = task.to_dict()
item["is_done"] = task.status == config.STATUS_DONE
item["due_label"] = _due_label(due, now_text)      # "今天 18:00"
item["overdue"] = bool(due and not item["is_done"] and due < now_text)
item["remind_soon"] = ...                            # 一小时内要提醒
```

**为什么这些「显示用」的字段要在服务端算？** 因为时间比较的规则属于业务逻辑
（「什么时候算今天」「过期怎么算」），这种规则只应该有一份实现。
窗口只负责把字符串画出来 —— **它是「笨」的，越笨越不容易出错。**

### 3.4 窗口进程的「座位」：文件锁

```python
def _lock_held() -> bool:
    probe = acquire_window_lock()
    if probe is None:
        return True          # 抢不到 = 有人在用
    release_window_lock(probe)
    return False
```

**这个函数是「必须真的抢一次」的正面例子。** 注释里记着踩过的坑：

> 最初写的是 `open(lock_file, "r+b")`，以为「打不开就是被占用」。**这是错的** ——
> 在 Windows 上，一个文件被某进程用 `msvcrt.locking` 上了字节锁之后，
> 别的进程依然能正常 `open()` 它，只是读不到那几个被锁的字节。

抢锁本身要保证文件至少有 1 个字节：

```python
handle.seek(0, os.SEEK_END)
if handle.tell() == 0:
    handle.write(b"\0")
    handle.flush()
handle.seek(0)
msvcrt.locking(handle.fileno(), msvcrt.LK_NBLCK, 1)
```

用「追加模式」打开时写入总是追加到末尾 —— 所以先判断一下，
别每次都往后追加一个 `\0`（那会让文件慢慢变大）。

### 3.5 「不要开出两个窗口」的第一道闸门

```python
with _SPAWN_LOCK:
    cfg = get_config()
    if not cfg["enabled"]:
        return {...}
    if is_window_running():
        return {"ok": True, "started": False, "message": "悬浮窗已经在运行"}
    ...
    proc = _spawn()
```

**「检查」和「启动」必须在同一个锁里。** 这在并发编程里叫
**检查-使用竞态（check-then-act race）**，是初学者最容易踩的一类坑：
守护线程和设置页按钮可能同时判断出「没有窗口」，然后各拉一个起来。
文件锁能兜住这个漏（第二个进程会自己退出），但让第二个进程白启动一次
也是浪费 —— 两道闸门一起用，才叫纵深防御。

### 3.6 子进程的启动：`_spawn()`

```python
env["TODO_HOST"] = config.HOST
env["TODO_PORT"] = str(config.PORT)
env["TODO_DATA_DIR"] = str(config.DATA_DIR)
env["TODO_FLOAT_TOKEN"] = floating_repo.get_token()      # ← BUG-023 就是漏了这一行
```

**最后一行是必须的**，而且它漏了会造成一个特别难查的现象：

> 窗口能起来，但每次调接口都收到 403 → 窗口自己退出 →
> 守护线程 3 秒后又把它拉起来 → **无限循环**。
> 任务管理器里堆出一串 `pythonw` 进程，而用户一头雾水。

这类 Bug **不报错、不崩溃**，只是在反复重启。
所以补了 `tests/test_floating_service.py::TestSpawnEnvironment` 专门盯着它。

启动方式分三种环境：

```python
if config.FROZEN:
    cmd = [sys.executable, "--floating"]                    # 安装版：同一个 exe 再启动一次
else:
    cmd = [str(_python_interpreter()), str(config.BASE_DIR / "run.py"), "--floating"]
```

源码版用 `pythonw.exe`（它和 `python.exe` 是同一个程序，区别只是**不带控制台窗口**）；
找不到就退回 `python.exe`（难看一点总比不能用好）。

还有两个 Windows 专属的启动标志：

```python
creationflags = (getattr(subprocess, "CREATE_NO_WINDOW", 0)
                 | getattr(subprocess, "CREATE_NEW_PROCESS_GROUP", 0))
```

- `CREATE_NO_WINDOW`：防止弹出黑色控制台；
- `CREATE_NEW_PROCESS_GROUP`：让窗口进程**不**跟着服务进程一起吃 `Ctrl+C`，
  这样服务重启时窗口还能活下来。

输出必须重定向：

```python
log_handle = open(log_path, "a", encoding="utf-8")
...
stdout=log_handle, stderr=subprocess.STDOUT
```

**为什么必须重定向？** 窗口是 `noconsole` 启动的，它没有控制台，
一旦抛异常，那段堆栈会消失得无影无踪 —— 到时候只能靠猜。
现在它落在 `data/floating/window.log` 里。

### 3.7 让窗口自己退出，而不是杀掉它

```python
stop_file = config.FLOAT_DIR / "stop.flag"
stop_file.write_text("stop\n", encoding="ascii")
# ... 等最多 3 秒 ...
still_alive = is_window_running()
if still_alive and pid:
    logger.warning("悬浮窗没有响应退出信号（pid=%s），改为强制结束", pid)
    _kill(pid)
```

**为什么是「请它退出」而不是「杀掉它」？**
直接 `kill` 会跳过 tkinter 的清理：**窗口位置 / 大小还没来得及存**，
用户刚拖动过的地方下次就丢了。
所以先写一个「停」字给窗口看，让它自己保存设置再退出；
只有它赖着不走（超过 3 秒）才动手强杀 —— 这是最后手段。

窗口那边对应的是：

```python
def _watch_stop_file(self):
    if self._stop_file.exists():
        logger.info("收到停止信号，准备退出")
        self._patch_config({"visible": False}, quiet=True)
        self.shutdown()
        return
    self.root.after(1500, self._watch_stop_file)
```

### 3.8 窗口界面：无边框、拖动、缩放

去边框：

```python
self.root.overrideredirect(True)              # 去掉系统标题栏
self.root.attributes("-topmost", True)        # 总在最前
self.root.attributes("-alpha", 0.30)          # 整窗透明度
self.root.attributes("-toolwindow", True)     # 不出现在任务栏和 Alt+Tab 里
```

`-toolwindow` 的作用是让窗口**不出现在任务栏和 Alt+Tab 列表里** ——
悬浮窗的正确形态是「贴在桌面上的便签」，不是「一个正经的应用窗口」。

**去掉系统标题栏是有代价的**：系统提供的「拖动、缩放、关闭」全都没了，
必须自己补回来。这是无边框方案必须付的账。

拖动：

```python
def _drag_start(self, event):
    self._dragging = True
    self._drag_offset = (event.x_root - self.root.winfo_x(),
                         event.y_root - self.root.winfo_y())

def _drag_move(self, event):
    if not self._dragging:
        return
    x = event.x_root - self._drag_offset[0]
    y = event.y_root - self._drag_offset[1]
    self.root.geometry("+%d+%d" % (x, y))
```

**为什么要记「偏移量」，不能直接用鼠标坐标当窗口坐标？**
那样窗口会「跳」一下：你按窗口右边，窗口左上角就跑到鼠标那儿去了。
记住偏移量、拖动时保持它不变，手感才对。

缩放：右下角放一个 `◢` 小三角，拖动它改宽高，并夹在允许范围内：

```python
width = max(config.FLOATING_MIN_WIDTH, min(start_w + (event.x_root - start_x),
                                           config.FLOATING_MAX_WIDTH))
```

保存位置用**防抖**：

```python
def _schedule_save_position(self):
    if self._save_job is not None:
        self.root.after_cancel(self._save_job)
    self._save_job = self.root.after(400, self._save_position)
```

用户拖动时会连续触发几十次移动事件，每次都写一次数据库 =
几十次磁盘写 + 几十次版本号 +1，纯属浪费。
延迟到「手停下来」再存一次，这个过程叫**防抖（debounce）**。

### 3.9 「窗口跑到屏幕外了」怎么自救？

```python
def _clamp_position(self, x, y, width, height) -> tuple:
    screen_w = self.root.winfo_screenwidth()
    screen_h = self.root.winfo_screenheight()
    margin = 40
    x = max(margin - width, min(x, screen_w - margin))
    y = max(0, min(y, screen_h - margin))
    return x, y
```

这是一种很常见的困境：用户把窗口拖到副屏，后来副屏拔了，
窗口就「活在屏幕外面」—— 看不到、点不着、也没法拖回来。
启动时和每次改几何时都校正一次，就堵住了这条路。

留 40 像素余量是为了「让用户至少还能看见一条边，能用鼠标抓到它」。

### 3.10 自动挑对比色，保证文字一定看得清

```python
def contrast_text(bg: str) -> str:
    r, g, b = _hex_to_rgb(bg)
    # 人眼对绿色最敏感、对蓝色最不敏感，所以加权系数不一样（国际标准公式）
    luminance = (0.299 * r + 0.587 * g + 0.114 * b) / 255
    return "#000000" if luminance > 0.6 else "#FFFFFF"
```

**为什么需要它？** 用户可以把背景设成纯黑，也可以设成纯白。
如果文字颜色是「跟着主题写死的」，换主题后很可能变成
**深色字配深色底 —— 一片糊**，程序不报任何错，用户以为程序坏了。
用亮度公式自动挑黑或白，任何配色都不会看不清文字。

这个函数有专门的测试（`TestContrastText::test_all_themes_are_readable`），
会遍历所有内置主题，确认「文字和背景的亮度差足够大」——
以后有人加了一个「深紫色」主题、恰好落在分界上导致字看不清，测试会立刻失败。

### 3.11 不重画也会「卡住」：`_appearance_changed` 的教训

窗口每 3 秒问一次服务端「设置改了没」，判断依据是一张字段清单：

```python
keys = ("bg_color", "fg_color", "accent_color", "font_family", "font_size")
```

另一个函数管外框相关的：

```python
def _geometry_changed(self, new_config: dict) -> bool:
    keys = ("x", "y", "width", "height", "opacity", "always_on_top")
```

**分两个函数的理由**：配色变了必须**重建整个界面**（着色不能在原地改）；
而位置/大小/透明度只要改外框就够了（更快、也不闪）。

清单漏一项的后果是「用户改了它，窗口毫无反应，看起来像设置坏了」。
**BUG-024 就是这么来的**（当时 `_appearance_changed` 里漏了 `width` / `height`）。

为了防复发，写了一条**自动检查**：

```python
def test_every_config_field_is_watched_by_something(self):
    EXEMPT = {"enabled", "autostart", "visible", "show_completed",
              "highlight_reminders", "group_by", "scope", "data_version"}
    # 从判断函数里把字段名读出来（源码即规格）
    ...
    missing = set(floating_repo.FIELDS) - watched - EXEMPT
    assert not missing, "这些设置项改了窗口却不会响应：%s" % sorted(missing)
```

**这才是防复发的正确姿势。** BUG-024 的本质不是「漏写了 width」，
而是「漏写了也不会有人发现」。这条测试把这件事变成自动检查：
以后新增设置项，要么被某个判断函数盯上，要么显式写进 `EXEMPT` 说明理由。

顺带还写了「没变就别乱重建」的反向测试 —— 防的是
「每次轮询都重建整个界面」（那样窗口会每 3 秒闪一次）。

### 3.12 编辑对话框：为什么时间换算要走服务端？

窗口里的「10 分钟后 / 今天 18:00 / 明天 09:00」这些快捷选项，
换算成具体时间**不是客户端算的**：

```python
def remind_at(self, choice: str) -> str:
    return self._request("/api/floating/remind-at?choice=" +
                         urllib.parse.quote(str(choice)))["remind_at"]
```

**为什么？** 因为新建/修改待办时，接口会校验「**提醒时间不能早于当前时间**」。
如果换算在窗口进程里做、校验在服务进程里做，两边时钟只要差几秒，
就会出现「我明明选了 10 分钟后，却提示时间早于当前」这种莫名其妙的错误。

换成服务端来算，用的就是服务端自己的钟 ——
**自相矛盾从结构上就不可能发生**（这叫「单一事实来源」）。

服务端那边还要处理一个边界情况：

```python
if target <= now:
    target += timedelta(days=1)
```

已经过了今天 18:00 还想「今天 18:00 提醒」？那就顺延到明天同一时刻 ——
否则接口会以「时间早于当前」拒绝，用户反复点却怎么也加不上，会以为是 Bug。

### 3.13 业务规则只有一份：`quick_add()`

```python
def quick_add(payload) -> dict:
    task = task_service.create_task(payload)
```

窗口新建待办**完全复用** `task_service.create_task`，
不另写一套校验。

**为什么这条要单独说？** 因为「再写一套」是很自然的诱惑
（窗口的入参和网页不完全一样）。但那样「提醒时间不能早于当前」这类规则
就有了两份实现，改了一处忘了另一处，**两个入口的行为就会不一致** ——
而「两个入口行为不同」是最难查的一类 Bug。

正确做法是：**接口可以有两个，业务规则只能有一份。**

### 3.15 旧数据的迁移

```python
LEGACY_OPACITY_THRESHOLD = 5.0     # 新的合法值恰好落在 0.05~1.0，永远小于 5

def migrate_legacy_settings() -> dict:
    raw = setting_repo.get(opacity_key)
    ...
    if not (LEGACY_OPACITY_THRESHOLD <= value <= 100):
        return {"migrated": False, "reason": "透明度已经是新格式（%s）" % raw}
    new_value = round(value / 100.0, 2)
    setting_repo.set_value(opacity_key, new_value)
```

三个必须做到的点，都有对应测试：

| 要求 | 为什么 | 对应测试 |
| --- | --- | --- |
| 幂等（跑两次结果一样） | 服务每次启动都会跑，不幂等就是灾难 | `test_idempotent` |
| 不碰新格式的值 | 判断写错的话 `0.3` 会被再除一次变成 `0.003`，窗口淡到看不见 | `test_does_not_touch_new_format` |
| 坏值不能让启动崩掉 | 设置表可能被手改过；崩溃的话整个服务都起不来 | `test_garbage_value_is_not_fatal` |

**为什么不干脆清空用户的设置、用新默认值？**
透明度只是他调过的众多设置之一。直接清空会顺手抹掉他精心调好的
字号、颜色、位置 —— 那是一种「为了省事而破坏用户数据」，
违反**数据安全铁律四**（永远不要替用户判断「这些东西不重要」）。

| **改字号 / 颜色 / 透明度 / 字体** | 点右上角 **⚙** → 设置弹窗 |

想真正关闭请在设置页关掉总开关。

### 5.3 怎么确认「提醒真的能用」

提醒由**后台线程**扫描并发系统通知，不依赖浏览器。测法：

1. 在悬浮窗里新建一条待办，提醒时间选「10 分钟后」；
2. 等 10 分钟 —— 右下角应该弹出 Windows 系统通知；
3. 同时窗口内也会浮出一个提示条（万一系统通知被专注助手拦掉，
   窗口内的提示就是第二条保险）。

想立刻测而不是等 10 分钟，可以双击 `test_reminder.bat`。

### 5.4 怎么确认「不会开出两个窗口」

这是最容易出问题的地方，值得单独测：

1. 打开悬浮窗（确认桌面上只有一个）；
2. 在设置页把开关**关了又开**，重复三四次；
3. 打开任务管理器，找 `pythonw.exe` —— **应该只有一个**。

也可以用命令行验证（**在 `win11` 里执行**）：

```powershell
python -c "import urllib.request,json; print(json.load(urllib.request.urlopen('http://127.0.0.1:8000/api/floating'))['window'])"
```

`running` 是 `True`、`pid` 是一个具体数字，就说明只有一个窗口在跑。

## 第 6 步：Bug 排查

### 6.1 窗口没出现？按这个顺序查

**第 1 步：看设置页的「窗口进程」那一行**

它会直接告诉你状态，例如：

| 显示 | 含义 | 怎么办 |
| --- | --- | --- |
| 未开启 | 总开关没开 | 打开开关 |
| 已开启，但窗口当前是隐藏的 | 之前点过 ✕ | 点「立即显示」 |
| 已开启，窗口正在启动中… | 拉起来了但还没握手成功 | 等 5 秒再看；还不行就点「重启窗口」 |
| 运行中（进程号 12345） | 正常 | — |
| 当前 Python 没有 tkinter | 解释器缺模块 | 重装 Python（勾选 tcl/tk），或改用安装版 |

**第 2 步：看窗口日志**

点设置页的「**打开窗口日志目录**」，看 `window.log`。
窗口是 `noconsole` 启动的，**它的报错只在这里**。
常见内容：

| 日志里出现 | 原因 | 怎么办 |
| --- | --- | --- |
| `HTTP Error 403: Forbidden` | 令牌不对 | 点设置页的「重启窗口」（会带上新令牌） |
| `ConnectionResetError` / `连接不上服务` | 服务正在重启或已经退出 | 确认服务在跑；窗口会自己重试 |
| `已有一个悬浮窗在运行` | 已经有一个窗口了 | 正常的自我保护，不是错误 |
| `_tkinter.TclError: bad color` | 颜色值不合法 | 一般不会出现（接口那一层已经挡住了），报上来我查 |

**第 3 步：手动把它叫回来 / 重开**

```
（设置页）立即显示 → 重启窗口
```

**第 4 步：还没有？用命令行兜底**

```powershell
# 在 win11 里执行
python run.py --floating-stop      # 先把残留的窗口停掉
python run.py --floating           # 再手工启一个，这次会直接打印报错
```

手工启动时**报错会打印到屏幕上**，比看日志更直接。

### 6.2 窗口跑到屏幕外面看不见了

拔掉副屏、改过分辨率之后可能出现。两个办法：

| 办法 | 怎么做 |
| --- | --- |
| 恢复默认位置 | 设置页 → 「恢复默认设置」（位置回到左上角 80,80） |
| 强行停掉再来 | `python run.py --floating-stop`，然后重新「立即显示」 |

程序自己也有防护：启动时和每次改几何**都会把位置夹回屏幕可见范围**，
正常情况下不会出现这个问题。

### 6.3 改了设置但窗口没反应

按这个顺序排：

1. **等 3 秒**。窗口每 3 秒才问一次设置 —— 改完立刻看可能还没轮到。
2. **看是哪个设置**。有两类：
   - 配色 / 字体：会**重建整个界面**，一定能生效；
   - 位置 / 大小 / 透明度 / 置顶：只改外框，也应该生效。
3. **如果是「位置」不生效**，请记下来告诉我 ——
   这是本次开发**已知还没排查完的一个点**（见下一节）。
4. 点设置页的「重启窗口」，这是最可靠的兜底。
