# 待优化与已知问题清单

> **这个文档是干什么的**
> 记录"功能上想改、但现在先不做"的事情。
>
> **为什么不立刻做？**
> 因为先把整体框架搭完整，比反复打磨某一个细节更重要。
> 很多优化在框架完整后做，成本会低得多（因为能复用的代码更多了）。
>
> **使用约定**
> 1. 编号 `OPT-XXX` 依次递增，只增不改（做完就标记状态，不删记录）；
> 2. 每条要写清楚：**类型 / 描述 / 优先级 / 来源 / 状态**；
> 3. 用户反馈的问题**原话照录**，不要自己"翻译"成技术语言——
>    原始描述往往包含你自己想不到的线索（见 BUG-004 的教训）。

**用户原话：**

**已做的修复**：

3. **立刻实现自动备份**（把 OPT-010 从第三阶段提前，每次启动备份，保留 7 份）
4. 设置页新增"备份"卡片 + 立即备份按钮
5. 把"数据安全铁律"写进 `AGENTS.md`

**建议下一步**：实现**软删除 / 回收站**（OPT-001、OPT-011），让"删除"变成可撤销的操作。

### 反馈 3（2026-09-12）

**用户原话：**

> "编辑待办弹出一个新的窗口，在原部分修改不够突出，让别人不好看清"

**状态**：✅ 已完成（见 OPT-018）

**分析**：用户指出"就地编辑"的可见性问题 —— 数据填回**顶部**表单，
但用户点的是**列表中部的某一条**，视线要跳上去；
而且顶部表单一秒钟前还是"添加待办"的样子，切换不明显，容易让人以为没反应。

### 反馈 4（2026-09-12）

**用户原话：**

> "提示的优先级不高，能不能做成系统级的，不点取消就一直挂在右下角"

**状态**：✅ 已完成（见 OPT-019）

**分析**：用户指的是"提醒提示"。原来的做法是**页面内居中弹窗**，有三个硬伤：
1. 只在浏览器里可见 —— 切到别的软件就看不见了；
2. 居中挡住内容 —— 打断感太强；
3. 浏览器标签页关掉就完全没有提醒。

**方案**：改成**后端直接发 Windows 原生通知**

- XML 里加 `scenario="reminder"` —— **不点掉就不会消失**
- **浏览器关着也能收到**（顺带解决了一直写在文档里的那个限制）

页面内则改为**右下角常驻卡片**（带"标记完成 / 稍后提醒"按钮），不再遮挡内容。

**架构影响**：提醒的主控权从"前端轮询"移交给"后端后台线程" —— 详见 BUG-012 的说明。

### 反馈 5（2026-09-14）

**用户原话：**

> "提醒弹窗能不能设置成关闭浏览器也可以弹出，即有后台运行就可在提醒时间进行系统级别通知"

**状态**：功能**早已实现**（OPT-019，v0.2.0）→ 真正的问题是**文档没说清楚**，已转为 **OPT-023**

**分析**：

这个能力在 v0.2.0 就已经做好了 —— 提醒由**后端守护线程**（每 20 秒扫一次）直接发 Windows 系统通知，
**浏览器从头到尾不参与**。关掉浏览器、关掉整个浏览器进程，都不影响。

那用户为什么又问了一次？因为 **README 里从来没有明确写过这件事**。
README 的提醒一节讲的是"怎么设置提醒时间"，但**没有回答"浏览器关了还响不响"**这个最自然的疑问。

**这条反馈的真正价值**：

> **功能做了，但用户不知道 —— 在用户眼里就等于没做。**

它提醒我们：写文档时不能只写"怎么用"，还要写"**你可能担心的那件事，其实不用担心**"。
用户提问的地方，往往就是文档该补的地方。

**顺带确认的另一点**：用户问"有后台运行就可以吗"—— 这个理解是**对的**。
程序本身（那个黑窗口 / 开机自启起的后台进程）必须活着；浏览器关不关无所谓。

## 四、优先级判断标准

不确定一个优化该不该现在做时，问三个问题：

1. **不做会不会导致数据丢失或安全问题？** → 会，就是**高**优先级（如 OPT-010 备份）
2. **不做会不会挡住后面的功能开发？** → 会，就是**中**优先级（如 OPT-008 渲染方式）
3. **只是"感觉更好"？** → **低**优先级，等框架完整后再统一处理

> 这条标准能帮你避免"过早优化"——新手最常犯的错误之一，
> 就是把大量时间花在打磨一个还没定型的细节上。

## 五、第四阶段（桌面悬浮窗）的遗留问题详解

### OPT-024：从设置页改窗口位置不会立刻生效

**现象**（2026-09-14 实机验证，隔离环境 port 8123）：

```
1) 量窗口矩形:         pos=(310,436)  size=260x340
2) PATCH config {"width":420,"height":300}
3) 等 5 秒再量:        pos=(310,436)  size=420x300      ← ✅ 大小生效了
4) PATCH config {"x":500,"y":260}
5) 等 5 秒再量:        pos=(310,436)  size=420x300      ← ❌ 位置没动
```

**v0.3.1 的复查结果：已经生效了。**

重做界面时把"应用几何"这件事统一到了 `apply_geometry()` 一个函数里，并且
**位置和尺寸各管各的**（不再像原来那样"夹位置时顺手改尺寸、但只改 tkinter 不改设置"）。
复查结果：

```
设置 x=640 y=150 → 等 5 秒 → 窗口矩形 (427,100) 227x293
                  换算回逻辑坐标正好是 (640,150)（本机 150% DPI 缩放）
```

**结论**：功能已经正常。现在"改位置"的延迟上限是**轮询间隔 3 秒**
（窗口每 3 秒问一次设置），这是设计如此，不是 Bug。
窗口自己拖动时是**立即**生效的（那条路径不依赖轮询）。

保留这一段记录的目的：**把"当时卡在哪、后来怎么好的"留下来**。
下次遇到"改了没反应"，可以照这里的排查思路走一遍：

| 怀疑点 | 怎么排除 |
| --- | --- |
| tkinter 不支持无边框窗口程序化改位置 | 写最小 tkinter 脚本验证（`overrideredirect` + `-toolwindow` 下 `geometry("+400+300")` 正常） |
| 位置被"夹回屏幕内"的逻辑吃掉了 | 手算一遍夹取公式，确认没超出 |
| 配置没真的存进去 | `GET /api/floating` 看返回值 |
| 窗口没在跑 | 看 `window.running` 和 `window.pid` |
| 「变化检测」漏了 x / y | 看 `_geometry_changed()` 的字段清单 + 单测 |
| **窗口自己把位置改回去了** | ★ 这次的真凶：拖动防抖会回写 `winfo_x()/winfo_y()`，和外部改位置打架 |


### OPT-025：守护线程需要"失败退避"

**背景**：守护线程每 3 秒检查一次「该不该开窗口」，缺一个"连续失败就放慢"的机制。
BUG-027（令牌没传）就是被它从"一次失败"放大成
「无限重启 + 任务管理器里堆出一串 `pythonw`」的。

**建议做法**：在 `_supervisor_loop()` 里记连续失败次数，
失败 3 次之后把检查间隔从 3 秒退避到 30 秒，并写一条 WARNING 日志
（日志里要带上具体原因，用户一看就知道要做什么）。
连续失败 10 次以上就**停下来**并在设置页显示红点 + 原因。

这类机制在运维领域叫**指数退避（exponential backoff）**，
是所有"自动重试"逻辑的标准配套 —— 重试本身是对的，
但**没有上限的重试会把小问题变成大问题**。

### OPT-026：透明度是「整窗」的，不是「只让背景透明」

**用户的原话**：

> 悬浮窗背景透明度可以更改，默认为黑色 30%透明度，字体为宋体

**后续补充的原话（这一条改变了整件事的处理方式）**：

> 保持字体的高清晰度为排版的最基本前提

**问题**：按字面理解，「背景透明度」听起来应该是"只有背景变透明"。
但实测会发现：**调低透明度时，窗口里的文字、按钮也一起变淡了。**

**为什么？** 因为实现用的是 tkinter 的窗口级属性：

```python
self.root.attributes("-alpha", 0.70)     # 0.0 全透明 ~ 1.0 完全不透明
```

`-alpha` 是 **Windows 的分层窗口（Layered Window）** 机制，
它作用在**整个窗口位图**上 —— 窗口里的每一个像素（包括文字）
都按同一个系数混合。**tkinter 没有提供"逐控件透明度"这个能力。**

**几种可能的做法，以及为什么都没做**：

| 做法 | 能做到吗 | 为什么不做 |
| --- | --- | --- |
| `wm_attributes("-transparentcolor", 某色)` | 只对**一种纯色**透明 | ① 会把同色的文字/图标一起抠掉；② 抗锯齿的边缘留毛边，很脏；③ 只支持一种颜色 |
| 改用 Qt / PyQt | ✅ 完全能做到 | 要引入几十 MB 依赖，与「下载即跑」原则冲突（见 `docs/阶段四-01-桌面悬浮窗.md` 第 1.1 节的选型对比） |
| 自绘 + 自己算混合 | 理论可以 | tkinter 的 Canvas 没有半透明填充支持，等于自己做渲染器，复杂度远超收益 |

**★ 结论（v0.3.3 最终定案）：两个概念分清楚之后，这一条根本不是"冲突"，不用取舍**

后来用户又澄清了一句，把整个问题解开了：

> 字体清晰指的是**字体分辨率保持高**，在任何情况下不能因为模糊像素低而看不清

这句话说明**我把两个不同的量当成一个了**：

| | 是什么 | 由什么决定 | 受透明度影响吗 |
| --- | --- | --- | --- |
| **清晰度**（锐利） | 笔画边缘利不利、糊不糊 | **渲染方式**（DPI 感知） | ❌ **完全不受影响** |
| **对比度**（好不好读） | 字和背景的亮度差 | 半透明混色的比例 | ✅ 会按比例变小 |

**为什么降低透明度不会让字变糊？** 因为 `-alpha` 走的是 Windows 的
**分层窗口**机制：整幅位图按同一个系数和桌面混合，
每个像素只和**自己同一位置**的底色混合 —— **不涉及邻域平均**。
而"模糊"的本质恰恰是邻域平均。所以从数学上它只可能让颜色变淡，不可能变糊。

于是最终的做法是**把两条要求各归各位**：

| 要求 | 落在哪里 | 取值 |
| --- | --- | --- |
| 「字体必须清晰（不模糊）」 | **DPI 感知** | `FLOATING_DPI_AWARE = True`（v0.3.1 已做，见 BUG-030） |
| 「透明度可以调低」 | **不透明度范围** | 默认 **0.70**（= 透明度 30%）、下限 0.30、提醒线 0.60 |

两条要求**不再冲突**，也就不需要"用范围换清晰"那种取舍了。

**★ v0.3.1 那次取舍是白做的 —— 这一段保留下来当教材**

| 项 | v0.3.0 | v0.3.1（基于错误前提） | v0.3.3（澄清后） |
| --- | --- | --- | --- |
| 默认不透明度 | 0.30 | 0.92 | **0.70** |
| 下限 | 0.05 | 0.80 | **0.30** |
| 提醒线 | 无 | 0.85 | **0.60** |

v0.3.1 里我写下了"低于 80% 字就开始明显发虚"这句**错话** ——
依据是"半透明会让字发虚"，而真实原因是**没声明 DPI 感知、被 Windows 拉伸**。
两件事凑在一起发生，我把它们当成了因果。

**教训（比结论重要）**：
1. **遇到两个互相冲突的要求，先问清"这两个词各指什么"，再谈取舍。**
   前提错了，取舍就是白做 —— 而且会写进文档、看起来还很"有道理"。
2. **"现象同时出现"不等于"有因果关系"。**
   "字糊"和"窗口半透明"是同时存在的两件事，但让字糊的是 DPI 拉伸，不是透明度。
   （排查时把每个因素**单独隔离**验证一次，就不会把巧合当因果。）
3. **错误结论要留在文档里并标注"已推翻"**，而不是悄悄删掉 ——
   否则下一个人还会踩同一个坑。

**另外三条"保清晰"措施保留**（它们确实和锐利度有关）：

1. **声明 DPI 感知**（`app/gui/window.py` 的 `enable_dpi_awareness()`）—— 唯一的关键项；
2. **只给整数磅字号** —— 非整数会被 Tk 取整，边缘可能错位半个像素；
3. **不靠"放大字体控件"来缩放** —— 位图放大必然发虚，
   改字体磅值让系统重新渲染才是锐的。
