# 待优化与已知问题清单

> **这个文档是干什么的**
> 记录"功能上想改、但现在先不做"的事情。
>
> **为什么不立刻做？**
> 因为先把整体框架搭完整，比反复打磨某一个细节更重要。
> 很多优化在框架完整后做，成本会低得多（因为能复用的代码更多了）。
>
> **使用约定**
> 1. 编号 `OPT-XXX` 依次递增，只增不改（做完就标记状态，不删记录）；
> 2. 每条要写清楚：**类型 / 描述 / 优先级 / 来源 / 状态**；
> 3. 用户反馈的问题**原话照录**，不要自己"翻译"成技术语言——
>    原始描述往往包含你自己想不到的线索（见 BUG-004 的教训）。

## 二、用户反馈区

> 用户随口提的一句"感觉有点别扭"，往往比开发者自己的清单更有价值。
> 这里**原话照录**，等技术评估后再补上分析。

### 反馈 1（2026-09-12）

**用户原话：**

> "我发现一些功能上的缺陷，你可以先进行下一步操作，完全把框架搭起来后再慢慢优化"

**状态**：✅ 已关闭

**处理说明**：这条反馈的重点**不是某个具体缺陷，而是推进节奏的选择** ——
先把框架搭完整，再回头做优化。

这个决定后来被证明是对的。框架搭好之后，很多原本要单独写一堆代码才能做的优化，
都变成了「在已有结构里改一处」：

| 后来的优化 | 复用了什么 |
| --- | --- |
| 编辑改成弹窗（OPT-018） | 已有的表单与接口 |
| 提醒改成系统级通知（OPT-019） | 已有的扫描线程 |
| 回收站 / 软删除（OPT-001、OPT-011） | 已有的仓储层与页面框架 |

至于具体的功能缺陷，后来在使用过程中陆续被发现并逐条记录了 ——
这正是本清单存在的意义。

### 反馈 2（2026-09-12）

**用户原话：**

> "重新用start.bat启动后新的todo界面没有历史记录"

**状态**：✅ 已定位并修复机制 —— 归档为 **BUG-011**（数据丢失事故）

**根因**：开发者（AI 助手）的临时测试脚本对**真实数据库**执行了"删除全部任务"，
导致用户创建的待办全部丢失。**丢失的数据无法恢复**（当时还没有备份机制）。

**已做的修复**：
1. 危险操作加闸门（`reset_all(confirm=True)`）
2. 统一测试隔离工具（`scripts/_isolation.py`）+ 运行时守卫
3. **立刻实现自动备份**（把 OPT-010 从第三阶段提前，每次启动备份，保留 7 份）
4. 设置页新增"备份"卡片 + 立即备份按钮
5. 把"数据安全铁律"写进 `AGENTS.md`

**建议下一步**：实现**软删除 / 回收站**（OPT-001、OPT-011），让"删除"变成可撤销的操作。

### 反馈 3（2026-09-12）

**用户原话：**

> "编辑待办弹出一个新的窗口，在原部分修改不够突出，让别人不好看清"

**状态**：✅ 已完成（见 OPT-018）

**分析**：用户指出"就地编辑"的可见性问题 —— 数据填回**顶部**表单，
但用户点的是**列表中部的某一条**，视线要跳上去；
而且顶部表单一秒钟前还是"添加待办"的样子，切换不明显，容易让人以为没反应。

**结论**（见下一条反馈的完整处理）：

**结论**：
- **添加**保持内嵌（高频操作，始终可见最顺手）
- **编辑**改成**居中弹窗**（低频、需要专注，弹窗把它从周围信息里"拎出来"）
- 弹窗标题明确写"编辑待办 #N"，并顺手加上**未保存修改提醒**

### 反馈 4（2026-09-12）

**用户原话：**

> "提示的优先级不高，能不能做成系统级的，不点取消就一直挂在右下角"

**状态**：✅ 已完成（见 OPT-019）

**分析**：用户指的是"提醒提示"。原来的做法是**页面内居中弹窗**，有三个硬伤：
1. 只在浏览器里可见 —— 切到别的软件就看不见了；
2. 居中挡住内容 —— 打断感太强；
3. 浏览器标签页关掉就完全没有提醒。

**方案**：改成**后端直接发 Windows 原生通知**
- 系统级，出现在**屏幕右下角**
- XML 里加 `scenario="reminder"` —— **不点掉就不会消失**
- **浏览器关着也能收到**（顺带解决了一直写在文档里的那个限制）

页面内则改为**右下角常驻卡片**（带"标记完成 / 稍后提醒"按钮），不再遮挡内容。

**架构影响**：提醒的主控权从"前端轮询"移交给"后端后台线程" —— 详见 BUG-012 的说明。

### 反馈 5（2026-09-14）

**用户原话：**

> "提醒弹窗能不能设置成关闭浏览器也可以弹出，即有后台运行就可在提醒时间进行系统级别通知"

**状态**：功能**早已实现**（OPT-019，v0.2.0）→ 真正的问题是**文档没说清楚**，已转为 **OPT-023**

**分析**：

这个能力在 v0.2.0 就已经做好了 —— 提醒由**后端守护线程**（每 20 秒扫一次）直接发 Windows 系统通知，
**浏览器从头到尾不参与**。关掉浏览器、关掉整个浏览器进程，都不影响。

那用户为什么又问了一次？因为 **README 里从来没有明确写过这件事**。
README 的提醒一节讲的是"怎么设置提醒时间"，但**没有回答"浏览器关了还响不响"**这个最自然的疑问。

**这条反馈的真正价值**：

> **功能做了，但用户不知道 —— 在用户眼里就等于没做。**

它提醒我们：写文档时不能只写"怎么用"，还要写"**你可能担心的那件事，其实不用担心**"。
用户提问的地方，往往就是文档该补的地方。

**顺带确认的另一点**：用户问"有后台运行就可以吗"—— 这个理解是**对的**。
程序本身（那个黑窗口 / 开机自启起的后台进程）必须活着；浏览器关不关无所谓。

## 四、优先级判断标准

不确定一个优化该不该现在做时，问三个问题：

1. **不做会不会导致数据丢失或安全问题？** → 会，就是**高**优先级（如 OPT-010 备份）
2. **不做会不会挡住后面的功能开发？** → 会，就是**中**优先级（如 OPT-008 渲染方式）
3. **只是"感觉更好"？** → **低**优先级，等框架完整后再统一处理

> 这条标准能帮你避免"过早优化"——新手最常犯的错误之一，
> 就是把大量时间花在打磨一个还没定型的细节上。
