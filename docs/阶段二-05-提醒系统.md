## 一、设计思路（以下为最初实现的设计说明）

### 1.1 ★ 一个重要的设计演进：不需要后台线程

原设计写的是"后端起一个线程，每 20 秒扫描一次并标记已提醒"。实现时重新推演，发现它会**丢提醒**：

| 方案 | 浏览器没开时会怎样 |
| --- | --- |
| 后端线程扫描并标记 | 时间到了 → 线程把 reminded_at 写上 → **但没人看见** → 你打开浏览器时它已经不弹了 → **提醒永久丢失** ❌ |
| **前端轮询，接口内扫描+标记** | 没人轮询 → 提醒**保持未标记状态** → 重新打开时补弹 ✅ |

**核心洞察：`reminded_at` 应该在"用户真的看到"时才写入，而不是"时间到了"就写入。**

这样"不漏提醒"是**自动成立**的 —— 因为没被看到的提醒永远不会被消费掉。
顺带还少了一个线程、少了一类并发 Bug、少一个需要关闭时才退出的东西。

> **这是一条通用的设计经验：**
> 加一个组件之前，先问"不加它会怎样"。
> **每多一个后台线程，就多一类"关不干净、抢资源、偶发卡死"的问题。**
> 能用"请求驱动"解决的，就不要用"定时驱动"。

### 1.2 "扫描"和"消费"必须放在同一个函数里

如果分成两步 —— 先查询返回给前端，前端显示完再回来调接口标记 —— 会出问题：

```
第 1 次轮询：查到提醒 A，返回给它  ─┐
                                 │ 这中间 A 还没被标记
第 2 次轮询：又查到提醒 A！      ─┘  -> 同一条提醒被弹两次
```

放在一起就是**原子操作**：取走的同时就消费掉。
代价是"万一响应丢失，这条提醒就没了" —— 但对本机访问来说这个概率极低，
**用它换来的"绝不重复弹"是值得的**。

### 1.3 三层提醒，覆盖不同场景

| 层 | 作用 | 什么时候能看到 |
| --- | --- | --- |
| **页面内弹窗** | 主要提醒，带三个操作按钮 | 页面打开时 |
| **系统通知**（Notification API） | 切到别的软件也能看到 | 授权后始终可见 |
| **提示音** | 听觉提醒 | 页面打开且音频未被浏览器拦截时 |

三层叠加，是因为**单靠任何一层都有盲区**：
只看弹窗，切走就看不见；只看通知，容易被忽略；只看声音，静音就没了。

### 1.4 提示音用 Web Audio 现场合成，不用音频文件

传统做法是放一个 `remind.mp3`。本项目的做法是**用代码合成两个音**：

- **省掉二进制资源**：项目更轻，Git 仓库更小，也不会出现"音频文件加载失败"；
- **完全离线可用**：不依赖任何外部文件；
- **想换音色只改两个数字**（频率）。

### 1.5 批量上限：一次最多弹 5 个

想象你关了三天电脑，一打开：**23 条提醒同时弹出** —— 浏览器直接卡住，你也看不过来。

所以加了一个上限（`REMINDER_MAX_BATCH = 5`）。关键是：

> **超出的部分不会被标记，所以下一轮轮询会继续返回它们。**
> **批量上限只影响"一次弹几个"，绝不影响"会不会漏"。**

### 1.6 "稍后提醒"要用"当前时间 + N"，不能用"原提醒时间 + N"

| 算法 | 场景：8:00 的提醒，你 10:00 才点"稍后 10 分钟" | 结果 |
| --- | --- | --- |
| 原提醒时间 + 10 分钟 | 8:00 + 10 = **8:10** | 已经是过去时间 → **立刻又弹一次** ❌ |
| **当前时间 + 10 分钟** | 10:00 + 10 = **10:10** | 符合直觉："从现在起再过 10 分钟提醒我" ✅ |

### 2.2 服务层核心（`fetch_due`）

    def fetch_due(limit=None):
        """取出所有"到点该提醒"的任务，并立刻标记为已提醒，然后返回它们。"""
        if limit is None:
            limit = config.REMINDER_MAX_BATCH

        tasks = task_repo.due_for_reminder()

        # 截断：一次最多弹 limit 条。
        # 超出的部分【不标记】，下一轮轮询会继续返回它们。
        batch = tasks[:limit]

        now = timeutil.now_str()
        for task in batch:
            task_repo.mark_reminded(task.id, now)

        return batch

### 2.3 前端轮询（`reminder.js`）

    async function poll() {
      if (checking) return;      // 上一次还没回来就跳过，避免请求堆积
      checking = true;
      try {
        const tasks = await api.dueReminders();
        if (tasks && tasks.length) {
          tasks.forEach(function (t) { queue.push(t); });
          if (!current) show(queue.shift());
          else updateQueueLabel();
        }
      } catch (err) {
        // 【静默失败】提醒轮询不该因为一次网络抖动就弹错误框打扰用户
      } finally {
        checking = false;
      }
    }

    poll();                          // 立刻查一次（处理"关机期间到点的提醒"）
    setInterval(poll, POLL_MS);      // 之后每 20 秒一次

### 2.4 提示音合成（不需要音频文件）

    function playChime() {
      const ctx = getAudioContext();
      if (!ctx) return;
      const start = ctx.currentTime;
      // 两个音符：[频率(Hz), 起始延迟(秒)]   880=A5, 1174.66=D6
      const notes = [[880, 0], [1174.66, 0.18]];
      notes.forEach(function (note) {
        const osc = ctx.createOscillator();
        const gain = ctx.createGain();
        osc.type = "sine";
        osc.frequency.value = note[0];
        // 音量包络：快速淡入、缓慢淡出，听起来才像"叮"而不是"啪"
        gain.gain.setValueAtTime(0.0001, start + note[1]);
        gain.gain.exponentialRampToValueAtTime(0.22, start + note[1] + 0.02);
        gain.gain.exponentialRampToValueAtTime(0.0001, start + note[1] + 0.45);
        osc.connect(gain);
        gain.connect(ctx.destination);
        osc.start(start + note[1]);
        osc.stop(start + note[1] + 0.5);
      });
    }

### 2.5 顺手修复：退出时合并 WAL 日志

开发过程中注意到 `data/todo.db-wal` 涨到了 **1.1 MB**（见文件清单），于是补了一处：

    # app/main.py 的 lifespan 里
    yield
    # ---- yield 之后是"服务关闭时"要执行的代码 ----
    database.checkpoint_wal()

    # app/database.py
    def checkpoint_wal():
        """把 WAL 日志里的内容合并回主数据库文件，并清空 WAL。"""
        with engine.connect() as conn:
            conn.execute(text("PRAGMA wal_checkpoint(TRUNCATE)"))

**为什么需要它？** 我们用了 WAL 模式（功能 2 讲的），写操作先落进 `todo.db-wal`，
之后再慢慢合并回 `todo.db`。SQLite 会在合适的时候自动合并，
但如果**强制结束进程**（关黑窗口、任务管理器结束进程），自动合并就来不及做。

它**不会丢数据**（下次打开时 SQLite 会自动恢复），但会让 `data/` 里躺着一个大文件。

**实测效果**：

    合并前 todo.db-wal: 1,116,552 字节
    合并后 todo.db-wal: 0 字节
    主数据库 todo.db  : 28,672 字节（数据完好）

> 这是一个典型的"**不影响功能但不干净**"的问题。
> 记入待优化清单当然也可以，但它只有 3 行代码 —— **顺手做掉比记下来更省事。**
> 判断标准：**修复成本低于"记录 + 以后重新理解上下文"的成本时，就顺手修。**

## 三、关键代码逐行解释

### 3.1 `due_for_reminder()` 的四个条件（在功能 2 就写好了）

| 条件 | 少了会怎样 |
| --- | --- |
| `remind_enabled == 1` | 用户关掉了提醒却被弹窗骚扰 |
| `status == "todo"` | 做完的事还弹出来提醒你 |
| `remind_at <= now` | 未来的任务提前弹 |
| **`reminded_at IS NULL`** | **同一条提醒每 20 秒弹一次，直到你崩溃** |

### 3.2 `checking` 标志位：防止请求堆积

    if (checking) return;
    checking = true;
    ...
    finally { checking = false; }

如果后端响应变慢（比如数据库被锁住 3 秒），而轮询间隔只有 20 秒 —— 看起来没问题。
但如果网络卡了 30 秒，就会有**第二个请求发出去**，然后第三个……
最后同时有 10 个请求在飞，服务器压力瞬间放大。

这叫**请求堆积**，是轮询类功能最常见的坑。一个布尔标志位就能解决。

### 3.3 静默失败：为什么轮询出错不弹提示

    } catch (err) {
      // 静默失败
    }

**这是故意的。** 理由：

1. 轮询每 20 秒一次，如果每次失败都弹错误框，**用户会被错误提示淹没**；
2. 下一轮会自动重试，绝大多数抖动会自愈；
3. 提醒是"锦上添花"的功能，**它出问题不应该妨碍用户管理待办**。

> **判断标准**：错误的严重程度要和提示的打扰程度匹配。
> 会丢数据的错误要**大声报**；后台轮询的小抖动要**安静重试**。

### 3.4 `visibilitychange`：解决后台标签页降频

    document.addEventListener("visibilitychange", function () {
      if (!document.hidden) poll();
    });

**浏览器的节能机制**：标签页切到后台时，`setInterval` 会被降频到大约**每分钟一次**。
这意味着如果页面在后台，提醒可能延迟最多 1 分钟才弹。

解决办法：监听"标签页重新可见"事件，**切回来的一瞬间立刻检查一次**。
实际体验上完全没有等待感 —— 你切回页面，提醒就在那里。

> 彻底解决需要 **SSE / WebSocket** 推送（服务器主动推，不受降频影响），
> 已记入待优化清单 OPT-016，第三阶段可以考虑。

### 3.5 `exponentialRampToValueAtTime`：为什么不是直接设音量

    gain.gain.setValueAtTime(0.0001, start);
    gain.gain.exponentialRampToValueAtTime(0.22, start + 0.02);   // 20ms 淡入
    gain.gain.exponentialRampToValueAtTime(0.0001, start + 0.45); // 450ms 淡出

如果直接把音量设为 0.22 再设为 0，声音会"**啪**"的一下爆开又突然消失 ——
这在音频里叫**爆音（click/pop）**，听起来很廉价。

**音量包络**（快速淡入 + 缓慢淡出）让声音变成"**叮**"，这是所有提示音的标准做法。

另外注意用的是 `exponentialRampToValueAtTime`（指数变化）而不是线性变化 ——
因为**人耳对音量的感知是对数的**，指数变化听起来才自然。

> ⚠️ 指数渐变有个限制：**目标值不能是 0**（数学上指数永远到不了 0）。
> 所以代码里用的是 `0.0001` 而不是 `0` —— 这是个必须知道的小陷阱。

### 3.6 跨文件通信：自定义事件

提醒弹窗里点了"标记完成"，**列表应该立刻刷新**。但 `reminder.js` 和 `list.js` 是两个独立文件，
直接互相调用会让它们**互相依赖**。

本项目的做法是**发事件**：

    // reminder.js：发消息的人不知道谁在听
    window.dispatchEvent(new CustomEvent("tasks:changed"));

    // list.js：听的人不知道谁发的
    window.addEventListener("tasks:changed", loadTasks);

**这叫"解耦"。** 好处是以后要加第三个听众（比如日历页也要刷新），
**完全不用改 `reminder.js`**。

### 3.7 AudioContext 的"解锁"

    document.addEventListener("click", unlockAudio);   // 用户一点页面就"解锁"

浏览器有**自动播放策略**：页面没有被用户交互过时，音频上下文处于 `suspended` 状态，
直接播放会被静默阻止（不报错，就是没声音）。

解决办法：**在用户第一次点击页面时创建/恢复音频上下文**。
因为用户用这个程序时必然点过"添加"，所以正常情况下提示音都能响。

## 四、如何运行

### 4.1 启动

**双击 `start.bat`**，浏览器打开待办页面。

### 4.2 第一次使用：开启系统通知

页面**底部的提醒设置条**会显示"系统通知：未开启"，点旁边的"开启系统通知"按钮，
浏览器会弹出授权请求，选"允许"。

> **注意**：浏览器要求"由用户点击触发"才允许申请通知权限，
> 所以没法在页面加载时自动申请 —— 这是浏览器的安全设计，不是 Bug。

### 4.3 立刻看到提醒效果（不用等）

正常创建一个提醒最少也要等 1 分钟，调试太慢。所以做了一个测试工具：

    python scripts/test_reminder.py

它会往数据库里写一条"提醒时间已经过去 1 分钟"的任务，然后：

> **切到浏览器，最多等 20 秒（或者按 F5 刷新一下），弹窗就会出来。**

其他命令：

| 命令 | 作用 |
| --- | --- |
| `python scripts/test_reminder.py` | 造一条立刻该弹的提醒 |
| `python scripts/test_reminder.py --list` | 看看当前有哪些待提醒的任务 |
| `python scripts/test_reminder.py --clear` | 删掉测试数据 |

### 4.4 正常使用方式

在"添加待办"表单里填上**提醒时间**（提醒开关会自动打开），到点了就会弹窗。

    GET   /api/reminders/stats
    POST  /api/reminders/{task_id}/snooze

可以手动调 `/api/reminders/due` 观察：**第一次调用返回数据，第二次调用返回空数组** ——
这就是"消费式读取"最直观的证明。

## 六、常见问题排查

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 弹窗一直不出现 | 提醒时间还没到，或 `remind_enabled` 是 0 | 用 `test_reminder.py --list` 看那条任务的提醒时间和开关状态 |
| 没有声音 | 浏览器自动播放策略拦住了 | **先在页面上随便点一下**（比如点标题输入框），再测一次 |
| 没有系统通知 | 没授权，或浏览器不支持 | 看底部提醒条的状态；点"开启系统通知" |
| 系统通知按钮点了没反应 | 已经被拒绝过，浏览器不再弹询问 | 点地址栏左侧的锁/信息图标 → 通知 → 允许 → 刷新页面 |
| 提醒重复弹了 | 说明"扫描"和"标记"被拆成了两步 | 检查 `fetch_due()` 是否在同一个函数里完成两件事（见 1.2） |
| 关了程序期间到点的提醒，打开后没弹 | 检查是不是被标记过了 | `test_reminder.py --list` 看 `reminded_at` 是否为空（正常应该为空） |
| 后台标签页延迟很久才弹 | 浏览器对后台定时器降频 | **正常现象**（最多约 1 分钟）；切回标签页会立刻检查（见 3.4） |
| 一次弹出几十个窗口 | 批量上限没生效 | 检查 `config.REMINDER_MAX_BATCH` |
| 点"稍后提醒"后立刻又弹 | 用了"原提醒时间 + N"而不是"当前时间 + N" | 见 1.6 |
