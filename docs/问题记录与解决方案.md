## BUG-001：双击 start.bat 窗口一闪而过

- **日期**：2026-09-12
- **所属阶段**：第二阶段 · 功能 1（环境搭建与第一个网页）
- **涉及文件**：`start.bat`
- **状态**：✅ 已修复

> 这是本项目**真实踩过的第一个坑**。请重点看**排查的思路**，而不是结论——
> 因为以后你会遇到无数个没见过的 Bug，结论帮不了你，思路才能。

### 1.1 症状

双击 `start.bat`，黑窗口闪一下就消失，什么提示都来不及看清。

### 1.2 复现

新手最常见的反应是"我觉得可能是 Python 没装好"然后开始乱改。
正确做法是：**让同样的命令在一个"窗口不会关掉"的地方跑一次，把报错抓出来。**

在 PowerShell 里执行（`cmd /c` 表示用命令解释器跑这个脚本）：

    cmd /c "start.bat"

### 1.3 报错原文

    '??动' is not recognized as an internal or external command,
    operable program or batch file.
    '服务已停止。按任意键关闭窗口。' is not recognized as an internal or external command,
    operable program or batch file.

这两行信息量很大：

1. 报错说"某段文字不是内部或外部命令"——说明 **cmd 把中文提示语当成了命令名去执行**。
2. 而它本来应该是 `echo 正在启动...`，也就是 **`echo` 这个词丢了**。

一个 `echo` 凭空消失，这就不是"写错字"能解释的，而是**cmd 读文件的方式出了问题**。

### 1.4 根因分析：两个原因叠加

#### 原因一（致命）：行尾必须是 CRLF

| 换行符 | 字节 | 谁在用 |
| --- | --- | --- |
| `LF` | `0x0A` | Linux / macOS / 现代编辑器**默认** |
| `CRLF` | `0x0D 0x0A` | Windows 传统格式 |

最初生成 `start.bat` 时用的是 LF（实测：**0 个 CRLF，10 个孤立 LF**）。

而 `cmd.exe` 解析批处理文件时，是**按字节偏移量去读、并默认行尾为 CRLF** 的。
遇到 LF 就会"读串位"——本该属于下一行的 `echo` 被算进了上一行，
于是剩下的中文就被当成命令去执行 → 报错 → 脚本中断 → 窗口关闭。

> **关键知识点**：为什么 Python / HTML / JS 用 LF 完全没事？
> 因为它们的解释器**读完整个文件再解析**，不依赖固定字节位置。
> **只有 `.bat` / `.cmd` / `.vbs` 这类老式批处理对行尾极度敏感。**

自查命令（数一数到底有几个 CRLF、几个孤立 LF）：

    $b = [System.IO.File]::ReadAllBytes("start.bat")
    "CRLF 个数: " + ([regex]::Matches([System.Text.Encoding]::ASCII.GetString($b), "`r`n")).Count
    "LF  总数: " + ($b | Where-Object { $_ -eq 10 }).Count

#### 原因二（加重）：.bat 文件里写了中文

当时命令行的活动代码页是 **936（GBK 中文编码）**，而文件是 **UTF-8**。
同一个汉字两种编码的字节解读完全不同，`正在启动` 被读成了 `??动`，
进一步加剧了行解析错位。

### 1.5 修复方案

| 问题 | 修复 |
| --- | --- |
| 行尾 LF | 把 `start.bat` 转成 **CRLF** |
| 文件含中文（UTF-8 与 GBK 冲突） | **`start.bat` 改为纯 ASCII（英文）**，所有中文提示交给 Python 打印——Python 处理编码可靠得多 |
| 出错时窗口直接关掉、看不到原因 | 每个错误分支都加 `pause`，让窗口停住等你按键 |
| 没装 Python 或装错位置时一片空白 | 启动前检测 `python`，找不到就退回 `py` 启动器；都没有则给出人话提示和下载地址 |

另外加的两行保险（配合 `chcp 65001` 保证黑窗口里中文不乱码）：

    set PYTHONUTF8=1
    set PYTHONIOENCODING=utf-8

修复后的完整 `start.bat` 见《阶段二 · 功能1》文档 2.8 节。

### 1.6 验证

**① 字节级检查**（必须三项全部达标）：

    字节数        : 1008
    CRLF 行数     : 42
    孤立 LF 行数  : 0    <- 必须为 0
    非 ASCII 字节 : 0    <- 必须为 0
    结论: OK 可以双击运行

**② 用同一条复现命令再跑一次**：

    cmd /c "start.bat > _out.txt 2>&1"

输出应为：

      Starting Offline Todo List ...

    INFO:     Started server process [36244]
    INFO:     Application startup complete.
    INFO:     Uvicorn running on http://127.0.0.1:8000 (Press CTRL+C to quit)
    ========================================================
      离线待办清单  v0.1.0
    ========================================================
      主界面  : http://127.0.0.1:8000
      接口文档: http://127.0.0.1:8000/docs   <- 可以直接在网页上调试接口
      数据文件: <项目绝对路径>\data\todo.db
      按 Ctrl + C 停止服务
    ========================================================

**③ 服务可用性**：浏览器访问 `http://127.0.0.1:8000/api/health` 返回 **200**。

### 1.7 经验

1. **复现 > 猜测。** 闪退时第一件事是到不会关的终端里跑同一条命令，把报错抓全。
2. **报错里的"奇怪字符"是线索。** `??动` 这种半截中文，直接指向"编码不对"，不用瞎试。
3. **文件格式也是代码的一部分。** 行尾、编码、BOM 这些看不见的东西，同样能让程序崩掉。
4. **让错误"可见"。** 所有可能失败的脚本，结尾都要有 `pause`，否则你永远看不到原因。
5. **不要让一种语言替另一种语言处理编码。** 批处理文件里别写中文；中文交给 Python 打印。
6. **修完必须用同一条命令再验一次。** 没验证过的修复，等于没修。

### 1.8 推广：以后写 .bat 文件的检查清单

- [ ] 行尾是 CRLF（不是 LF）
- [ ] 文件内容纯 ASCII，不含中文
- [ ] 开头有 `chcp 65001 >nul`（让 Python 的中文能正常显示）
- [ ] 有 `cd /d "%~dp0"`（保证工作目录是脚本所在目录）
- [ ] 每个错误分支都有 `pause`
- [ ] 结尾有 `pause`

## BUG-002：Markdown 文档里残留转义符，Word 显示错乱

- **日期**：2026-09-12
- **所属阶段**：第一阶段（设计文档）收尾
- **涉及文件**：`docs/阶段一-项目设计.md`
- **状态**：✅ 已修复

### 2.1 症状

用 `scripts/md2docx.py` 生成 Word 后，正文里出现「反斜杠 + 反引号」这样的怪字符，
本该显示成"代码样式"的内容变成了普通文字。

### 2.2 复现

生成文档后检查源文件，发现其中有 **26 处**「反斜杠紧跟着反引号」。

### 2.3 报错原文

没有报错。**属于"静默错误"——程序不报错，但结果不对**，这类问题最容易被忽略。

### 2.4 根因分析

这是一次**工具链自身的转义问题**：
生成 Markdown 的那段程序本身用"反引号包裹的字符串"来书写，
在那种语法里，反引号必须写成转义形式；而当时使用的另一种字符串语法**不会消解转义**，
于是转义用的反斜杠被原样写进了文件。

一句话：**"我用来生成文件的工具"和"文件内容要求的转义规则"不是同一套。**

### 2.5 修复方案

写一个一次性修正脚本，把「反斜杠 + 反引号」替换成单独的反引号，然后重新生成 Word：

    text = md.read_text(encoding="utf-8")
    text = text.replace("\\" + chr(96), chr(96))
    md.write_text(text, encoding="utf-8")

同时**修改了后续文档的生成方式**，从根源上不再产生这种转义（第二阶段文档复查残留为 0 处）。

### 2.6 验证

    Markdown 行数: 520   字符数: 15951
    反引号数量: 160   (成对出现)
    残留转义（反斜杠 + 反引号） : 0
    Word: 211 段落 / 15 表格 / 51.8 KB

### 2.7 经验

1. **不报错 ≠ 没问题。** 文档类产出一律要"打开看一眼"，不能只看程序 exit code 是 0。
2. **给产出物加自检。** 现在是靠肉眼发现；更好的做法是写进校验脚本（本项目已有 `scripts/smoke_test.py`）。
3. **工具的转义规则要看清楚。** 生成代码的工具本身也有转义层，两层混淆就会互相污染。

## BUG-003：文档里写错了日期

- **日期**：2026-09-12
- **所属阶段**：第二阶段 · 功能 2（数据库与数据表）
- **涉及文件**：`docs/` 下的三份 Markdown 文档
- **状态**：✅ 已修复

### 3.1 症状

三份文档的页眉和变更记录里都写着"2026-02-14"，但今天其实是 2026-09-12。
文档看起来一切正常，**没有任何报错**。

### 3.2 复现

    Get-Date -Format "yyyy-MM-dd"
    # 输出：2026-09-12   <- 与文档里写的日期对不上

### 3.3 报错原文

**没有报错。** 这又是一次典型的**静默错误**：
程序照跑不误，但产出物的可信度被悄悄破坏了。
（对比 BUG-002：同样是"不报错但结果是错的"，这类问题最容易被忽略。）

### 3.4 根因分析

两个层次的错误：

1. **直接原因**：生成文档时**凭印象**写了一个日期，而不是**先执行命令查询系统日期**。
   记忆是不可靠的信息源，机器输出才是。
2. **深层原因**：同一个日期被**手写**到了 3 个文件、4 个地方（页眉、索引表、变更记录）。
   只要有一处写错，就会跟着复制扩散——**"重复的手写信息"本身就是隐患**。

### 3.5 修复方案

1. 先执行 `Get-Date` 拿到真实日期，再用脚本统一替换三份文档里的错误日期；
2. 定下规矩：**以后凡是需要日期的文档，一律先查命令，绝不凭印象写**。

### 3.6 验证

    Get-Date -Format "yyyy-MM-dd"    ->  2026-09-12
    三份文档中的日期            ->  2026-09-12   （已一致）

### 3.7 经验

1. **凡是机器能准确告诉你的信息，就不要凭记忆写。** 日期、版本号、路径、IP 都属于这类。
2. **同一信息写在多处 = 多处会一起出错。** 能引用就别复制；必须复制时，改一处就要全局搜索一遍。
3. **"不报错的错误"最危险。** 每次产出文档后，都应该像看代码一样**真的打开看一眼**。
4. **记录错误不丢人，掩盖错误才丢人。** 这条本身也值得写进日志——它提醒你以后抽查产出物。

## BUG-004：用户找不到 scripts 文件夹（命令 vs 路径的认知差）

- **日期**：2026-09-12
- **所属阶段**：第二阶段 · 功能 2（数据库与数据表）
- **涉及文件**：`docs/阶段二-02-数据库与数据表.md`、新增 `check.bat`
- **状态**：✅ 已修复

> 这条不是程序 Bug，而是**易用性缺陷**——而且比程序 Bug 更值得记录，
> 因为"代码没错但用户不会用"，一样等于项目失败。

### 4.1 症状

用户反馈："python scripts 在项目文件夹里吗，我没有搜索到。"

### 4.2 复现与核实

先用命令核实文件到底在不在：

    Get-ChildItem "<项目绝对路径>\scripts"
    # 结果：check_repo.py / demo_db.py / md2docx.py / smoke_test.py —— 四个文件都在

再全盘搜索，确认**没有第二份副本**会造成混淆：

    Get-ChildItem -Path C:\, E:\ -Filter "demo_db.py" -Recurse -File
    # 结果：只有一条，就是项目里那份

**结论：文件确实在，程序没问题。问题出在"怎么表达"上。**

### 4.3 根因分析

用户把 **命令** 当成了 **文件路径**。

    python scripts/demo_db.py
    └────┬─┘ └────────┬────────┘
      程序名        参数（指向一个文件）

因此在资源管理器里搜索 `python scripts` 永远搜不到——**因为它根本不是一个文件名**。

更深一层的原因，是我写文档时默认了一个前提：
**"读者知道要在项目根目录下敲命令"**。而对第一次做项目的人来说，
"什么是命令行""当前目录是什么意思""相对路径相对谁"这些**从来没被教过**。

> **教训：文档里每一步操作，都要交代"在哪里做"。**
> 只说"运行 xxx 命令"，等于默认读者已经有背景知识——这是技术文档最常见的毛病。

### 4.4 修复方案

1. **教程文档新增 4.0 节《命令要在哪个文件夹里敲？》**：
   - 把命令拆成"程序名 + 参数"图解，说明为什么搜不到；
   - 解释"相对路径相对于你当前所在的文件夹"；
   - 给出**三种打开命令行的方法**（含"点击地址栏输入 cmd"这个实用技巧）；
   - 教一个自查方法：敲 `dir` 应该能看到 `app`、`scripts`、`run.py` 才算位置对。
2. **新增 `check.bat`（双击版）**：彻底绕开命令行。
   双击 → 自动跑 34 项自检 + 列出数据库内容 → 停住等按键。
3. **排查表新增两行**：`can't open file 'scripts/...'` 和"搜不到 scripts"。
4. 把"要交代操作在哪里进行"写进项目约定（AGENTS.md）。

### 4.5 验证

    cmd /c "check.bat > _chk.txt 2>&1"

结果：输出 84 行，包含 `通过 34 项`，**没有** `not recognized` 等报错。
字节检查：1447 字节 / CRLF=53 / 孤立LF=0 / 非ASCII=0（符合 BUG-001 定下的铁律）。

### 4.6 经验

1. **"能跑"和"用户会用"是两件事。** 只测程序不测文档，项目依然会卡住人。
2. **凡是要求用户敲命令的地方，都要交代"在哪里敲"。** 路径、目录、前置条件，一个都不能省。
3. **给初学者尽量提供"双击入口"。** 一个 .bat 文件能消灭一整类困惑。
4. **同一个知识点讲三遍不丢人**：拆解原理 + 三种方法 + 一个自查手段。

## BUG-006：路由顺序错误，`/stats` 被 `/{task_id}` 抢先匹配

- **日期**：2026-09-12
- **所属阶段**：第二阶段 · 功能 4（完整任务管理）
- **涉及文件**：`app/routers/tasks.py`
- **状态**：✅ 已修复

> **这条特别值得记录：我在自己的文档里专门警告过这个坑，结果实现时还是踩了。**
> 说明"知道"和"做到"之间还有距离——**只有踩过并记录过的坑，才真正变成你的**。

### 6.1 症状

新增"按 id 查询"接口 `GET /api/tasks/{task_id}` 之后，
原本正常的 `GET /api/tasks/stats` **突然开始报 422**。

### 6.2 复现

    GET /api/tasks        -> 200
    GET /api/tasks/stats  -> 422

### 6.3 报错原文

    {"detail":[{
       "type":"int_parsing",
       "loc":["path","task_id"],
       "msg":"Input should be a valid integer, unable to parse string as an integer",
       "input":"stats"
     }]}

**关键线索在 `"input":"stats"`** —— 后端把我请求里的 `stats` 当成了一个 `task_id` 的值。

### 6.4 根因分析

FastAPI（以及几乎所有 Web 框架）匹配路由是**按定义顺序、自上而下**进行的，
**先匹配上的先用**。

当时文件里的顺序是：

    @router.get("/{task_id}")     <- 第 65 行，先被匹配
    ...
    @router.get("/stats")         <- 第 138 行，永远轮不到

访问 `/api/tasks/stats` 时：

1. 框架从上往下扫，先遇到 `/{task_id}` 这个**动态路由**；
2. `stats` 符合"任意字符串"的模式，**匹配成功**；
3. 框架尝试按声明把 `"stats"` 转成 `int`（因为函数签名是 `task_id: int`）；
4. 转换失败 → 直接返回 **422**，**根本不会继续往下找 `/stats`**。

> `/stats` 这个路由**就像不存在一样**。

### 6.5 修复方案

把**所有固定字符串的路由**移到**动态路由之前**：

    @router.get("/stats")         <- 先定义
    ...
    @router.get("/{task_id}")     <- 后定义

并在文件里加了一段醒目注释，防止以后再加接口时又写反。

**通用规则：静态路径永远写在动态路径前面。**

### 6.6 验证

    GET /api/tasks/stats  -> 200  {'total': 2, 'todo': 2, 'done': 0}
    >>> 不再被当成 task_id，修复成功

### 6.7 经验

1. **框架的路由匹配是有顺序的，不是"最精确优先"。** 这一点和很多人的直觉相反。
2. **报错里的 `input` 字段是金线索。** 看到 `"input":"stats"` 就该立刻反应过来"它被当成参数了"。
3. **加新路由时要检查顺序。** 只要项目里存在 `/{id}` 这类动态路由，每次加静态路由都要想一想放哪。
4. **写了警告不等于不会犯。** 我在文档里写过这个坑，实现时照样踩了。
   **所以要有"防呆机制"**（比如把动态路由集中放到文件最后），而不能只靠记性。

## BUG-007：类定义顺序错误，服务直接起不来

- **日期**：2026-09-12
- **所属阶段**：第二阶段 · 功能 4（完整任务管理）
- **涉及文件**：`app/services/task_service.py`
- **状态**：✅ 已修复

### 7.1 症状

想给服务层加一个"找不到数据"的异常类，编辑完之后**整个服务启动失败**，
浏览器直接无法访问。

### 7.2 复现

    python -m uvicorn app.main:app

### 7.3 报错原文

    File "app\services\task_service.py", line 25, in <module>
        class NotFoundError(BusinessError):
                            ^^^^^^^^^^^^^
    NameError: name 'BusinessError' is not defined

### 7.4 根因分析

我想表达的是"NotFoundError 继承 BusinessError"，
但**插入代码时把子类写到了父类的前面**：

    class NotFoundError(BusinessError):   <- 第 25 行，此时 BusinessError 还不存在
        pass

    class BusinessError(ValueError):      <- 第 32 行，太晚了
        pass

**Python 是自上而下逐行执行的。** 执行到第 25 行的 `class` 语句时，
它需要立刻去找 `BusinessError` 这个名字来建立继承关系 —— 但那时它还没被定义，于是 `NameError`。

> 这一点和 Java / C# 等编译型语言不同：那些语言里"类"是整体编译的，
> 顺序无关紧要；**而 Python 的 `class` 语句是一个"运行时执行的动作"**，
> 父类必须先存在于命名空间里。

### 7.5 修复方案

调换顺序，让父类先定义：

    class BusinessError(ValueError):
        pass

    class NotFoundError(BusinessError):
        """要操作的数据不存在。"""
        pass

并在子类上方加注释，写明"必须定义在父类之后"。

### 7.6 验证

    python -c "from app.services import task_service; print(task_service.NotFoundError.__mro__)"
    -> (<class 'NotFoundError'>, <class 'BusinessError'>, <class 'ValueError'>, ...)

继承链正确，服务正常启动。

### 7.7 经验

1. **Python 里"定义顺序"是有意义的。** 不光是类，变量、函数也都一样：
   必须先定义后使用（函数内部调用可以例外，因为调用发生在运行时）。
2. **`NameError` 几乎总是"顺序问题"或"拼写问题"**，先查这两个，别急着怀疑环境。
3. **一次只改一个地方。** 这次我同时改了两处代码（服务层加异常类 + 路由层加接口），
   结果第一步就崩了，反而多花了一轮排查。
   **改完一处就验证一次，是最高效的做法。**

## BUG-008：残留死代码 —— 被自动交叉检查抓出来

- **日期**：2026-09-12
- **所属阶段**：第二阶段 · 功能 9（提醒系统）
- **涉及文件**：`app/static/js/health.js`
- **状态**：✅ 已修复（**由自动化检查发现，不是靠人眼**）

### 8.1 症状

页面运行**完全正常**，没有任何报错。
但在做提醒功能的验证时，我顺手写了一个"交叉检查"脚本，结果它报了警：

    HTML 里定义的 id 数量: 34
      [通过] list.js        引用的 19 个 id 全部存在
      [通过] reminder.js    引用的 10 个 id 全部存在
      [失败] health.js      缺少: ['btn-check', 'health-output']

### 8.2 复现

把 HTML 里所有 id 抓成一个集合，再把每个 JS 文件里 getElementById 引用的 id 抓成集合，**求差集**：

    差集为空  -> 所有 JS 需要的元素页面都有，没问题
    差集非空  -> JS 引用了页面上不存在的元素

这是一个 10 行就能写完的脚本，但它能查出人眼几乎不可能发现的问题。

### 8.3 报错原文

**没有报错。** 又是一次静默问题。

原因是我在 health.js 里写了判空保护（`if (output) ...`），
它挡住了异常，所以程序不崩 —— **但从代码质量角度看，这仍然是问题**。

### 8.4 根因分析

历史遗留。项目经历过一次结构变化：

| 阶段 | 页面形态 | health-output / btn-check |
| --- | --- | --- |
| 功能 1 | 首页是一个"自检页"，有输出框和"重新检测"按钮 | ✅ 存在 |
| 功能 3 | 首页改成了真正的待办界面，自检功能缩成底部四个小圆点 | ❌ 不再存在 |

改版时我更新了 index.html 和渲染逻辑，**但没有回头清理 health.js 里已经不用的代码**。

**这类问题的本质：删掉一个功能时，忘了删"依赖这个功能"的代码。**

它的危害不像崩溃那么明显，但会：

1. 让后来的人（包括几个月后的你）以为"页面上应该有个输出框"；
2. 让判空保护变成一种"到处都是"的习惯，从而**掩盖真正的错误**；
3. 让代码越积越多，清理的时候无从下手。

### 8.5 修复方案

把 health.js 里所有和 health-output / btn-check 相关的代码删掉，
只保留"四色状态圆点"这一件事。

同时**把失败时的信息输出到浏览器控制台**，而不是硬塞进一个不存在的 DOM 元素：

    } catch (err) {
      if (window.console && console.warn) {
        console.warn('[health] 后端检测失败：' + err.message);
      }
    }

这样既消除了死代码，又保留了排查能力（F12 → Console 就能看到）。

### 8.6 验证

    JS 文件          引用 id 数    结果
    ------------------------------------------------------------
    api.js         0          [通过]
    health.js      4          [通过]
    list.js        19         [通过]
    reminder.js    10         [通过]
    ------------------------------------------------------------
    结论: 全部 JS 引用的元素都存在 OK

### 8.7 经验

1. **★ 让机器去检查"人不擅长发现的东西"。**
   "JS 引用了不存在的元素"这类问题，人眼几乎不可能在 4 个 JS 文件、34 个元素里查出来，
   但一个十几行的脚本一秒钟就查完了。
   **这类交叉引用检查应该固化成脚本，纳入常规验证流程。**

2. **判空保护会掩盖问题。** `if (output)` 让程序不崩，但也让错误悄无声息。
   **保护要配日志**：宁可写一句 `console.warn`，也不要什么都看不见。

3. **删除功能时，要连带搜索它的"下游"。**
   删掉一个 DOM 元素、一个接口、一个字段之后，
   **立刻全局搜索它的名字**，把引用一起清理干净。

4. **改版是最容易留下死代码的时刻。** 每次大改页面结构后，都应该跑一遍这类检查。

## BUG-009：容错代码写了，但永远不执行

- **日期**：2026-09-12
- **所属阶段**：第二阶段 · 功能 10（日历视图）
- **涉及文件**：`app/routers/calendar.py`、`app/services/calendar_service.py`
- **状态**：✅ 已修复

> 这条的教训不在"代码写错了"，而在**"代码写对了位置，却永远轮不到它执行"**。

### 9.1 症状

日历接口我特意做了容错设计：参数不合法就退回"今天所在的月份"，
这样用户手改网址、或者书签过期了，页面也不会白屏。

测试时发现：**部分非法参数确实能容错，但另一些直接返回 422。**

### 9.2 复现

    GET /api/calendar/month?year=abc&month=99   -> 422
    GET /api/calendar/month?year=-5&month=0     -> 200（这个是正常的）

### 9.3 报错原文

    422 Unprocessable Entity
    {"detail":[{"type":"int_parsing","loc":["query","year"],
                "msg":"Input should be a valid integer, unable to parse string as an integer",
                "input":"abc"}]}

### 9.4 根因分析

我最初的路由签名是这样写的：

    def get_month(year: int = Query(None), month: int = Query(None)):
        today = date.today()
        return calendar_service.month_view(year or today.year, month or today.month)

服务层里也写了范围检查：

    if not (1970 <= year <= 2999): year = date.today().year
    if not (1 <= month <= 12):    month = date.today().month

看起来两层都做了防护。但**执行顺序**是这样的：

    ① FastAPI 解析查询参数，发现 year: int，尝试把 "abc" 转成 int
    ② 转换失败 -> 直接返回 422，【请求处理函数根本没有被调用】
    ③ 服务层那些 if 判断……一行都没跑到

**关键认识：FastAPI 的参数类型注解是在【框架层】校验的，比服务层早得多。**

我用 `int` 声明参数，本意是"让框架帮我转成整数"，
但同时也**把"参数不是数字"这种情况从服务层的手里拿走了** ——
框架直接把它变成 422，服务层再想容错也没有机会。

（`year=-5` 之所以能容错，是因为 `-5` 本身是一个合法的整数，
  框架放行，服务层的范围检查才生效。）

### 9.5 修复方案

**把参数以字符串接收进来，自己解析、自己容错：**

    # routers/calendar.py
    def get_month(
        year: str = Query(None),     # ← 刻意用 str，不用 int
        month: str = Query(None),
    ):
        return calendar_service.month_view(year, month)

    # services/calendar_service.py
    def parse_year_month(year_raw, month_raw):
        today = date.today()
        try:
            year = int(str(year_raw).strip())
        except (TypeError, ValueError):
            year = today.year          # 转不了就用今年
        ...

**判断标准**：

| 场景 | 该怎么做 |
| --- | --- |
| 这是一个**给程序调用的 API** | 用 `int` 声明，格式不对就返回 422 —— 这是正确行为 |
| 这是一个**给浏览器页面用的接口**，非法参数退回默认值体验更好 | 用 `str` 接收，在服务层自己解析 |

日历页显然是后者：**网址被手改错就白屏，是不可接受的。**

### 9.6 验证

    什么都不传                  -> 200  2026 年 9 月
    年份是字母、月份越界        -> 200  2026 年 9 月
    负数年月                    -> 200  2026 年 9 月
    月份 13                     -> 200  2026 年 9 月
    年份超大                    -> 200  2026 年 1 月
    年份带小数点                -> 200  2026 年 9 月
    空白字符                    -> 200  2026 年 9 月
    正常参数                    -> 200  2026 年 2 月
    结论: 全部返回 200，容错生效 OK

### 9.7 经验

1. **★ 校验发生的位置，决定了你的容错代码有没有机会运行。**
   写防护代码之前，先想清楚"这个错误会在哪一层被拦下"。
   拦在前面的层，后面的层就永远看不到它。

2. **框架的"方便"和"控制权"往往是矛盾的。**
   `year: int` 让框架帮你转型很方便，但也把控制权交出去了。
   **需要精细控制时，就得把参数降级成 `str` 自己处理。**

3. **"部分情况下能容错"是最迷惑人的 Bug。**
   `year=-5` 能容错、`year=abc` 不能，这种"有时候行有时候不行"
   最容易让人以为是偶发问题。**测试要把各种非法输入都列出来试一遍。**

4. **文档里写的承诺要去验证。**
   我在函数文档里写了"参数不合法时会自动退回当月"——
   如果没实际测这一条，这个承诺就是假的。
   **写了什么，就要测什么。**

## BUG-010：输出重定向到文件后，启动横幅"不见了"

- **日期**：2026-09-12
- **所属阶段**：第二阶段 · 功能 11（设置页 + 开机自启）
- **涉及文件**：`start.bat`、`start_silent.bat`
- **状态**：✅ 已修复

### 10.1 症状

验证开机自启脚本 `start_silent.bat` 时，我把它输出重定向到文件方便检查：

    cmd /c "start_silent.bat > _silent.txt 2>&1"

结果文件里**只有 uvicorn 的日志，没有程序自己的启动横幅**：

    INFO:     Started server process [36800]
    INFO:     Application startup complete.
    INFO:     Uvicorn running on http://127.0.0.1:8000 (Press CTRL+C to quit)

服务其实是正常的（`/api/health` 返回 200），但那段"离线待办清单 v0.1.0 / 主界面: ..."
的提示**一个字都没有**。

### 10.2 复现

    cmd /c "start_silent.bat > _silent.txt 2>&1"
    # 等几秒，然后看 _silent.txt

### 10.3 报错原文

**没有报错。** 又是一次静默问题 —— 程序跑得好好的，只是"话没说出来"。

### 10.4 根因分析

这不是 Bug，是 Python 的**输出缓冲（buffering）**机制，属于语言的标准行为：

| 标准输出的去向 | 缓冲方式 | 效果 |
| --- | --- | --- |
| **终端 / 控制台** | 行缓冲（遇到换行就输出） | `print()` 立刻可见 ✅ |
| **文件 / 管道** | **块缓冲**（攒够约 8KB 才输出） | 内容先攒在内存里，**看不到** ❌ |

**为什么要这样设计？** 因为"往终端逐行输出"和"往文件连续写"的开销差别很大。
程序要往文件里写几十万行时，一行一行写会慢得离谱；攒成一块一次写就快得多。
所以 Python 检测到输出不是终端时，就自动切换成块缓冲。

我们的启动横幅只有几百字节，**远不到 8KB，所以一直躺在缓冲区里**，
直到进程结束才会被真正写出来。而我们是在进程还活着的时候去读文件的 —— 自然什么都看不到。

### 10.5 修复方案

在批处理里设置环境变量，强制不做缓冲：

    set PYTHONUNBUFFERED=1

加到了 `start.bat` 和 `start_silent.bat` 里。

**这个变量的作用**：等价于运行 `python -u`，让 `print()` 立刻写到目的地，不再攒着。

**代价**是输出量很大时（比如一次打印几万行）会稍微慢一点 ——
但对本项目来说完全无所谓，而"日志立刻可见"的价值大得多。

### 10.6 验证

    ========================================================
      离线待办清单  v0.1.0
    ========================================================
      主界面  : http://127.0.0.1:8000
      接口文档: http://127.0.0.1:8000/docs
      数据文件: E:\...\data\todo.db
      按 Ctrl + C 停止服务
    ========================================================
      （静默模式：请在浏览器里手动访问上面的地址）

    启动横幅出现了 : 是
    提示了静默模式 : 是
    服务可用      : 是 (status=ok)

### 10.7 经验

1. **"程序正常运行但什么都没打印"时，先怀疑缓冲，不要怀疑代码。**
   这是新手最容易掉进去的坑之一。

2. **记住这条规律：输出到终端是行缓冲，输出到文件/管道是块缓冲。**
   所以"我手动运行能看到，脚本里看不到"是很典型的现象。

3. **验证脚本时，一定要用和真实使用【相同的输出方式】。**
   我这次是重定向到文件去验证的，恰好暴露了这个问题；
   如果只是在终端里跑一下看到横幅就收工，这个坑会一直藏着。

4. **"看不到"和"没发生"是两回事。** 服务其实一直在正常工作 ——
   如果当时慌慌张张去改代码，就会把好的代码改坏。**先确认现象的真实范围。**

    tasks 表记录数     ->  0
    settings 表记录数  ->  3

**② 关键一步：扫描数据库文件的原始字节。**

所以如果曾经写入过内容，原始文字可能还留在文件里：

    '[提醒测试] 这是一条测试提醒看到这个弹窗，就说明提醒功能正常工作了。'

**③ 检查有没有备份：**

    data/backups/  ->  空

### 11.3 报错原文

**没有报错。** 程序从来没有告诉过任何人"我在删数据"。

这是最可怕的一类事故：**静默的、不可逆的、由自己人造成的。**

### 11.4 根因分析

#### 直接原因：我的临时测试脚本里有这样一段

    # 几乎每个临时测试脚本的开头都有这一行
    from app.repositories import task_repo
    for t in task_repo.list_tasks():
        task_repo.delete(t.id)          # ← 删掉的是【用户真实创建的待办】

写这段的动机是好的："先清空，方便测试"。
但我把它跑在了**默认的数据库**上，而默认数据库就是用户的数据。

#### 深层原因：我违反了自己定下的规矩

更让人难受的是 —— **我早就想到过这个问题，并且已经做对了。**

在功能 2 时，我专门为 `check_repo.py` 写了隔离机制：

    os.environ["TODO_DB"] = str(TEST_DB)     # 把数据库指向 data/test/

并且把它写进了项目约定（见 `docs/阶段二-02-数据库与数据表.md` 第五章）：

> **"测试环境必须与真实环境隔离。"**

**但后来写临时脚本时，我没有遵守。**

为什么没遵守？三个原因，每个都很典型：

| # | 我当时的心态 | 为什么危险 |
| --- | --- | --- |
| 1 | "这只是个临时脚本，跑完就删" | **临时脚本也会造成永久损失。** 数据不区分脚本是不是临时的。 |
| 2 | "隔离那套要写好几行，太麻烦" | 图省事省下的 3 行代码，代价是用户几小时的工作。 |
| 3 | "现在库里没几条数据，删了也没事" | **我在替用户判断"你的数据不重要"。** 而且用户随时可能已经录入了他自己的东西。 |

#### ★ 根本原因：备份被排到了"以后"

还有一个更根本的问题。

我在功能 2 的设计文档里就写了：

> "**自动备份**：程序启动时，若 data/todo.db 存在，复制一份到 data/backups/…"

但我把它归到了"第三阶段：数据持久化优化"，还自己在 `docs/待优化与已知问题.md` 里定了优先级标准：

> "**不做会不会导致数据丢失或安全问题？会，就是高优先级。**"

**OPT-010（自动备份）被我自己标成了"高"优先级，然后我把它排到了第三阶段。**

结果：风险窗口期就在"第二阶段的这几十次测试"里，事故恰好发生在这个窗口。

> **教训：优先级标签只有在"真的据此排期"时才有意义。**
> **把"高优先级"和"以后再做"写在同一行，等于自欺欺人。**

### 11.5 修复方案

分四层，从"防再次发生"到"发生了也能救回来"：

#### 第一层：给危险操作加闸门

    def reset_all(user_id=1, confirm=False) -> int:
        """删除该用户的【全部】待办。"""
        if not confirm:
            raise ValueError(
                "reset_all() 会删除全部待办且无法恢复，必须显式调用 reset_all(confirm=True)。"
            )
        ...

**加了这道闸门后，那种"顺手一行就清空数据库"的脚本会直接抛异常停下**，
而不是安静地把数据删光。

> 减少一次事故，往往只需要一个"你确定吗"。

#### 第二层：统一测试隔离工具 + 运行时守卫

新增 `scripts/_isolation.py`，任何写数据的脚本开头只要两行：

    from scripts._isolation import use_isolated_db, assert_isolated
    TEST_DB = use_isolated_db("脚本名")     # 必须在 import app 之前！
    ...
    from app import config, database
    assert_isolated()                       # 第二道网：不是隔离库就立刻中止

`assert_isolated()` 会在检测到"正在操作真实数据库"时，用一段**显眼的提示**中止脚本，
并告诉写脚本的人应该怎么改。

#### 第三层：★ 立刻实现自动备份（把 OPT-010 从第三阶段提前）

新增 `app/core/backup.py`：

- **程序每次启动时自动备份**（距上次不足 60 分钟则跳过，避免刷屏）
- **最多保留 7 份**，自动删最旧的
- 用 **SQLite 官方在线备份 API**（`sqlite3.Connection.backup`），
  即使数据库正在被写入也能得到一致的副本（直接复制文件则可能复制到"写了一半"的状态）

设置页新增"备份"卡片：份数、最近备份时间、清单、**立即备份**按钮、打开备份目录。

#### 第四层：把规矩写进项目约定

在 `AGENTS.md` 里加了一条**硬性规定**（见 11.7）。

**③ 频率限制生效：**

### 11.7 经验（这一节请重点看）

1. **★ "不做可能丢数据"的功能，优先级就是最高的 —— 而且要【真的先做】，不是标个"高"然后排到最后。**
   我把 OPT-010 标成"高优先级"却放在第三阶段，结果风险窗口期就出了事。
   **标注优先级不等于执行优先级。**

2. **★ 定过的规矩要一直遵守，不能"这次情况特殊"。**
   我明明在功能 2 就写下了"测试必须隔离"，还在文档里强调过。
   但写临时脚本时觉得"麻烦""就一次" —— **事故从来都发生在"就这一次"里。**

3. **★ 危险操作要加闸门，不能依赖人的自觉。**
   靠"我记得要小心"是靠不住的。`confirm=True` 这种强制参数，
   让"不小心"变成一次**可见的报错**，而不是一次**静默的灾难**。

4. **临时脚本和正式代码一样危险。** "跑完就删"的脚本，

5. **永远不要替用户判断"这些数据不重要"。**

6. **备份要"能验证的备份"才算备份。**
   这次我特意验证了"备份文件能打开、能查询、表和数据都在"。
   只看到目录里有个文件就宣布"备份好了"是很常见的自欺。

7. **有备份 ≠ 可以随便删。** 备份是最后一道防线，不是第一道。
   正确顺序是：**隔离 → 闸门 → 备份**，三道都要有。

这次丢失是你手动创建、我无法还原的待办数据，**责任完全在我**。

现在三道防线都已到位：**测试隔离**（脚本碰不到真实数据）、
**危险操作闸门**（清空必须显式确认）、**自动备份**（每次启动留一份，保留 7 份）。

    except Exception:
        ...记录错误...

    _stop_event.wait(config.REMINDER_SCAN_SECONDS)   # ← 这里出错，上面的 except 抓不到

后果链条是这样的：

    ① 后台线程执行到这一行
    ② config 里没有这个属性 -> 抛 AttributeError
    ③ 这一行不在 try 里 -> 异常一路往上冒出 _loop() 函数
    ④ 线程函数返回 -> 【线程直接结束】
    ⑤ 没有人发现：页面正常、接口正常、服务正常，只是【再也不提醒了】

**这就是"后台线程的静默死亡"** —— 所有后台线程类 Bug 里最难查的一种。

而且我甚至给它加了"错误记录"机制（`last_run["error"]`），
**但那个机制保护不到 try 外面的代码** —— 等于白写了。

### 12.5 修复方案

#### ① 修正常量引用

`setting_service.py` 改用 `config.REMINDER_SCAN_SECONDS`，全局搜索确认无残留。

#### ② 给"读配置"加兜底，绝不抛异常

    DEFAULT_INTERVAL = 20

    def _interval() -> int:
        """安全地读取扫描间隔。配置缺失或值不合法时退回默认值，绝不抛异常。"""
        try:
            return max(5, int(config.REMINDER_SCAN_SECONDS))
        except (AttributeError, TypeError, ValueError):
            return DEFAULT_INTERVAL

这里还顺手加了 `max(5, ...)` —— 防止有人把间隔配成 0 或负数，
那会让循环变成"疯狂空转"，把 CPU 跑满。

#### ③ ★ 把整个循环体都包进 try

    while not _stop_event.is_set():
        try:
            result = reminder_service.scan_and_fire()
            ...
        except Exception as exc:
            last_run["error"] = ...

        try:
            _stop_event.wait(_interval())
        except Exception as exc:
            last_run["error"] = ...
            time.sleep(DEFAULT_INTERVAL)      # 兜底：出错了也要继续转

**原则：后台线程的循环体里，不允许有任何一行裸露在 try 之外。**

#### ④ 让"线程还活着吗"变得可见

新增接口 `GET /api/reminders/scheduler`，返回：

    {
      "running": true,                    // 线程活着吗
      "poll_seconds": 20,
      "last_run": {
        "at": "2026-09-12 23:55",         // 最后一次扫描的时间
        "fired": 0,                       // 扫出几条
        "native_ok": 0,                   // 系统通知发成功几条
        "error": null                     // 出过错吗
      }
    }

设置页也会显示"后台提醒线程：运行中 · 上次检查 2026-09-12 23:55"。

**"看不到的东西就容易坏掉了没人知道"** —— 把状态暴露出来，问题才会被发现。

### 12.6 验证

**① 线程真的在跑（而且扫描过多次）：**

    运行中: True  扫描间隔: 20 秒
    last_run: {'at': '2026-09-12 23:55', 'fired': 0, 'native_ok': 0, 'error': None}

**② 完整链路（造一条 2 分钟前的提醒）：**

    已创建 #2，提醒时间 2 分钟前
    等待后台线程（最多 25 秒）...
       ...15 秒
    >>> 17 秒后出现
    系统通知发送成功: True
    返回信息       : 通知已发送
    reminded_at = 2026-09-12 23:55      ← 已标记，不会重复弹

### 12.7 经验

1. **★ 后台线程的循环体，不允许有任何一行裸露在 try 之外。**
   线程死了不会有人告诉你。**宁可吞掉异常并记录，也不要让它死。**

2. **★ 重命名常量/函数后，必须全局搜索旧名字。**
   改定义只要一秒，漏掉一个使用方就可能埋一个隐形炸弹。
   **能自动查的不要靠眼睛**（这次就是靠 grep 抓出来的）。

3. **"加了错误处理"不等于"覆盖了所有可能出错的地方"。**
   我明明写了 `last_run["error"]` 记录机制，但它保护不到 try 外面的那一行 ——
   **防护的边界在哪里，比有没有防护更重要。**

4. **让后台任务的状态可见。** 提供 `running` / `last_run` / `error` 这样的状态接口，
   能把"静默失效"变成"一眼看出来"。

5. **读配置要兜底。** 配置项可能被改错、被删、被写成字符串；
   关键定时任务的间隔，必须有默认值。

## BUG-013：Windows 静默丢弃通知（"成功"却是假的）

- **日期**：2026-09-13
- **所属阶段**：第二阶段 · 系统级提醒
- **涉及文件**：`app/core/notifier.py`、`app/config.py`
- **状态**：✅ 已修复（方案已落地，并由后续的「系统级提醒」功能实际验证通过）

> 这条和 BUG-010 属于同一类："**程序说成功了，但用户什么都没看到**"。
> 这类问题最难查 —— 因为所有环节都告诉你"没问题"。

### 13.1 症状

用户反馈（原话）：

> "从离线待办清单的设置中发送测试信息无回应，我确定 win 的设置正确。"

接口返回 `{"ok": true, "message": "通知已发送"}`，**但屏幕右下角什么也没出现**。

### 13.2 复现

    POST http://127.0.0.1:8000/api/reminders/test
    -> {"ok": true, "message": "通知已发送"}
    -> 观察屏幕右下角：什么都没有

### 13.3 报错原文

**没有报错。** PowerShell 返回码 0，还打印了 `TOAST_OK`。

我做了四组对照实验来定位：

| 编号 | 应用身份 (AppId) | 场景 | PowerShell 结果 |
| --- | --- | --- | --- |
| 1 号 | 自定义 `离线待办清单` | reminder | 成功 |
| 2 号 | PowerShell 官方 AUMID | reminder | 成功 |
| 3 号 | PowerShell 官方 AUMID | 普通通知 | 成功 |
| 4 号 | **注册过的自家 AUMID** | reminder | 成功 |

**四组全部"成功"，但用户反馈一个都没看到。**

### 13.4 根因分析

关键认识：**`CreateToastNotifier(appId)` 返回不代表通知会被显示。**

Windows 对通知的显示有一套**准入规则**：

    ① 应用必须有一个"身份"(AppUserModelID)
    ② 这个身份必须在系统里【注册过】（有 DisplayName）
    ③ 否则通知可能被【静默丢弃】—— 不报错、不提示，就是不显示

对于**打包应用**（从微软商店安装的），系统会自动注册身份。
但**我们是一个"未打包"的普通 Python 程序**：

    没有安装程序、没有开始菜单快捷方式、没有任何注册记录
    -> 我们传的 `离线待办清单` 这个字符串，在系统眼里【谁也不是】
    -> Windows 就把通知丢掉了

> "未打包应用"（unpackaged app）发通知需要**显式注册身份** ——
> 这是微软文档里写明的，但非常容易被忽略。
> 很多教程用 `CreateToastNotifier("随便一个名字")` 能跑通，
> 是因为某些 Windows 版本/配置比较宽松；**换个环境就静默失效**。

### 13.5 修复方案

给应用注册一个属于自己的身份。只往注册表写一条（**HKCU，不需要管理员权限**）：

    HKEY_CURRENT_USER\Software\Classes\AppUserModelId\OfflineTodoList.Desktop
        DisplayName = "离线待办清单"

实现（用 Python 标准库 `winreg`，不启动 PowerShell，更快更可靠）：

    REG_PATH_PREFIX = "Software" + chr(92) + "Classes" + chr(92) + "AppUserModelId" + chr(92)

    def register_app_id() -> dict:
        import winreg
        path = REG_PATH_PREFIX + config.NOTIFY_APP_ID
        key = winreg.CreateKeyEx(winreg.HKEY_CURRENT_USER, path, 0, winreg.KEY_WRITE)
        try:
            winreg.SetValueEx(key, "DisplayName", 0, winreg.REG_SZ, config.APP_NAME)
        finally:
            winreg.CloseKey(key)
        return {"ok": True, ...}

然后在 `show()` 里，发通知前自动确保身份已注册：

    if not app_id_registered():
        register_app_id()

另外加了设置页的"应用身份"状态显示 + 一个"注册"按钮，以及
`POST /api/settings/register-notify-app` 接口。

> **关于"项目自包含"**：这条注册表项在 HKCU 下，是"程序在系统里登记的名字"，
> 不是散落的文件。它体积为零、随时可删，也是"未打包应用发通知"的**正规做法**。
> 这和 BUG-005 里"往 C 盘临时目录扔文件"是两回事。

### 13.6 验证

    注册前是否已注册  : False
    执行注册          : {"ok": True, "message": "已注册应用身份：OfflineTodoList.Desktop"}
    注册后是否已注册  : True

    注册表核实:
       DisplayName = '离线待办清单'

**⚠️ 通知是否真的显示出来，还需要用户肉眼确认**（程序无法自己判断）。

### 13.7 经验

1. **★ "API 返回成功"和"用户看到了"是两件事。**
   凡是"程序无法自己验证结果"的功能（通知、打印、声音、外设），
   **都必须给用户一个"手动测试"的入口**，让人类来确认。

2. **"未打包应用"是一个容易被忽略的处境。**
   我们不是从商店安装的、没有安装程序，所以不能假设系统"认识我们"。

3. **多组对照实验是定位"无报错故障"的好办法。**
   一次改一个变量、同时发出去，让用户报告"哪几个出现了"，比反复试错快得多。

4. **静默失败是最危险的失败。** 宁可报错，也不要"什么都不说地不工作"。

## BUG-014：提示音被错误地抑制（"支持"不等于"送达"）

- **日期**：2026-09-13
- **所属阶段**：第二阶段 · 系统级提醒
- **涉及文件**：`app/static/js/reminder.js`、`app/services/reminder_service.py`
- **状态**：✅ 已修复

### 14.1 症状

用户反馈（原话）：

> "打开离线待办清单后 2.才出现弹窗，但无提示音"

提醒卡片正常出现，**但完全没有声音** —— 系统通知没响，页面也不响。

### 14.2 复现

造一条到点提醒，观察：卡片出现，但一声不响。

### 14.3 报错原文

**没有报错。** 又是一次静默问题。

### 14.4 根因分析

这是我**自己设计的一个逻辑错误**。

当初为了避免"系统通知响一次、页面又响一次"（双响），我写了这样的判断：

    let nativeSupported = true;   // 系统通知能不能用
    ...
    if (added && !nativeSupported) playChime();   // 只有系统通知不可用时才自己响

后端传的是：

    "native_supported": notifier.is_supported(),

而 `is_supported()` 的判断是 —— **`sys.platform.startswith("win")`**。

也就是说：**只要系统是 Windows，页面就认为"系统通知会响"，于是保持安静。**

**但"系统支持"和"通知真的弹出来了"完全是两回事。**
（BUG-013 就是活生生的例子：Windows 支持，但通知被静默丢弃了。）

结果：系统通知没出来 + 页面不响 = **完全没有声音**。

> **★ 核心教训：判断"要不要做兜底"时，依据必须是"上一步真的做成了"，
> 而不是"上一步理论上能做"。**
> 用"能力"当"结果"是典型的逻辑错误。

### 14.5 修复方案

改成**由用户自己决定**，而不是程序猜：

1. 新增设置项 `notify_sound_enabled`（默认开启）
2. 接口 `POST /api/settings/preference` 读写它（带**白名单**，只允许改这一项）
3. 收件箱接口返回它：`inbox()` 里加 `"sound_enabled"`
4. 前端改成 `if (added && soundEnabled) playChime();`
5. 设置页加了一个"页面内提醒播放提示音"开关

**为什么默认开启？**
因为"没有声音"比"响两声"糟糕得多 ——
响两声只是吵，没声音会让用户**完全错过提醒**。宁可吵一点。

### 14.6 验证

    读回: False
    打开: {"ok": true, "key": "notify_sound_enabled", "value": true}

    白名单校验:
      尝试写危险键 autostart_enabled -> 400 不支持的设置项（可选：notify_sound_enabled）

### 14.7 经验

1. **★ "能力"不等于"结果"。** 判断兜底条件时，永远用"实际上一步成功了没有"，
   而不是"上一步理论上能不能成功"。

2. **不要让程序替用户猜。** 这种"要不要响"的偏好，交给用户开关最省事，
   也最不容易猜错。

3. **默认值要选"失败代价更小"的那一边。**

**结论一：`scenario="reminder"`（不点不走）完全没问题** —— 2 号用的就是它。

| **7 号** | OfflineTodoList.Diagnostic | 约 30 分钟 | ✅ |

**最终结论：注册表方式完全可行 —— 只是 Windows 需要时间刷新身份缓存。**

同一个身份，刚注册完发不出去、过一阵就正常了。
这也解释了最初那个「所有调用都成功、却一个通知都不出现」的怪现象。

> 所以不是「注册表方式不行」，而是「**注册完不能马上用**」。
> 这类「需要时间生效」的机制很坑 —— 幸好用对照实验把它测出来了。

**最终方案：默认借用系统已注册的 PowerShell 身份。**

| 模式 | 用的身份 | 通知顶部显示 | 可靠性 |
| --- | --- | --- | --- |
| **`system`（默认）** | PowerShell 已注册身份 | "Windows PowerShell" | ✅ **实测稳定** |
| `own` | 我们自己的 OfflineTodoList.Desktop | "离线待办清单" | ⚠️ 系统不一定认可 |

为了不让用户被绑死，做成了**设置页可切换**：

    config.NOTIFY_APP_ID_MODE = "system"      # 默认：兼容模式
    APP_ID_MODES = {
        "system": "{1AC14E77-...}\WindowsPowerShell\v1.0\powershell.exe",
        "own":    "OfflineTodoList.Desktop",
    }

    设置页 -> "通知身份模式" 下拉框：兼容模式（推荐）/ 自有身份

**代价要如实说明**：兼容模式下，通知顶部会显示 Windows PowerShell 而不是
离线待办清单。这是「能用」和「好看」之间的取舍。

**但既然自有身份最终能用，就没必要二选一 —— 于是做了「自动模式」：**

| 模式 | 行为 |
| --- | --- |
| **auto（默认）** | 本次启动时身份**已经注册过** -> 用自有身份（显示「离线待办清单」）；本次启动**才新注册** -> 先用兼容模式（保证立刻能用），下次启动自动升级 |
| system | 始终借用系统身份 |
| own | 始终用自有身份 |

关键实现（notifier.init()，程序启动时调用一次）：

    _registered_before_start = None

    def init():
        """程序启动时准备应用身份。"""
        global _registered_before_start
        _registered_before_start = app_id_registered()   # 启动时是不是已经注册过
        if not _registered_before_start:
            register_app_id()                            # 没有就现在注册

    def active_mode():
        mode = 读设置() or config.NOTIFY_APP_ID_MODE
        if mode == "auto":
            return "own" if _registered_before_start else "system"
        return mode

**为什么要在启动时注册，而不是「用到时才注册」？**
因为注册后需要时间生效。启动时就注册，等第一条提醒真的到点（至少 20 秒后，
通常更久），身份多半已经被系统认下了 —— 成功率比「要弹通知那一刻才注册」高得多。

实测（身份已注册的情况下）：

    保存的模式      : auto
    实际使用的模式  : own
    启动前已注册    : True
    实际使用的身份  : OfflineTodoList.Desktop
    发通知          -> {"ok": true, "message": "通知已提交给 Windows（身份：own）"}

### 13.9 顺手修掉的一个隐患：生成物过期

改造时我把 PowerShell 脚本从"应用身份写死在脚本里"改成"用参数传进来"，
但磁盘上那份**旧脚本还在**。

而 `_ensure_script()` 原来的判断是：

    if not PS_SCRIPT.exists():
        PS_SCRIPT.write_text(...)      # 文件已存在 -> 跳过 -> 用的还是旧脚本

**结果：新代码 + 旧脚本 = 调用时参数对不上，通知直接失败。**

修复：判断标准从"文件在不在"改成"**内容和模板一致不一致**"：

    if PS_SCRIPT.exists() and PS_SCRIPT.read_text(encoding="utf-8-sig") == PS_TEMPLATE:
        return PS_SCRIPT
    PS_SCRIPT.write_text(PS_TEMPLATE, encoding="utf-8-sig")    # 不一致就覆盖

> **★ 通用经验：凡是"运行时生成的文件"，都要考虑它过期了怎么办。**
> "文件存在就跳过"是一个很常见的、会随代码升级而悄悄失效的写法。

## BUG-016：批处理菜单死循环，一次误建 108 条任务

- **日期**：2026-09-13
- **所属阶段**：第二阶段 · 工具脚本
- **涉及文件**：`test_reminder.bat`
- **状态**：✅ 已修复

> **又是我的错，而且这次实实在在污染了用户的数据（108 条脏数据）。**
> 记录下来，因为它揭示了一个批处理的经典陷阱。

### 16.1 症状

用户说在 `C:\Users\<用户名>` 下敲 `python scripts/test_reminder.py` 报
"can't open file"（这是 BUG-004 的老问题：命令要在项目目录里敲）。

为了以后不用敲命令，我做了一个双击就能用的 `test_reminder.bat`：
带一个菜单（1 新建 / 2 列出 / 3 清理 / 0 退出），选完回到菜单继续。

**我测试它的时候，用了管道喂输入：**

    cmd /c "echo 2| test_reminder.bat"

### 16.2 复现

上面那条命令之后，数据库里多出了 **108 条**一样的测试任务。

    #109 [提醒测试] 这是一条测试提醒  提醒=2026-09-13 11:10
    #108 [提醒测试] 这是一条测试提醒  提醒=2026-09-13 11:10
    ...（共 108 条）
    #1   1                          提醒=2026-09-13 11:08  <- 用户自己的，只有这一条

### 16.3 报错原文

**没有任何报错。** 它就这么安安静静地建了一百多条任务。

### 16.4 根因分析

菜单的主体结构是这样的：

    :MENU
    cls
    ...打印菜单...
    set "CHOICE="
    set /p CHOICE=  Choose [1]: 
    if "%CHOICE%"=="" set "CHOICE=1"      # 直接回车 = 选 1
    if "%CHOICE%"=="1" %PYBIN% scripts\test_reminder.py
    ...
    pause >nul
    goto MENU                             # 回到菜单

**问题出在 `set /p` 遇到"输入结束"时的行为：**

| 情况 | `CHOICE` 会变成什么 |
| --- | --- |
| 用户敲了 `2` 再回车 | `"2"` -> 执行"列出" ✅ |
| 用户直接回车 | `""` -> 被下面那行改成 `"1"` -> 执行"新建" ✅ |
| **输入流结束了（管道/重定向读完）** | **保持不变，也就是 `""`** -> 又被改成 `"1"` -> **又执行"新建"** ❌ |

于是循环变成：

    MENU -> set /p 读不到东西 -> CHOICE="" -> 变成 "1" -> 建一条任务
         -> pause 立刻返回 -> goto MENU -> 再来一遍 -> ...

**死循环，每圈建一条任务。**

> 两个设计都有责任：
> ① `if "%CHOICE%"=="" set "CHOICE=1"` 这个"默认值"把**空输入**和**没有输入**混为一谈；
> ② `goto MENU` 让"出错"变成了"无限重复出错"。

### 16.5 修复方案

**去掉循环。** 一次菜单、一个动作、然后退出：

    rem ---- Run the chosen action, then EXIT ----
    rem This file used to loop back to the menu. That was a trap: when its input
    rem came from a pipe or a redirect, "set /p" hit end-of-input, the variable
    rem stayed empty, and the file kept re-running "create" in an endless loop.
    rem One menu, one action, then quit. Double-click again for another action.
    if "%CHOICE%"=="1" goto RUN_CREATE
    if "%CHOICE%"=="2" goto RUN_LIST
    if "%CHOICE%"=="3" goto RUN_CLEAR
    goto THE_END

**为什么不去修那个默认值，而是直接砍掉循环？**

因为「菜单循环」带来的便利**远小于它带来的风险**：

| | 有循环 | 没有循环 |
| --- | --- |
| 便利 | 不用重新双击 | 要再双击一次 |
| 风险 | 任何"输入异常"都可能无限循环 | **不可能循环** |

**这类取舍的原则：当"出错时的后果"远大于"不用它的麻烦"时，就把功能砍掉。**

### 16.6 验证

    管道输入测试:  cmd /c "echo 2| test_reminder.bat"
    -> 正常列出提醒
    -> 显示 "Done. Press any key to close this window."
    -> 退出码 0，【不再循环】

    数据清理:  python scripts/test_reminder.py --clear
    -> 已删除 108 条测试任务

    清理后核对:  共 1 条待办  #1 "1"  <- 用户自己的那条，完好

### 16.7 经验

1. **★ 测试脚本自己要小心"写数据"。**
   我为了测试菜单，用管道喂了一个输入 —— **结果它自己在那里无限建数据**。
   **测试一个会写数据的工具时，应该先指向隔离数据库**（AGENTS.md 3.0 铁律一）。

2. **★ "循环"会把一次错误放大成一百次。**
   写循环时永远要问："如果这一圈出错了，下一圈会更糟吗？"
   会，就不要让它自动进入下一圈。

3. **`set /p` 的"读不到输入"和"输入为空"是两件事，但批处理不区分。**
   任何依赖 `set /p` 的默认值逻辑，都要假设"可能永远读不到"。

4. **方便和安全冲突时，选安全。** 少一次双击，换来"绝不可能死循环"，很值。

5. **删数据前先看清楚哪些是自己造的。**
   这次清理用的是 `test_reminder.py --clear`（只删标题以 `[提醒测试]` 开头的），
   **用户自己那条 #1 完好无损** —— 这是 BUG-011 之后养成的习惯。

## BUG-017：字符串里的非法转义序列（未来的定时炸弹）

- **日期**：2026-09-13
- **所属阶段**：上线前全面体检
- **涉及文件**：`app/core/autostart.py`
- **状态**：✅ 已修复

> 这条不是用户报的，是**上线前做体检时扫出来的**。
> 它现在只是警告，但**未来版本的 Python 会把它变成错误** ——
> 也就是说：**今天能跑，某天升级 Python 就跑不起来了。**

### 17.1 症状

编译代码时出现警告：

    app\core\autostart.py:10: SyntaxWarning: "\M" is an invalid escape sequence.
        Such sequences will not work in the future. Did you mean "\\M"?
        A raw string is also an option.

对应那一行是模块文档字符串里的一句：

    位置：%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup

### 17.2 复现

    python -W always -c "import py_compile; py_compile.compile('app/core/autostart.py')"

或者更彻底：**编译每一个 .py 文件，收集所有 SyntaxWarning**（我写了个脚本扫全项目）。

### 17.3 根因分析

Python 的普通字符串里，反斜杠是**转义字符**：

| 写法 | Python 理解成 |
| --- | --- |
| `"\n"` | 换行符 |
| `"\t"` | 制表符 |
| `"\M"` | **不认识** -> 现在给警告，将来报错 |

我写的是 Windows 路径 `%APPDATA%\Microsoft\...`，
Python 看到 `\M`、`\W`、`\S` 都不认识，于是报警。

**当前行为**：Python 暂时"睁一只眼闭一只眼"，把这些当成字面的反斜杠 + 字母。
**未来行为**（官方已公告）：**直接抛 SyntaxError**。

> 也就是说：**这份代码今天能跑，用户明天升级 Python 可能就跑不起来了。**
> 对一个要发布到 GitHub、让别人下载使用的项目来说，**这是必须现在就修掉的**。

### 17.4 修复方案

把模块文档字符串改成**原始字符串**（raw string）—— 在引号前加一个 `r`：

    # -*- coding: utf-8 -*-
    r"""
    autostart.py -- 开机自启（模块 M7，Windows）。

    【注意这个 docstring 前面的 r】
        它是一个"原始字符串"，因为下面写了 Windows 路径
        （%APPDATA%\Microsoft\...）。不写 r 的话，Python 会把 \M、\W 当成
        转义序列，报 SyntaxWarning —— 而且未来版本的 Python 会直接报错。

        —— 这条是上线前体检时扫出来的，见 BUG-017。
    """

**`r"..."` 的作用**：里面的反斜杠**不再有特殊含义**，就是一个普通字符。
写路径、正则表达式时都应该用 `r` 开头 —— 这是 Python 的一条基本习惯。

### 17.5 验证

    全项目扫描 SyntaxWarning:
      修复前: 发现 1 处（app/core/autostart.py:10）
      修复后: 没有 SyntaxWarning ✅

### 17.6 经验

1. **★ 「能跑」和「以后还能跑」是两件事。**
   这个警告在 Python 3.12 就出现了，我一路开发都没注意 ——
   因为**警告默认不会打断你**，容易一直忽略到它变成错误的那天。

2. **★ 上线前应该做一次「静态扫描」**，而不只是"功能测过就行"。
   这类问题功能测试**永远测不出来**（今天运行完全正常）。

3. **写路径和正则，一律用 `r"..."`。** 这是最省心的习惯。

4. **把警告当错误看。** 有条件的话，开发时用 `-W error` 运行，
   让警告直接变成失败，就不会积攒了。

## BUG-018：时间解析太宽松，脏数据悄悄进了数据库

- **日期**：2026-09-13
- **所属阶段**：第三阶段 · 单元测试与代码重构
- **涉及文件**：`app/core/timeutil.py`
- **状态**：✅ 已修复（**由单元测试发现**）

> 这条 Bug 的特殊之处：**它没有任何报错**。
> 程序照常运行，数据照常保存，只有在"排序结果不对"的时候你才会隐约觉得不对劲 ——
> 而那时你根本不会想到是时间格式的问题。

### 18.1 症状

给时间工具写单元测试时，我顺手加了一条"非法输入应返回 None"的用例：

    timeutil.parse("2026-9-13 8:30")   # 月份、日期、小时都没补零

**我预期它返回 None**（因为这个格式不符合项目约定的 `YYYY-MM-DD HH:MM`）。
结果它返回了一个正常的 `datetime` 对象。

### 18.2 复现

在项目根目录执行：

    python -c "from datetime import datetime; print(datetime.strptime('2026-9-13 8:30', '%Y-%m-%d %H:%M'))"

输出：

    2026-09-13 08:30:00

**它成功了。** 这就是问题所在。

### 18.3 报错原文

**没有报错。** 一个都没有。

这是最危险的一类 Bug —— 它不吵不闹，只是在背后悄悄破坏数据。

### 18.4 根因分析

`datetime.strptime` 的格式符 `%m`、`%d`、`%H`、`%M` 是**宽松匹配**的：

| 格式符 | 我以为的意思 | 它实际接受 |
| --- | --- | --- |
| `%m` | 两位月份 | `9` 或 `09` **都接受** |
| `%d` | 两位日期 | `3` 或 `03` **都接受** |
| `%H` | 两位小时 | `8` 或 `08` **都接受** |

**为什么这在本项目里特别致命？**

回顾决策 3B：项目把时间存成**定宽字符串** `YYYY-MM-DD HH:MM`，
并且依赖一个关键前提：

> **字符串的字典序 == 时间的先后顺序**

这个前提**只在"宽度固定"时成立**。举个例子：

    "2026-09-13 08:30"   ← 规范
    "2026-9-13 8:30"     ← 不规范

按字符串排序：

    "2026-09-13 08:30"
    "2026-9-13 8:30"      ← 排在了规范格式的【后面】

但按真实时间排序，`2026-9-13 8:30` 和 `2026-09-13 08:30` 是**同一时刻**。
更糟的是跨月份比较：`"2026-9-13"` 和 `"2026-10-01"` 按字符串比，
`9` > `1`，于是 **9 月被认为排在 10 月之后**。

一旦这种字符串进了数据库：
- 列表按时间排序会乱；
- 提醒扫描（`remind_at <= 现在`）会漏掉或多弹任务；
- 日历按日期范围查询会查不到。

**而且它不会立刻暴露** —— 要等到数据积累到一定量、跨了月份，才会显出症状。
到那时你根本不会怀疑是几个月前某次输入格式的问题。

### 18.5 修复方案

在 `app/core/timeutil.py` 的 `parse()` 里加一道**往返校验**（round-trip validation）：

    解析出来的时间，再格式化回去，必须和原始输入【一模一样】。

    def parse(raw):
        if not raw:
            return None
        try:
            dt = datetime.strptime(raw, FORMAT)
        except (ValueError, TypeError):
            return None
        # ★ 关键一步：转回字符串，必须与输入完全相同
        if dt.strftime(FORMAT) != raw:
            return None
        return dt

**为什么这样能挡住？** 因为 `strftime` 输出**永远是补零的规范格式**：

    "2026-9-13 8:30"  → 解析成功 → strftime → "2026-09-13 08:30"
                                    ↑ 和原输入不一样 → 判定为非法 ✅

**为什么不用正则去校验？** 也可以，但往返校验更省事也更可靠 ——
它不需要你手写"闰年 2 月有 29 天"这类规则，`strptime` 已经帮你查过了，
你只是补上"格式是否规范"这一条。

### 18.6 验证

在 `tests/test_timeutil.py` 中新增了专门针对这个坑的用例：

    非补零月份 "2026-9-13 08:30"      → None   ✅
    非补零日期 "2026-09-3 08:30"      → None   ✅
    非补零小时 "2026-09-13 8:30"      → None   ✅
    非补零分钟 "2026-09-13 08:3"      → None   ✅
    规范格式   "2026-09-13 08:30"     → 正常解析 ✅

全部测试：`python -m pytest tests/` → **229 项全部通过**。

### 18.7 经验

1. **★ 「解析成功」不等于「输入合法」。**
   库函数的校验范围通常比你的业务要求**宽**。凡是"用户输入会存进数据库"的地方，
   都要问一句：*这个值真的是我想要的形态吗？*

2. **★ 单元测试的价值恰恰在于"没报错的地方"。**
   这条 Bug 功能测试永远测不出来 —— 手动点几下，输入规范的格式，一切正常。
   是"我预期它返回 None"这个念头把它揪出来的。

3. **定宽格式的约定必须强制执行，不能靠自觉。**
   "字符串排序即时间排序"是个很省事的设计，但它的前提条件必须在**唯一入口**处守住
   （本项目里就是 `timeutil.parse()`）。

4. **往返校验是个通用套路。**
   凡是要存"格式化字符串"的场景（时间、金额、序列号）都可以用：
   *解析 → 再格式化 → 与原文比对*。

## BUG-019：输出重定向到文件时，脚本自己崩了

- **日期**：2026-09-13
- **所属阶段**：第三阶段 · 收尾
- **涉及文件**：`scripts/check_errors.py`（第 149 行）、新增 `scripts/_console.py`
- **状态**：✅ 已修复

> 这个是"检查工具本身出问题"的 Bug，很有代表性：
> **直接跑一切正常，重定向一下就崩** —— 差别只在"输出去了哪里"。

### 19.1 症状

直接运行异常处理自检脚本，一切正常，最后打印「全部通过 ✅」。

但把输出**重定向到文件**时（比如想把检查结果存档、或者在 `.bat` 里记录日志）：

    python scripts/check_errors.py > result.txt

脚本**在最后一行崩溃**，并且前面的检查结果因为异常也没能正常收尾。

### 19.2 复现

在项目根目录执行（注意 `>` 重定向）：

    python scripts/check_errors.py > data\test\result.txt

### 19.3 报错原文

    Traceback (most recent call last):
      File "...\scripts\check_errors.py", line 149, in <module>
        print(("失败项: " + str(problems)) if problems else "全部通过 \u2705")
        ~~~~~^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
    UnicodeEncodeError: 'gbk' codec can't encode character '\u2705'
    in position 5: illegal multibyte sequence

（`\u2705` 就是那个 ✅ 字符；报错信息里的中文因为控制台编码问题显示成了乱码，这里已还原。）

### 19.4 根因分析

**关键问题：Python 的 `sys.stdout` 用哪个编码，取决于"输出去了哪里"。**

| 运行方式 | `sys.stdout.encoding` | ✅ 能编码吗 |
| --- | --- | --- |
| 直接在控制台运行 | 控制台编码（中文 Windows 下通常是 GBK） | — |
| **重定向到文件** | **按系统 locale 推断**（中文 Windows = `gbk` / `cp936`） | ❌ **不能** |

而 `✅`（U+2705）这个字符**根本不在 GBK 字符集里** —— GBK 是中文字符集，
收录的是汉字和常见符号，emoji 不在其中。

于是 `print()` 在把字符串写出去的时候，编码失败 → 抛 `UnicodeEncodeError`。

**为什么"直接跑正常、重定向才崩"？**
因为很多现代终端（Windows Terminal / VS Code 集成终端）默认使用 UTF-8，
而文件重定向走的是系统 locale（GBK）。**同一个脚本，换了个输出目的地，行为就变了。**

**为什么崩在最后一行？**
因为 ✅ 只出现在结尾的汇总行里。前面的几十项检查都跑完了，
**结果全都在内存里，最后一步没打印出来** —— 也就是说，你重定向拿到的文件是**不完整的**。

> 这类 Bug 的教训和 BUG-010 是同一个家族的：
> **「输出到哪里」会改变程序行为**，重定向是必须专门测一遍的场景。

### 19.5 修复方案（已实施）

**思路**：让 `stdout` 在遇到"编码不出来的字符"时**用替代字符顶替，而不是抛异常**。

**第一步：把 ✅ 换成纯文本。**

    print(("失败项: " + str(problems)) if problems else "全部通过 ✅")
    print(("失败项: " + str(problems)) if problems else "全部通过")      # ← 改成这样

这是治本 —— 只要不输出非 GBK 字符，就不会有编码问题。
也和项目里「.bat 文件必须纯 ASCII」的约定保持一致。

**第二步：加一道通用的防护（新增 `scripts/_console.py`）。**

只换掉这一处，下次别人写个 ★ 或生僻字还会再崩一次。所以再补一层保护：

    def use_safe_output():
        """让 stdout 遇到装不下的字符时用 ? 顶替，而不是抛异常。"""
        stream = getattr(sys, "stdout", None)
        if stream is None:
            return False
        try:
            stream.reconfigure(errors="replace")
            return True
        except (AttributeError, ValueError, OSError):
            return False

然后在脚本的 import 之后调用一次：

    from scripts._console import use_safe_output
    use_safe_output()

目前已经加到 `check_errors.py`、`check_repo.py`、`smoke_test.py` 三个会被重定向的脚本上。

**为什么返回 False 也不报错？**
因为这只是"锦上添花"的防护。旧版本 Python 没有 `reconfigure`，
这时应该继续跑，而不是因为这个可选优化没生效就让整个脚本失败。

**为什么不干脆改成 UTF-8？**
因为那样在中文控制台里直接运行时会显示乱码（终端按 GBK 解码 UTF-8 字节）。
`errors="replace"` 更稳：**编码方式不动，只把装不下的字符降级成 `?`**，
两种场景都能正常跑完。

**扫描结果（全项目）**：只有 3 个文件出现过非 GBK 字符，其中**只有 1 处会真的输出**：

| 文件:行 | 内容 | 会输出吗 |
| --- | --- | --- |
| `check_errors.py:149` | `print(... "全部通过 ✅")` | ✅ **会** —— 就是它崩的 |
| `test_reminder.py:56` | 注释里的 `⚠️` | ❌ 不会（注释不参与运行） |
| `_isolation.py:5` | 文档字符串里的 `⚠️` | ❌ 不会（docstring 不打印） |

> **教训**：不用把整个项目翻个底朝天。**先定位"哪一行真的执行到了"**，
> 范围一下子就缩小到了 1 行。

### 19.6 验证（已通过）

**验证方法**：用 `Start-Process -RedirectStandardOutput` 做**真实文件句柄**重定向
（这正是当初触发崩溃的场景）。

    修复前:
        退出码   : 1
        stdout   : 0 字节        ← 一个字都没写出来
        stderr   : UnicodeEncodeError: 'gbk' codec ...

    修复后:
        退出码   : 0
        stdout   : 11843 字节    ← 完整输出了
        stderr   : 只有 FastAPI 的 httpx 弃用警告（无害）

**一个额外的证据**：修复后生成的文件是 **GBK 编码**的。
这反过来证明了重定向时 Python 用的**确实是 gbk 编解码器** ——
也就是说测试真的命中了出问题的代码路径，而不是"碰巧绕过去了"。

**直接运行也正常**：`python scripts\check_errors.py` 仍能正常跑完，中文不乱码。

### 19.7 经验

1. **★ 「输出到哪里」是程序行为的一部分，必须专门测。**
   控制台 / 重定向到文件 / 管道给别的程序 —— 这三种情况 Python 选的编码可能不一样。
   这已经是本项目第二个由重定向引发的 Bug 了（另一个是 BUG-010）。

2. **★ 命令行工具的提示符号尽量用纯文本。**
   emoji 好看，但它把"字符集兼容性"这个无关的问题引进了你的程序。
   本项目已经因为编码踩过好几次坑（`.bat` 必须 ASCII、PowerShell 脚本要 `utf-8-sig`、
   现在又是 `stdout`）—— **教训是统一的：越少非 ASCII 字符，越省事。**

3. **被检查的工具本身也要有测试。**
   这个脚本是用来"检查异常处理做得好不好"的，结果自己被一个异常打崩了 ——
   有点讽刺，但也说明：**工具代码同样是代码，同样需要验证。**

4. **注意崩溃的位置。**
   它崩在最后一行，导致"前面全跑完了但结果全丢了"。
   如果脚本改成"边检查边写文件"，影响会小很多 ——
   **把结果尽早落盘，比攒到最后一次性输出更抗风险。**

## BUG-020：脚本里写死了本机的绝对路径（还泄露了目录结构）

- **日期**：2026-09-13
- **所属阶段**：第三阶段 · 发布前排查
- **涉及文件**：`scripts/check_errors.py`（第 7 行）
- **状态**：✅ 已修复

> 这条不是"程序跑不起来"的 Bug，而是**发布前隐私排查**扫出来的。
> 它的危害不体现在你本机 —— 你本机跑得好好的 —— 而是体现在**别人下载你的代码之后**。

### 20.1 症状

在按你的要求做「检查有没有把不需要公布的内容排除掉」时，
我用「搜索盘符」（搜 `C:\`、`E:\` 这样的模式）扫了一遍全项目。

结果 `scripts/check_errors.py` 第 7 行赫然写着：

    PROJECT_ROOT = Path(r"<项目绝对路径>")

**项目里其它所有脚本都是这样写的**（对比一下就看出问题了）：

    PROJECT_ROOT = Path(__file__).resolve().parent.parent

只有这一个文件写死了盘符。

### 20.2 复现

把整个 `to_do_list` 文件夹复制到别的位置（比如 U 盘、`D:\` 盘），再运行：

    python scripts\check_errors.py

或者更直接 —— 打开 `scripts/check_errors.py` 看第 7 行。

### 20.3 报错原文

**你本机不会有任何报错** —— 因为那个路径在你机器上确实存在。

在别人机器上会变成 import 失败，或者更糟：
**如果对方碰巧也有个叫 `<项目绝对路径>` 的目录，
它会去导入那个目录里的 `app`** —— 也就是别人自己的一份代码。

### 20.4 根因分析

这个脚本最早是当"临时验证脚本"写的，当时图省事直接把路径粘了进去。
后来它变成了正式脚本，这行**从来没人回头看**。

**它同时造成三个问题**：

| # | 问题 | 后果 |
| --- | --- | --- |
| 1 | **可移植性被破坏** | 违反 AGENTS.md 3.1「项目自包含原则」：复制走整个文件夹就应该能完整工作 |
| 2 | **泄露本机信息** | 把一个真实的个人目录结构（用户名、盘符、项目组织方式）公开到了 GitHub 上 |
| 3 | **可能导入错误的代码** | `sys.path.insert` 会把那个路径插到最前面，导致导入到**别的副本**的 `app` |

第 3 点尤其阴险：它不会报错，只会让"这个脚本测的"和"你改的"**不是同一份代码**，
于是你改了半天，脚本却一直通过 —— 因为它测的是另一个目录里的旧版本。

> **数据安全方面的影响**：这次不用担心。
> 因为 `use_isolated_db()` 在导入 app **之前**就把数据库指向了隔离目录，
> 而且隔离路径是 `_isolation.py` 用**它自己的** `__file__` 算出来的 —— 与这行写死的路径无关。
> 所以第二道防线（`assert_isolated()`）依然是有效的。但这属于**运气好**，不是设计得好。

### 20.5 修复方案

改成和所有其它脚本一致的写法：

    # 【必须用 __file__ 推算路径，不能写死绝对路径】
    # 写死的话：① 用户把项目文件夹换个位置就失效；
    #           ② 把自己的本机目录结构泄露到了公开仓库里。
    PROJECT_ROOT = Path(__file__).resolve().parent.parent

**为什么用 `.resolve()`？**
因为它会把 `..` 和软链接都解析成**绝对的真实路径**。
不 resolve 的话，得到的是 `scripts/..` 这种相对路径，
而后面 `sys.path.insert` 需要的是绝对路径才可靠。

顺带做的事情：
- 给这个脚本补上了缺失的模块文档字符串（说明用法和数据隔离）；
- 移除了一个**导入了却从来没有调用过**的 `cleanup`（属于残留代码）。

### 20.6 验证

**全项目扫描盘符**（搜索 `X:\` 形式的绝对路径）：

    修复前:
        scripts\check_errors.py:7   PROJECT_ROOT = Path(r"X:\...\to_do_list")   ← 真问题
        app\config.py:24            注释里举例"C:\Program Files"          ← 无害
        app\core\autostart.py:51-53 注释里举例"C:\Users\你的名字\..."     ← 无害（带占位符）

    修复后:
        只剩注释里那三处【带"你的名字"之类占位符的示例】 ✅

**功能验证**：`python scripts\check_errors.py` 正常运行，退出码 0。

### 20.7 经验

1. **★ 「绝对路径扫描」应该进发布前检查清单。**
   这类问题功能测试**永远发现不了** —— 因为在你本机它工作得完美无缺。
   一行搜索命令就能扫出来，成本极低，收益极高。

2. **★ 临时脚本"转正"的时候，要重新读一遍。**
   这行代码在它还是临时脚本时是合理的（图快），
   但一旦变成正式脚本、还要跟着项目发布，它就成了问题。
   **代码的"合不合适"取决于它被放在哪里、给谁看。**

3. **路径推算认准一个写法：`Path(__file__).resolve().parent...`。**
   全项目统一，别有的写死有的推算 —— 不统一就一定会漏。

4. **"在你机器上能跑"不是验收标准。**
   对一个要给别人用的项目，验收标准是"在别人机器上能跑"。

## BUG-021：自检脚本跑第二遍必然"失败"

- **日期**：2026-09-13
- **所属阶段**：第三阶段 · 收尾
- **涉及文件**：`scripts/check_errors.py`
- **状态**：✅ 已修复

> 这条是**修完 BUG-019 之后才暴露出来的** —— 修好之后脚本终于能跑完了，
> 结果一跑完就报了两个失败。**如果不去深究，就会得出完全错误的结论。**

### 21.1 症状

修完 BUG-019，第一次运行：**2 项失败**。

     [!!!] 500 异常只被记录一次  实际记录了 2 次
     [!!!] 完整堆栈只记录一次    实际有 3 个堆栈

看起来像是"异常被重复记录了两次"这个老问题又回来了。

**但有一个可疑的细节**：这两项检查的是**日志文件里的内容**。
而日志是**追加**写入的。

### 21.2 复现

在项目根目录，**连续跑两次**：

    python scripts\check_errors.py
    python scripts\check_errors.py

第一次通过，第二次失败 —— 而且失败项**一次比一次多一个**。

**反证实验**（把隔离目录删掉，让日志归零）：

    Remove-Item -Recurse -Force data\test\error_handling
    python scripts\check_errors.py
    → 全部通过 ✅

### 21.3 报错原文

    [!!!] 500 异常只被记录一次  实际记录了 2 次
    [!!!] 完整堆栈只记录一次    实际有 3 个堆栈
    ============================================================================
    失败项: ['500 异常只被记录一次', '完整堆栈只记录一次']

### 21.4 根因分析

脚本里有两条断言：

    text = log_file.read_text(encoding="utf-8", errors="replace")   # 读【整个】日志
    n_500_logs = text.count("未处理的异常")
    check("500 异常只被记录一次", n_500_logs == 1, ...)

**问题出在 `read_text()` 读的是整个文件，而文件是跨次运行累积的**：

    第 1 次运行：日志里 1 次 "未处理的异常"  → n == 1 → 通过 ✅
    第 2 次运行：日志里 2 次                → n == 2 → 失败 ❌
    第 3 次运行：日志里 3 次                → n == 3 → 失败 ❌

而脚本在开始前**没有清理上一次的日志**。

对比一下就清楚：`check_repo.py` 开头有这么一行，`check_errors.py` 却漏了：

    if TEST_DB.exists():
        TEST_DB.unlink()          # 每次从干净的临时库开始

**所以这根本不是"功能坏了"，而是"测试没做隔离"** ——
和 BUG-011 是同一个病根：**测试状态在多次运行之间串味了**。

### 21.5 修复方案

**关键约束**：清理动作必须放在 **`from app.main import app` 之前**。

原因是 `app/main.py` 的第 38 行是这样写的：

    # 日志：尽早初始化，后面的所有日志都靠它
    logging_setup.setup()          # ← 模块级！一导入就执行

它**不在**生命周期的钩子里，而是在**模块顶层**。
也就是说：`from app.main import app` 这一句执行完，日志文件就已经被打开占用了。
**在 Windows 上，被占用的文件是删不掉的** —— 这时候再 `rmtree` 会静默失败。

所以清理代码的位置是这样安排的：

    from app import config                     # ← 安全：config 不碰日志

    import shutil
    shutil.rmtree(config.LOG_DIR, ignore_errors=True)      # ★ 必须在这里
    config.LOG_DIR.mkdir(parents=True, exist_ok=True)

    from app.core import errors as app_errors, logging_setup
    from app.main import app                   # ← 从这里开始日志被占用

**为什么删掉整个目录而不是删一个文件？**
因为日志是"按天轮转"的，目录里可能还有 `app.log.2026-09-12` 这样的历史文件。
只删 `app.log` 会漏掉它们。

**保留了什么**：清理后不再调用 `cleanup()`，
所以 `data/test/error_handling/` 会留着 —— 万一脚本失败，你可以去那里翻完整的日志。
（临时删掉的那个未使用导入见 BUG-020 的"顺带做的事情"。）

### 21.6 验证

**连续运行 3 次，每次都必须是"全部通过"**：

    第 1 次运行 → 失败项 0 个 → 全部通过 ✅
    第 2 次运行 → 失败项 0 个 → 全部通过 ✅
    第 3 次运行 → 失败项 0 个 → 全部通过 ✅

**为什么验证要跑 3 次而不是 1 次？**
因为这类 Bug 是"**第 N 次才出现**"的 —— 跑一次永远发现不了。
**凡是涉及"追加 / 累积 / 历史"的东西，验证就必须做幂等性测试。**

### 21.7 经验

1. **★ 自检脚本必须"可重复运行"。**
   一个跑第二遍就失败的检查工具，比没有检查工具更糟 ——
   它会让你怀疑自己刚写好的代码，浪费大量时间去查一个不存在的问题。
   （这次就差点让我以为"异常重复记录"的老毛病复发了。）

2. **★ 断言不要依赖"追加型数据"的历史。**
   日志、审计表、流水记录这类只增不减的东西，
   一旦在断言里数总数，就必然随运行次数漂移。
   正确做法只有两种：**要么先清空，要么只统计"本次新增的部分"**（记下起始行号/偏移量）。

3. **★ 反过来想：这个"失败"会不会是工具自己的问题？**
   看到失败的第一反应是"我刚改的代码有问题"，但这里真正的原因是脚本没做隔离。
   **判断方法**：先做一个"反证实验"（这里是删掉隔离目录再跑），
   如果环境一干净就通过，那问题就在**测试环境**，不在被测代码。

4. **文件被谁占用了，决定了你什么时候能删它。**
   这次必须搞清楚 `logging_setup.setup()` 到底在哪一行被调用（模块级还是生命周期里）——
   **光看"有没有调用"是不够的，要看"什么时候调用"。**

   这和 BUG-009（校验发生的位置很重要）是同一条道理：
   **在错误的时间点做正确的事，等于没做。**

## BUG-022：文档里给的检查命令，多列了一行

- **日期**：2026-09-13
- **所属阶段**：上线前体检
- **涉及文件**：`docs/上线前检查清单.md`
- **状态**：✅ 已修复

> 这条 Bug 的特别之处：**出错的是文档，不是代码。**
> 而且它不会报错 —— 只会让人对着一个正常的输出**白白紧张一场**。

### 22.1 症状

上线前检查清单里写着这样一条自查命令：

    git ls-files | findstr data

文档承诺："正确的结果应该**只有 `data/.gitkeep` 一行**。"

实际执行，得到的是**两行**：

    app/database.py
    data/.gitkeep

于是自然会产生一个可怕的联想：
**"是不是有敏感文件被 Git 跟踪了？"**

### 22.2 复现

在项目根目录执行：

    git ls-files | findstr data

输出：

    app/database.py
    data/.gitkeep

### 22.3 报错原文

**没有报错。** 命令正常执行、正常退出，返回的也是"真实的"结果 ——
只是这个结果**被误读了**。

### 22.4 根因分析

**`findstr` 默认是「子串匹配」，不是「前缀匹配」。**

看这个文件名：

    app/data【base】.py
         ^^^^
         这 4 个字母就是 "data"

所以它命中了。**命令没错，是文档的措辞把它解读错了。**

真正的问题在**写文档的人**（我）身上：

> 我写下这条命令时，脑子里想的是"要找出 data 目录下的文件"，
> 但**没有实际跑一遍看看输出长什么样**。
> 我把一个「我以为会怎样」的结果，当成「它实际会怎样」写进了文档。

这个问题在本项目里**已经是第三次**了：

| 编号 | 同样是"凭印象写文档" |
| --- | --- |
| BUG-003 | 文档里写错日期（真实日期 2026-09-12，写成了 2026-02-14）|
| BUG-004 | 只写"运行 xxx 命令"，没交代**在哪个文件夹里**敲，用户完全卡住 |
| **BUG-022** | 给的命令没验证过，输出与文档描述不符 |

### 22.5 修复方案

**第一步：把命令换成不会歧义的写法。**

    git ls-files data/                      ← 直接指定目录，最直观

或者保留管道写法，但**加上锚定**：

    git ls-files | findstr /R "^data/"      ← /R 开启正则，^ 表示行首

**第二步：在文档里显式警告这个坑**，免得下一个人（或未来的自己）
再去踩同一个雷：

> ⚠️ **不要写成 `git ls-files | findstr data`** —— `findstr` 默认是**子串匹配**，
> 它会把 `app/database.py` 也列出来（因为「**data**base」里含有「data」），
> 让人误以为有敏感文件被跟踪，白白紧张一场。
> 要匹配**路径开头**，得用锚定写法：`git ls-files | findstr /R "^data/"`。

### 22.6 验证

三种写法对比（在真实仓库上执行）：

    ① git ls-files | findstr data
         app/database.py        ← 误报，因为文件名里有 "data"
         data/.gitkeep

    ② git ls-files | findstr /R "^data/"
         data/.gitkeep          ← 正确

    ③ git ls-files data/
         data/.gitkeep          ← 正确，而且最好记

**结论**：`data/` 下被 Git 跟踪的文件数 = **1**（就是 `.gitkeep`），
**没有任何敏感文件被跟踪**。虚惊一场。

### 22.7 经验

1. **★ 写进文档的命令，必须【先自己跑一遍】，并把【真实输出】贴上去。**
   不是贴"我觉得它会输出什么"。
   这类错误特别隐蔽 —— 因为命令本身是能跑的，没有任何报错提示你写错了。

2. **★ 子串匹配 / 前缀匹配，是一个通用陷阱。**
   `findstr`、`grep`、`LIKE`、字符串 `in` 判断……到处都有这个选择。
   规律是：**默认行为几乎总是"子串匹配"**（因为最宽松），
   而你要的往往是"开头匹配"。**每次都要想一下这个问题。**

3. **★ 「检查命令的误报」比「漏报」更容易被忽视，危害却不小。**
   漏报会让你漏掉问题；**误报会让你开始不相信检查工具**。
   一旦人对告警产生"大概又是误报吧"的心态，
   真正的问题就会被一起忽略掉 —— 那才是最大的风险。

4. **同一个坑踩三次，说明流程有问题，不是运气不好。**
   三次（BUG-003 / BUG-004 / BUG-022）的共性都是**文档没有经过验证**。
   真正的修复不是在文档里补一句"注意"，而是养成习惯：
   **凡是写进文档的命令和输出，先在终端里跑一遍，复制粘贴真实结果。**

## 四、通用排查心法（每次遇到问题先看这里）

### 4.1 四步定位法（从外往里查）

遇到"页面不对"，永远按这个顺序查，**顺序反了会浪费大量时间**：

| 顺序 | 查什么 | 怎么查 | 结论 |
| --- | --- | --- | --- |
| 1 | 后端活着吗 | 浏览器直接开 `/api/health` | 有 JSON → 后端没问题 |
| 2 | 静态文件对吗 | 浏览器直接开 `/static/js/api.js` | 能看到源码 → 路径没问题 |
| 3 | 前端报错了吗 | `F12` → Console 看红字 | 有红字 → 就是 JS 问题 |
| 4 | 请求发出去没 | `F12` → Network 看状态码 | 404 → 路径错；500 → 后端报错 |

### 4.2 三条铁律

1. **先复现，再动手。** 不能稳定复现的问题，改了也是瞎改。
2. **一次只改一个地方。** 同时改三处，好了也不知道是哪处起的作用。
3. **修完必须验证。** 用**同一条**复现命令再跑一次，确认真的好了。

### 4.2.1 养成"让机器检查"的习惯

人能一眼看出的问题很有限。以下几类**一定要写成脚本自动检查**：

| 检查项 | 为什么人不擅长 | 本项目已有的工具 |
| --- | --- | --- |
| 所有网址能不能打开 | 每次改完都手动点一遍太累 | scripts/smoke_test.py |
| 数据层增删改查是否正确 | 边界情况（null、不存在、重复删）太多 | scripts/check_repo.py（34 项） |
| **JS 引用的 DOM 元素是否存在** | 4 个 JS 文件、34 个元素，人眼查不出来 | 见 BUG-008 的检查脚本 |
| 文档里有没有残留的错误字符 | 几百行里找几个特殊字符 | 生成文档时的自检 |

> **判据**：一件事如果你"每次改完都要手动确认一遍"，那它就应该变成脚本。（见 BUG-008）

### 4.3 卡住超过 30 分钟怎么办

1. 把问题**完整写下来**（写的过程常常就能发现漏洞）；
2. 用最小化法：**把代码删到只剩能复现问题的最少几行**；
3. 把报错信息**原样**拿去搜索，不要自己转述成中文再搜；
4. 回头检查最基础的东西：路径对不对、括号配对没、缩进对不对、有没有拼错单词。
