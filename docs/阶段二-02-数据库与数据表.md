## 一、设计思路

### 1.1 这一步要解决的核心问题

功能 1 结束时，程序能跑，但**任何数据都留不住**——关掉服务，一切归零。
本步要解决的就是"持久化"这三个字。

### 1.2 为什么用 SQLite，而不是 JSON 文件？

| 方案 | 优点 | 致命缺点 | 结论 |
| --- | --- | --- | --- |
| JSON 文件 | 简单、肉眼可读 | 并发写会**损坏文件**；查询要全量读进内存；没有事务 | ❌ |
| CSV | 能用 Excel 打开 | 结构太弱、无事务、无法存列表 | ❌ |
| **SQLite** | 单文件、有事务、支持复杂查询、Python 自带 | （对单人使用）没有 | ✅ |
| MySQL / Postgres | 支持大量并发 | 要装服务、要配置 | ⏳ 将来部署公网再换 |

**SQLite 最妙的一点**：一个数据库就是一个文件。你把它复制走，就是完整备份；
把它删掉，就是彻底重置。对"本地离线工具"来说是最优解。

### 1.3 为什么用 SQLAlchemy（ORM），而不是直接写 SQL？

对比一下同一件事的两种写法：

    # 直接写 SQL
    cursor.execute("INSERT INTO tasks (title, status) VALUES (?, ?)", (title, "todo"))

    # 用 ORM
    task = Task(title=title, status="todo")
    session.add(task)

ORM 带来的三个实际好处：

1. **防 SQL 注入**：手写 SQL 拼接字符串是安全漏洞的头号来源，ORM 自动处理转义；
2. **改数据库不用改业务代码**：以后从 SQLite 换成 Postgres，只改 `database.py` 一行；
3. **有类型提示**：编辑器能自动补全字段名，打错字立刻发现。

代价是多学一套 API——但每个项目都要付这个成本，值得。

### 1.4 为什么单独建一个 repositories 层？

**因为"数据存哪里"和"业务规则是什么"是两件会各自变化的事。**

举个例子：以后加一条规则"标题不能超过 200 字"——这属于业务规则，写在 services 层。
而"数据存在 SQLite 还是 Postgres"——这属于存储细节，写在 repositories 层。
两者混在一起，改一个就会碰到另一个。

所以本项目的铁律是：

> ***全项目只有 repositories 层能碰数据库。services 层要数据，只能调用 repositories。***

### 1.5 为什么必须开 WAL 模式（本步最重要的一个技术决策）

SQLite 默认的工作方式是：**一个人写的时候，别人不能读**。
一旦同时读写，就会抛出 `database is locked` 错误，程序直接卡死。

而本项目第 9 步会有这样一个场景：

- **后台提醒线程**：每 20 秒读一次数据库（找该提醒的任务）
- **你在网页上**：同时点"添加待办"，往数据库里写

**这两个动作必然同时发生**，不开 WAL 就一定出问题。

    PRAGMA journal_mode=WAL

WAL = Write-Ahead Logging（预写日志）。开启后：写操作先写日志文件，读操作读主文件，
**读写不再互相阻塞**。代价是 `data/` 目录下会多出 `todo.db-wal` 和 `todo.db-shm` 两个文件
（这是正常的，不是垃圾文件，不要手动删）。

> **这就是"提前设计"的价值**：如果等到第 9 步才发现这个问题，
> 你要回头改数据库配置、还要排查一堆"偶发卡死"，成本高得多。

### 1.6 为什么把时间处理单独抽成 timeutil.py？

因为时间是最容易出 Bug 的东西。常见事故：

- 有的地方存 `2026-09-12 08:30`，有的地方存 `2026-09-12T08:30:00`，比较时永远不相等；
- 某个文件忘了补零，存成 `2026-9-2 8:30`，字符串排序就全乱了。

**规定：全项目只允许在 `core/timeutil.py` 里做"时间 ↔ 字符串"的转换。**
这一条能消灭绝大部分时间相关的 Bug，将来要改成带时区的方案也只动一个文件。

### 2.2 `app/core/timeutil.py`（新增）

    from datetime import datetime, timedelta
    from app import config


    def now() -> datetime:
        """当前时间（秒和微秒归零，因为本项目只精确到"分"）。"""
        return datetime.now().replace(second=0, microsecond=0)


    def now_str() -> str:
        return format_dt(datetime.now())


    def format_dt(dt: datetime) -> str:
        return dt.strftime(config.DATETIME_FORMAT)


    def parse(text):
        """解析失败【不抛异常】，返回 None —— 让失败变成可判断的普通返回值。"""
        if not text:
            return None
        try:
            return datetime.strptime(str(text).strip(), config.DATETIME_FORMAT)
        except (ValueError, TypeError):
            return None


    def is_valid(text) -> bool:
        return parse(text) is not None


    def add_minutes(text: str, minutes: int) -> str:
        dt = parse(text) or now()
        return format_dt(dt + timedelta(minutes=minutes))


    def date_part(text: str):
        return text[:10] if text and len(text) >= 10 else None

### 2.3 `app/database.py`（新增，本步最核心的文件）

    from contextlib import contextmanager
    from sqlalchemy import create_engine, event
    from sqlalchemy.orm import DeclarativeBase, sessionmaker
    from app import config

    DATABASE_URL = "sqlite:///" + config.DB_PATH.as_posix()

    engine = create_engine(
        DATABASE_URL,
        echo=False,                                     # 改成 True 可以看到每条 SQL
        future=True,
        connect_args={"check_same_thread": False},      # 允许跨线程使用连接
    )


    @event.listens_for(engine, "connect")
    def _on_connect(dbapi_connection, connection_record):
        """每次建立连接时打开两个关键开关。"""
        cursor = dbapi_connection.cursor()
        cursor.execute("PRAGMA journal_mode=WAL")       # 读写不再互相阻塞
        cursor.execute("PRAGMA foreign_keys=ON")        # SQLite 默认不开外键检查
        cursor.close()


    class Base(DeclarativeBase):
        pass


    SessionLocal = sessionmaker(bind=engine, autoflush=False, expire_on_commit=False)


    @contextmanager
    def get_session():
        session = SessionLocal()
        try:
            yield session
            session.commit()        # 正常结束 -> 提交
        except Exception:
            session.rollback()      # 出错     -> 回滚，绝不写一半
            raise
        finally:
            session.close()         # 无论如何 -> 关闭


    def init_db():
        from app import models      # 写在函数内部，解开循环 import
        Base.metadata.create_all(bind=engine)

## 三、关键代码逐行解释

### 3.1 `DATABASE_URL = "sqlite:///" + config.DB_PATH.as_posix()`

- `sqlite:///` 是 SQLAlchemy 的数据库地址格式。**三个斜杠**：前两个是协议分隔，
  第三个开始才是文件路径。写两个斜杠会被理解成"内存数据库"。
- `as_posix()` 把 Windows 的反斜杠路径（`X:\项目\to_do_list`）转成正斜杠（`X:/项目/to_do_list`）。
  **为什么必须转？** 反斜杠在字符串里是转义符，`\d`、`\t` 会被误解；
  正斜杠在任何操作系统上都能正确表示路径。

### 3.2 `connect_args={"check_same_thread": False}` 为什么必须加？

SQLite 的 Python 驱动默认禁止**跨线程**复用同一个连接（防止多线程写坏数据）。

但本项目的结构是：

- FastAPI 处理"同步函数"时，会**在线程池里**执行（不是主线程）；
- 第 9 步的后台提醒线程，是**另一个线程**。

如果不开这个开关，你会看到这样的报错：

    SQLite objects created in a thread can only be used in that same thread.

> ⚠️ 注意：关掉这个安全检查的前提是**有 WAL + 每次操作用独立 session**。
> 我们的 `get_session()` 每次都是新连接，所以是安全的。
> 如果你以后看到别人说"不要关它"，那是因为他们的用法不同——**要理解原因，不要背结论**。

### 3.3 `expire_on_commit=False` 解决了什么坑？

SQLAlchemy 的默认行为是：**commit 之后，对象里的数据会被清空**，
下次访问属性时会自动去数据库重新查一遍。

问题在于：我们的 `get_session()` 在 commit 之后立刻 `close()` 了 session。
这时你再去读 `task.title`，它会尝试重新查询，但 session 已经关了：

    DetachedInstanceError: Instance <Task> is not bound to a Session

改成 `expire_on_commit=False` 后，commit 之后对象数据仍然在内存里，可以正常读取。
**这是"仓库层能把对象安全地返回给上层"的关键。**

### 3.4 `get_session()` 用 `with` 而不是手写 close

    with get_session() as session:
        session.add(obj)
    # 离开时自动 commit + close；出异常则 rollback + close

手写 `session.close()` 的问题是：**一旦中间抛异常，close 就被跳过了**，
连接一直不还，久了连接池被占满，程序表现为"越用越慢，最后卡死"。

`with` 的 `finally` 保证无论如何都会关闭。**这类"资源泄漏"是最难排查的 Bug 之一，
用 `with` 可以从根上避免。**

### 3.5 为什么 `init_db()` 里的 import 写在函数内部？

因为文件之间形成了循环引用：

    models.py  ──需要 Base──>  database.py
    database.py ──需要 Task──>  models.py

Python 在加载 `database.py` 顶部时就会执行 `from app import models`，
此时 `models.py` 又回头要 `database.py` 的 `Base`——而它还没定义完，直接报错。

把 import 放进函数内部后，**只有真正调用 `init_db()` 时才导入**，
那时两个模块都已经加载完毕，循环就解开了。

> 这是 Python 里处理循环依赖的标准手法之一。另一种做法是把 `Base` 单独放进第三个文件。

### 3.6 `flush()` 和 `commit()` 的区别

| 操作 | 做了什么 | 事务是否结束 |
| --- | --- | --- |
| `flush()` | 把 SQL 发给数据库执行 | ❌ 没结束，还能回滚 |
| `commit()` | 确认提交，数据真正落盘 | ✅ 结束 |

在 `create()` 里用 `flush()` 是有目的的：**执行 INSERT 后数据库才会分配自增 id**，
我们要拿到这个 id 返回给调用方，但又不想在这里就 commit（提交时机交给 `with` 统一管理）。

### 3.7 索引（Index）到底解决了什么？

没有索引时，数据库要**一行一行翻完整张表**才能找到符合条件的记录，这叫全表扫描。

本项目建了三个索引，都是有明确理由的：

| 索引 | 理由 |
| --- | --- |
| `idx_tasks_status` | 列表页按"未完成 / 已完成"筛选是**最频繁**的操作 |
| `idx_tasks_remind` | 提醒线程**每 20 秒**扫描一次，没有索引会越来越卡 |
| `idx_tasks_user_due` | 日历视图要按"用户 + 日期范围"查询 |

> **不要乱建索引**：索引会让查询变快，但会让写入变慢（每次写都要更新索引），还占空间。
> **只给"经常用来查询的字段"建索引。**

### 3.8 字段白名单：一个防呆设计（重要）

    allowed = {"title", "description", "status", ...}
    unknown = set(fields) - allowed
    if unknown:
        raise ValueError("不允许修改这些字段: " + ...)

如果没有这段，攻击者（或者几个月后犯迷糊的你自己）可以这样调用：

    task_repo.update(3, created_at="1999-01-01 00:00", id=999)

结果就是**创建时间被篡改、主键被改乱**，数据彻底不可信。

**"只允许改我允许你改的东西"** 这个思路叫白名单（whitelist），
比"禁止你做坏事"的黑名单安全得多——因为坏事的可能性是无限的，而合法的操作是有限的。

### 3.9 `due_for_reminder()` 的四个条件，每一个都不能少

    where(
        Task.remind_enabled == 1,                       # ① 开了提醒
        Task.status == "todo",                          # ② 还没完成
        Task.remind_at <= now_text,                     # ③ 提醒时间已到
        Task.reminded_at.is_(None),                     # ④ 还没提醒过 ★
    )

少任何一个都会出问题：

| 缺哪个 | 后果 |
| --- | --- |
| ① | 用户明确关掉了提醒，却被弹窗骚扰 |
| ② | 已经做完的事还弹出来提醒你 |
| ③ | 未来的任务提前弹出来 |
| **④** | **同一条提醒每隔 20 秒弹一次，直到你崩溃** |

第 ④ 条是本项目**防止重复提醒的核心设计**：弹过一次就写入 `reminded_at`，
之后无论程序重启、页面刷新多少次，它都不会再被扫出来。

## 四、如何运行

### 4.0 先搞清楚：命令要在哪个文件夹里敲？

**很多初学者会卡在这里，所以单独讲一节。**

首先看一条命令：

    python scripts/demo_db.py

它**不是文件路径，而是一条命令**。拆开看是三部分：

| 部分 | 是什么 | 说明 |
| --- | --- | --- |
| `python` | 程序名 | 系统里安装的 Python |
| `scripts/demo_db.py` | **参数**，指向一个文件 | 相对路径，相对于"你当前所在的文件夹" |
| 中间的空格 | 分隔符 | 表示"用 python 去执行后面这个文件" |

所以：

> ⚠️ **在资源管理器里搜索"python scripts"永远搜不到**——因为它不是一个文件名。
> `scripts` 是一个**文件夹**，`demo_db.py` 是它里面的一个**文件**。

**并且，这条命令必须在"项目根目录"下敲。** 因为 `scripts/demo_db.py` 是**相对路径**，
意思是"从我现在所在的位置往下找"。如果你在 `C:\Users\你的名字` 下敲，
Python 会去那里找 `scripts` 文件夹，找不到就报：

    can't open file 'scripts/demo_db.py': [Errno 2] No such file or directory

## 六、常见问题排查

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| `can't open file 'scripts/demo_db.py'` | 命令行**不在项目根目录**，相对路径找不到文件 | 见 4.0.1 的三种方法；或在根目录先执行 `dir` 确认能看到 `app`、`scripts` |
| 在资源管理器里搜不到 `scripts` | `scripts` 是**文件夹**，且命令 `python scripts/demo_db.py` 不是文件名 | 见 4.0；最省事的办法是**双击 `check.bat`** |
| `ModuleNotFoundError: No module named 'app'` | 直接运行了 `scripts/demo_db.py`，Python 只把 `scripts/` 当搜索起点 | 必须在**项目根目录**运行；脚本里已加 `sys.path.insert(...)` 兜底 |
| `sqlite3.OperationalError: database is locked` | 没有开 WAL，或有两个进程同时写 | 确认 `database.py` 里有 `PRAGMA journal_mode=WAL` |
| `DetachedInstanceError` | session 已关闭，还在读对象属性 | 确认 `sessionmaker(..., expire_on_commit=False)` |
| `SQLite objects created in a thread can only be used in that same thread` | 没加 `check_same_thread=False` | 见 3.2 |
| 数据写进去了，但 `--list` 看不到 | 用了不同的数据库文件 | 检查有没有残留的 `TODO_DB` 环境变量；确认 `config.DB_PATH` 指向哪 |
| 中文显示成乱码 | 命令行编码不是 UTF-8 | 命令行执行一次 `chcp 65001`；或设 `set PYTHONUTF8=1` |
| 改了两分钟内的字段，`updated_at` 看起来没变 | **不是 Bug**：决策 3B 只精确到"分" | 这是有意为之。若确实需要秒级，改 `config.DATETIME_FORMAT` 即可 |
| 数据库文件坏了 | 极少数情况（如断电） | 直接删掉 `data/todo.db` 重启，程序会自动重建（数据会丢，所以第 3 阶段会加自动备份） |
